## 1. 设计约束

| 约束 | 事实 | 影响 |
| --- | --- | --- |
| 团队规模 | 小团队 | 不上微服务；抽象层数克制 |
| 代码规模 | 83k 行（Go 58.5k + TS 20k） | 值得重构，但要能增量做 |
| 现状 | 已做过一轮"形式主义改造" | **本次重点是拆除表演性抽象**，不是再加一层 |
| 部署 | 单体后端 + 2 个独立前端 app，只有 local compose | 拆为 `backend`/`frontend`/`frontend_admin` 三目录 + `deploy/`；补生产流水线 |
| 语言 | Go 1.25 + Nuxt 4 | 用 `internal/` 强制边界；用 codegen 消除类型漂移 |

### 三条不可动摇的原则

1. **依赖必须是接口，不是结构体。**
   现状 30 个 `Deps` 都含 `*gorm.DB`，等于每个包都能操作整台数据库。目标：handler 只持有 3-5 个方法的能力接口，**拿不到 DB 连接**。

2. **规则必须可执行，不能靠文档。**
   `arch_guard.ps1` 的教训：符号匹配会空转，PowerShell 在 CI 跑不了，规则写在脚本里没人看。目标：规则写成 `go test`，进 CI，违规即失败。

3. **抽象必须能替换，否则删掉。**
   `platform/dbx` 只有一行 `return core.InitDB(...)`，无接口无第二实现——它的唯一作用是增加一层文件。目标：要么定义接口并有 fake，要么直接用 `core.InitDB`。

## 2. 目标形态总览

> 仓库级目录（取消 monorepo，四部分解耦）：`backend/`（Go）、`frontend/`（Nuxt 读者站）、`frontend_admin/`（Nuxt 管理后台）、`deploy/`（Docker / compose / nginx）。三部分通过"后端自动生成的 openapi"这唯一的契约耦合，不存在代码级共享包。

```
┌──────────────────────────────┐   ┌──────────────────────────────┐
│  frontend/  (Nuxt 读者站)      │   │  frontend_admin/ (Nuxt 后台)    │
│  ── 只做 UI + BFF 代理         │   │  ── 只做 UI + BFF 代理         │
│  ── 类型由 openapi 生成，不手写 │   │  ── 类型由 openapi 生成，不手写 │
└───────────────┬──────────────┘   └───────────────┬──────────────┘
                │ HTTP / SSE / WS（契约：openapi.json）  │
                └──────────────────┬───────────────────┘
┌───────────────────────────────▼───────────────────────────────┐
│  backend/  (Go)                                                 │
│                                                                 │
│  cmd/server/main.go  ← 唯一合成根，唯一允许 new 具体实现的地方     │
│                                                                 │
│  internal/article/    ← 垂直模块（domain / app / adapter）         │
│  internal/comment/  internal/user/  internal/chat/ ...           │
│  internal/ai/                                                  │
│                                                                 │
│  internal/platform/   ← 真实适配器（有接口 + fake；含 llm 网关）    │
└─────────────────────────────────────────────────────────────────┘
                │
   MySQL / Redis / ES / ClickHouse / LLM / 七牛

┌───────────────────────────────────────────────────────────────┐
│  deploy/  (基础设施，不属于任一 app)                              │
│  ── docker / compose / nginx；反向代理唯一 upstream 在此定义        │
└───────────────────────────────────────────────────────────────┘
```

### 关键变化：从"水平分层"改为"垂直模块"

**现状是水平切分**：`api/` 170 包、`service/` 170 包、`repository/` 8 包。后果已经出现——`article_api` 55 文件 6,012 行，而 `article_service` **1 文件 99 行**。同一个功能被切到三个顶层目录，且切得极不均匀。

**目标是垂直切分**：每个业务模块是一个自包含的目录。

```
internal/article/
├── domain/          # 实体、值对象、业务规则、端口定义（零外部依赖）
├── app/             # 用例编排，持有事务边界
└── adapter/         # HTTP handler + DTO + MySQL 实现 + ES 投影
```

三个包，不是五个。理由：
- `domain` 必须独立（可零依赖测试）
- `app` 必须独立（可注入 fake 端口测试）
- `adapter` 装"所有与外界打交道的东西"——HTTP 和 DB 都是适配器，放一起减少包数，且依赖方向仍是单向的 `adapter → app → domain`

**取舍说明**：纯 DDD 会把 `http` 和 `store` 分成两个 adapter 包。这里合并，是因为两者生命周期一致、都只被合成根构造，分开只会增加 import。代价是 `adapter` 包会比较大（单模块 2,000-4,000 行），用文件粒度控制。

## 3. 真实依赖注入

### 3.1 先看对比

**现状（Deps 装箱）：**

```go
// api/article_api/enter.go
type Deps struct {
    DB     *gorm.DB        // ← 整台数据库
    Redis  *redis.Client
    Logger *logrus.Logger
    ...
}

func (h *ArticleApi) Detail(c *gin.Context) {
    var count int64
    h.App.DB.Model(&models.ArticleDiggModel{}).
        Where("article_id = ?", id).Count(&count)     // ← 拿到 DB 就随便查
}
```

问题：`Deps` 里有 17 个字段，看不出这个 handler 到底依赖什么；能查任何表；测试要构造完整 `Deps`。

**目标（能力接口）：**

```go
// internal/article/app/port.go
type Reader interface {
    FindByID(ctx context.Context, id kernel.ID) (*article.Article, error)
    ListPublished(ctx context.Context, q ListQuery) ([]article.Article, int, error)
}

type DiggCounter interface {
    CountByArticle(ctx context.Context, id kernel.ID) (int64, error)
}

// internal/article/app/service.go
type Service struct {
    reader  Reader          // 只读这篇文章，不能写
    diggs   DiggCounter     // 只能数点赞，不能删点赞
    tx      TxManager
    outbox  Outbox
}

func New(reader Reader, diggs DiggCounter, tx TxManager, outbox Outbox) *Service {
    return &Service{reader: reader, diggs: diggs, tx: tx, outbox: outbox}
}
```

好处：
- **依赖可见**：4 个字段，一眼看出这个用例需要什么
- **能力受限**：`DiggCounter` 只有一个方法，**调不到 `Delete`**
- **可测试**：fake 只需实现 1 个方法
- **不可绕过**：没有 DB 连接，想写 SQL 也写不了

### 3.2 端口的定义位置

**端口由使用方定义**，不是由实现方定义。

```
internal/article/domain/port.go    ← 仓储端口（聚合根自己的持久化契约）
internal/article/app/port.go       ← 用例需要的外部能力（跨模块、外部服务）
```

跨模块调用时，**消费方定义接口**：

```go
// internal/comment/app/port.go
// 评论模块需要"检查文章是否可评论"，它自己定义需要什么，而不是 import article 的 service
type ArticleGate interface {
    CanAcceptComment(ctx context.Context, id kernel.ID) (bool, error)
}
```

这样 `comment` 不依赖 `article`，只依赖自己定义的接口。`article` 的 adapter 提供一个满足它的实现，在合成根里接上。

**这是模块解耦的关键**：模块之间不 import，只在合成根连线。

### 3.3 合成根

```go
// cmd/server/main.go —— 唯一允许 import 所有具体实现的地方
func main() {
    cfg := config.MustLoad(flagFile)

    infra := platform.New(cfg)          // DB / Redis / ES / CH / Logger
    defer infra.Close()

    // 每个模块的装配是一个函数，main 只负责连线
    articleSvc  := wireArticle(infra)
    commentSvc  := wireComment(infra, articleSvc.Gate)   // ← 跨模块通过接口
    aiSvc       := wireAI(infra, articleSvc.Projection)

    router := httpiface.NewRouter(articleSvc, commentSvc, aiSvc, ...)
    server.Run(cfg.System, router)
}
```

`wireXxx` 函数放在各模块的 `adapter/wire.go`，**依赖图完全可读**。

**约束**：
- `main.go` 之外任何地方不得 `new` 具体实现（archcheck 检查）
- 不得存在 `Deps` 这类聚合结构体
- 不得有包级可变状态

### 3.4 为什么不上 wire / dig

Go 生态有 `wire`（代码生成）和 `dig`（反射）。

**都不用**。理由：本项目模块数约 12 个，手写装配约 150 行。引入代码生成会让启动流程不可读、出错提示晦涩；反射会把编译期错误推后到启动期。手写 150 行换来"启动流程就是一张图"，这笔交易划算。

## 4. 模块边界与跨模块协作

### 4.1 模块划分

| 模块 | 聚合根 | 现状来源 |
| --- | --- | --- |
| `article` | Article / Category / Tag / Favorite / Top / ViewHistory | `api/article_api`(55) + `article_service`(1) + 3 个 repo |
| `comment` | Comment | `api/comment_api`(15) + `comment_service`(1) |
| `user` | User / Session / Profile | `api/user_api` + `user_service` |
| `auth` | Identity（QQ/邮箱/密码） | `api/user_api/auth_api` |
| `chat` | ChatSession / ChatMessage | `api/chat_api` + `chat_service` |
| `social` | Follow | `api/follow_api` + `follow_service` |
| `media` | Image / ImageRef | `api/image_api` + `image_service` |
| `search` | （查询侧无状态） | `api/search_api` + `search_service` + `es_service` |
| `ai` | （能力型） | `api/ai_api` + `ai_service`(27) |
| `notification` | GlobalNotif / SiteMsg | `api/{global_notif,sitemsg}_api` + `message_service` |
| `site` | SiteConfig / Banner | `api/{site,banner}_api` + `site_service` |
| `analytics` | （只读投影） | `api/data_api` + `log_service`(17) |
| `platform` | — | `platform/` + `core/` |

### 4.2 跨模块的三条规则

| 场景 | 做法 | 禁止 |
| --- | --- | --- |
| 需要读别的模块的数据 | 消费方定义窄接口，如 `ArticleGate` | import 别的模块的 domain 实体 |
| 需要被别的模块通知 | 发领域事件（Outbox） | 直接调用别的模块的 service |
| 确实需要共享的值对象 | 放 `internal/kernel`（ID、分页、时间） | 把业务实体放 kernel |

**唯一例外**：`kernel` 包可以被所有模块 import，但它只能有值对象，不能有业务规则。

### 4.3 依赖方向（编译器强制）

```
adapter  →  app  →  domain
   ↓                  ↑
platform ─────────────┘（domain 定义端口，platform 实现）
```

| 层 | 可 import | 禁止 |
| --- | --- | --- |
| `*/domain` | 标准库、`internal/kernel` | app、adapter、platform、gin、gorm、redis、es |
| `*/app` | 本模块 domain、`internal/kernel` | 本模块 adapter、其他模块、gin、gorm |
| `*/adapter` | 本模块 app/domain、`internal/platform`、第三方库 | 其他模块的内部包 |
| `platform` | 标准库、第三方库、`internal/kernel` | 任何业务模块 |
| `cmd` | 全部 | — |

## 5. 数据访问：从"到处 SQL"到"一个归属"

### 5.1 repository 的正确形态

**现状**：`func X(db *gorm.DB, ...)` —— 连接由调用方传入，repo 只是"SQL 语句的存放处"。

**目标**：repo 持有连接，实现 domain 定义的端口。

```go
// internal/article/adapter/mysql.go
type mysqlRepo struct{ db *gorm.DB }

func NewMySQLRepo(db *gorm.DB) *mysqlRepo { return &mysqlRepo{db: db} }

// 实现 domain.ArticleRepository
func (r *mysqlRepo) FindByID(ctx context.Context, id kernel.ID) (*article.Article, error) {
    var m articleRow
    err := r.db.WithContext(ctx).Where("id = ?", id).Take(&m).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, article.ErrNotFound
    }
    return m.toDomain(), err
}
```

关键差别：
- **连接在构造时注入一次**，不再层层传递
- **方法签名不带 `*gorm.DB`**
- **返回领域错误**（`article.ErrNotFound`），不是 `gorm.ErrRecordNotFound`
- **持久化模型 `articleRow` 与领域实体 `article.Article` 分离**，用 mapper 转换

### 5.2 为什么这次要真的分离领域实体与持久化模型

现状 `models.ArticleModel` 同时是：GORM 模型、API 响应体、业务对象。后果：
- 加一个 `gorm:"-"` 字段怕影响 API
- `BeforeDelete` 钩子里做级联删除 + 刷缓存 + 打日志（`models/article_model.go`）
- 领域规则无处安放

目标：
```
internal/article/domain/entity.go   ← Article（纯 struct + 方法）
internal/article/adapter/mysql.go   ← articleRow（GORM tag）+ mapper
internal/article/adapter/dto.go     ← HTTP 请求/响应
```

三者的字段可以不同。这是必要的样板成本——它换来的是"改数据库不影响 API、改 API 不影响业务规则"。

### 5.3 事务

事务边界在 **app 层**，通过 `TxManager` 端口：

```go
// internal/platform/tx.go
type TxManager interface {
    InTx(ctx context.Context, fn func(ctx context.Context) error) error
}

// internal/article/app/create.go
func (s *Service) Create(ctx context.Context, cmd CreateCmd) (*article.Article, error) {
    a, err := article.New(cmd.AuthorID, cmd.Title, cmd.Content)
    if err != nil { return nil, err }

    err = s.tx.InTx(ctx, func(ctx context.Context) error {
        if err := s.repo.Save(ctx, a); err != nil { return err }
        return s.outbox.Publish(ctx, a.CreatedEvent())   // 与业务同事务
    })
    return a, err
}
```

handler 不再 `Begin/Commit`。现状 12 个 handler 里手写事务的地方全部上移。

## 6. 前端架构

### 6.1 不做共享代码包，靠"契约"解耦

现状 web 与 admin 重复约 500 行（http client、image service、env 加载），且依赖版本已漂移 7 项。在 monorepo 时代，标准解法是抽 `packages/shared-*`。

但本方案已决定**取消 monorepo、拆分为三个解耦目录**，因此不再引入共享代码包。替代方案：

- **类型共享 → 各自生成，不共享代码**。两个前端都从 `backend` 自动生成的 `openapi.json`，用 `openapi-typescript` **各自生成**一份 `src/api/generated/api.gen.ts`。共享的是"契约"，不是"代码"——这正是解耦的本质。
- **http client / UI 组件 → 接受可控的重复**。两个 app 设计语言不同，强行合并收益低；允许各自保留一份薄 client。若未来重复显著扩大，再抽独立的 `@blogx/ui` 发布包（属后续独立工作，不在本次范围）。
- **env 加载 → 各自一份 dotenv 解析**（约 45 行），不再跨 app 引用。

这样 `frontend/` 与 `frontend_admin/` 之间**零代码依赖**，只有对后端契约的 consumer 关系，符合"各部分解耦"的决策。

### 6.2 契约自动维护（像 FastAPI 那样"代码即契约"）

现状：`openapi/blogx.openapi.json` 14,462 行手写、**全仓无人消费**；前端 736 行手写 interface。已删除手写文档。

目标流水线（**完全自动，无手写契约文件**）：

```
后端 handler + struct + swag 注解
        │  make openapi  (swag init)
        ▼
backend/openapi.json          ← 构建产物，自动生成（可纳入 git 供工具消费，CI 校验生成一致性）
        │  openapi-typescript  （每个前端各自跑）
        ├──────────────▶  frontend/src/api/generated/api.gen.ts
        └──────────────▶  frontend_admin/src/api/generated/api.gen.ts
```

- 后端：handler 加 `// @Summary` / `// @Param` / `// @Success` 注解，`make openapi` 生成。**单一来源是后端代码**，与 FastAPI 用类型推导生成 OpenAPI 是同一思路。
- 前端：每个 app 用 `openapi-typescript` 从同一份 `openapi.json` 生成 `api.gen.ts`，**禁止手写 API 类型**。
- CI 校验：`make openapi && git diff --exit-code backend/openapi.json`，防止有人手改生成的 json。

> 关于"有没有像 FastAPI 那样自动维护"：有，且是最贴近的做法。`swag` 读 Go 代码与注解生成 OpenAPI（FastAPI 读 Python 类型生成，原理一致）。若想更进一步摆脱注解、做到"零标注自动推导 schema"，可评估 `go-fuego`（用 Go 泛型 handler 自动产出 OpenAPI），但那需要替换 Gin 路由层——本次不换框架，故以 `swag` 为首选；`go-fuego` 作为可选升级项，待 S2 评估。

这样 118 个 operation ↔ 前端类型的漂移从"运行时 500"变成"编译期报错"，且不再有 14k 行需要人维护的文档。

### 6.3 单一上游（删除 `_backend` / `_origin` 别名）

`/api`、`/_backend`、`/_origin` 全部指向同一个后端，nginx 又复制 3 遍——这是无意义的别名噪音。

**决策：只保留单一上游。**

```
frontend/        →  server/routes/api/[...path].ts  唯一代理  →  $API_BASE_URL  (后端)
frontend_admin/  →  server/routes/api/[...path].ts  唯一代理  →  $API_BASE_URL  (后端)
deploy/nginx     →  upstream blogx_backend { ... }  唯一 upstream 定义处
```

- 两个前端的 Nuxt server **只保留 `api/[...path].ts` 一个代理入口**，`_backend`、`_origin` 两个文件删除。
- `_origin`（资源源站）不走 Nuxt 代理，由后端或 CDN 直出。
- **反向代理的唯一 upstream 定义在 `deploy/nginx`**（基础设施层），不在 app 代码里——两个 app 通过环境变量 `API_BASE_URL` 指向它。
- 若历史上确有外部调用方在用 `/_backend`，在 `deploy/nginx` 用 301 过渡一个版本周期后删除。

nginx 的 4 份 conf 进一步合并为 1 个模板 + `envsubst`（详见 [05 §3](./05-代码质量补审.md)）。

### 6.4 页面拆分

`pages/studio/write.vue` 2,043 行是前端最大的技术债。目标拆为：

```
pages/studio/write.vue              < 200 行（编排）
components/studio/write/
├── EditorPane.vue                  # 编辑器
├── MetaPanel.vue                   # 标题/摘要/分类/标签
├── AiAssistPanel.vue               # AI 改写/评分
├── PublishBar.vue                  # 保存/发布/预览
└── useWriteDraft.ts                # 草稿状态（组合式函数）
```

Store 循环依赖（`auth ↔ chat/message`）改为：`auth` 只发事件，不直接调用其他 store。

## 7. 让架构规则真正可执行

这是本次重构**与上一轮形式主义改造的分界线**。

### 7.1 废弃 PowerShell 守卫

`arch_guard.ps1` 的三个致命问题：符号匹配会空转、Linux/CI 跑不了、与 `test/architecture/` 重复。

**全部删除。**

### 7.2 用 Go AST 写规则

```
tools/archcheck/
├── main.go           # 入口，可独立运行也可被 test 调用
├── rules.go          # 规则定义
└── rules_test.go     # 规则自身的测试
```

用 `golang.org/x/tools/go/packages` 加载类型信息，**基于 import 图和类型签名**判断，而不是正则。

首批规则（每条都必须能在现有代码上**跑出违规**，否则说明规则无效）：

| 规则 | 判定方式 | 现状应报出的违规 |
| --- | --- | --- |
| `domain` 不得 import gin/gorm/redis/es | import 图 | 待迁移代码 |
| `app` 不得 import `adapter`/`platform` 具体实现 | import 图 | — |
| 任何包不得定义含 `*gorm.DB` 的导出结构体 | 类型检查 | **32 个 Deps** |
| `adapter` 之外不得出现 `*gorm.DB` | 类型检查 | **61 个 api 文件** |
| 模块之间不得互相 import | import 图 | 待迁移代码 |
| 单文件不得超过 800 行 | 行数 | `article_sync.go` 等 4 个 |
| `enter.go` 不得超过 50 行 | 行数 | 65 个 |

**最后两条特别重要**：现状所有守卫都不管文件大小，导致 1,547 行的文件能安静存在。把它变成规则，腐化才有刹车。

### 7.3 规则要有"自检"

```go
// tools/archcheck/rules_test.go
// 每条规则都必须能在一段人造的违规代码上报错，否则规则本身无效
func TestRuleDetectsViolation(t *testing.T) {
    for _, r := range rules {
        if !r.Matches(violationFixture(r)) {
            t.Fatalf("规则 %s 无法检测违规，规则本身失效", r.Name)
        }
    }
}
```

这条测试是防止"又一轮永真守卫"的关键。

## 9. 不做什么

- **不拆微服务**。单体后端 + 2 个独立前端是正确的形态。
- **不上 wire / dig**。手写 150 行装配更可读。
- **不引入完整 DDD**（工厂/规格/领域服务全上）。只用实体 + 值对象 + 端口。
- **不重写前端**。Nuxt 4 选型正确，只拆组件、各自生成类型（不抽共享代码包）。
- **不换 Gin / GORM**。
- **不保留 monorepo / workspace / `packages/`**。三部分解耦，仅以 openapi 契约为耦合点。
- **不为覆盖率而写测试**。目标是让 2,357 处已有断言真的执行。
- **不再新增任何"看起来规范"的中间层**。这次要删掉的正是这类东西。

## 11. 两个专项：日志管道与测试基建

### 11.1 日志：`internal/platform/log`（有界异步管道）

现状日志是"请求路径里同步写结构体"，会被打爆。目标架构（详见 [07](./07-日志模块治理.md)）：

```
业务 → log.Emit(ctx, Event)      // O(1)，不序列化、不落盘、不网络
     → 有界环形缓冲（条目 + 字节双限额）
     → 单写协程批量（≤500 条 / 1s）
     → ClickHouse 批量直写；失败落 WAL → 后台重放
```

三条硬规则（由 archcheck 强制）：

| 规则 | 说明 |
| --- | --- |
| **字段类型封闭** | `string/int64/uint64/float64/bool/duration/time/[]string`，禁止 `any` |
| **禁止传结构体** | 业务只传 ID 与摘要；`Extra` 只能是 `map[string]string` |
| **单条有上限** | 序列化 ≤32KB；body ≤16KB；栈 ≤8KB |

目录：

```
internal/platform/log/
├── event.go      # Event / Base / Field（类型化）
├── emit.go       # Emitter（有界投递，永不阻塞）
├── writer.go     # 批量写协程
├── sink_clickhouse.go
├── wal.go        # 落盘 + 重放
├── redact.go     # 边界脱敏（白名单 header）
├── sample.go     # 令牌桶限流
└── metrics.go    # 队列/丢弃/延迟
```

### 11.2 测试：`testkit` + 端口化

现状 117 文件 / 2,357 断言，但只有 3 处 `t.Parallel`，且依赖 `Deps`/全局。目标（详见 [06](./06-质量保障与治理.md)）：

```
testkit/
├── clock.go / idgen.go     # 确定性
├── http.go / db.go / redis.go / mysql.go / clickhouse.go
├── fake/                   # 有状态 fake（article/comment/user/outbox/tx）
├── fixture/                # 数据构造器
├── golden.go               # 逐字节基线
└── assert.go               # 领域断言
```

**可测性是架构的属性，不是测试的属性**：只有当 handler 拿不到 `*gorm.DB`、domain 不依赖外部、时间/ID 可注入时，规则才能被穷举测试。这也是为什么"测试重构"必须与"架构重构"同步推进。

### 11.3 依赖注入与测试的关系

| 现状 | 目标 |
| --- | --- |
| `Deps{DB,Redis,...}` → 构造完整结构体才能测 | 构造函数 3-5 个窄接口 → fake 只需实现用到的 1-2 个方法 |
| 规则散在 handler | 规则在 `domain/rule.go`，纯函数，零依赖 |
| 时间/ID 直取 | `Clock`/`IDGen` 端口注入，测试可控 |
| 测试共享全局 | 每测试独立实例，可 `t.Parallel` |
