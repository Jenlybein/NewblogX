# 11 · 契约可用性方案：让前端直接用 `openapi.d.ts`

> 拍板：2026-10-26　**状态：P0 / P1 / P2 / P4 / P5 已交付，P3 取消（理由见 §7）**
> 前置：M7（ADR-007）已让 ID 类型"说真话"，契约流水线已压到 2 步。
> 本文解决的是**下一个谎**：响应形状根本没从代码生成，是人手抄的。

---

## 0. 一句话结论

**契约的响应部分不是"生成的"，是"抄的"**——`119 个 @Success 注解全部手写 `object{...}`，零个引用真实 Go 类型。

这一条解释了目前所有症状。修它，其余问题大半自动消失。

---

## 1. 根因诊断（实测，不是推断）

```bash
# 119 个响应注解，全是手写形状
grep -rhoE "@Success 200 \{object\} object\{" --include=*.go internal/*/adapter/http/ | wc -l
# → 119

# 引用真实 struct 的：0 个
grep -rhoE "@Success 200 \{object\} [a-z]+\." --include=*.go internal/*/adapter/http/ | wc -l
# → 0
```

| 症状 | 根因 |
| --- | --- |
| required 只有 **44 / 636（6.9%）** | 注解里没有 struct，`binding:"required"` 无处生效 |
| 7 个 list 在 TS 里是 `Record<string, never>[]` | 注解写了 `list=[]object{}` |
| 契约表达不了 null（`nullable` 0 处） | 手写形状里没有 null 语法 |
| 改了 Go struct，契约一点不变 | 注解与代码之间**零机械关联** |

**这不是"注解写得不够细"，是"响应契约根本没被生成过"。**

## 2. 技术可行性（三个关键点，已全部实测）

### 2.1 swag v2 会读 `binding:"required"`

`field_parser.go:515` 的 `IsRequired()`：

```go
bindingTag := ps.tag.Get(bindingTag)
for _, val := range strings.Split(bindingTag, ",") {
    switch val {
    case "required":  return true, nil
    case "optional":  return false, nil
    }
}
```

项目里现成有 **68 处** `binding:"...required..."`，只要注解引用到 struct，这些就自动变成契约里的 `required`。

### 2.2 swag v2 支持在注解里写泛型

实测：注解写 `// @Success 200 {object} kernel.Envelope[kernel.ListData[string]]`，生成结果：

```json
"myblogx_internal_kernel.ListData-string":
  {"properties": {"count": {"type":"integer"},
                  "list": {"items":{"type":"string"},"type":"array"}}, "type":"object"}

"myblogx_internal_kernel.Envelope-...-string":
  {"properties": {"code":{"type":"integer"},
                  "data":{"$ref":".../ListData-string"},
                  "msg":{"type":"string"}}, "type":"object"}
```

**嵌套泛型、数组元素类型、`$ref` 全都正确。** 这是列表类接口的解药。

### 2.3 null 只能靠"去掉指针"，不能靠注解

| 尝试 | 结果 |
| --- | --- |
| `extensions:"x-nullable"` | 契约出 `"x-nullable": true`，但 **`openapi-typescript` 忽略它**，仍生成 `string` |
| `swaggertype:"string"` | 本来就是 `string`，无变化 |
| swag 从 `*T` 自动推导 `nullable` | **不支持**（源码里 `Nullable` 字段没有从指针赋值的路径） |

结论：**swag v2 无法输出 `type: ["string","null"]`**。null 问题必须在 Go 侧或前端侧解决。

指针字段实测分布（`internal/*/adapter/http/`）：

| 类别 | 数量 | 处理 |
| --- | --- | --- |
| **请求侧**（`*Request`/`*URI`/`*Payload`） | **49** | **必须保留**——PATCH 语义要区分"没传"和"传了空值" |
| **响应侧**（`*Response`/`*Item`/`*Data`） | **22** | 可改为零值，**只有这 22 个是真正要处理的 null** |

## 3. 方案：五个阶段

### P0 · 泛型响应类型（0.5 天）

在 `internal/kernel` 定义（已验证可用）：

```go
// ListData 是"分页列表"的标准 data 载荷。
type ListData[T any] struct {
	List  []T `json:"list"`
	Count int `json:"count"`
}

// Envelope 是统一响应外壳。
type Envelope[T any] struct {
	Code int    `json:"code"`
	Msg  string `json:"msg"`
	Data T      `json:"data"`
}
```

**为什么不顺手把 `res.OkWithList(list any, ...)` 改成泛型？** 改了也没用——swag 只读注解，不读函数调用处的泛型实参。这一条要在文档里写死，避免后人白干。

### P1 · 响应注解引用真实类型（最大工程，119 处）

把 `@Success 200 {object} object{...}` 改成引用真实 DTO。

按模块排期：

| 模块 | 处数 | 备注 |
| --- | --- | --- |
| article | **30** | `handler_sub.go` 占 22，是最集中的一块 |
| analytics | 14 | 大多是日志/统计数据形状 |
| auth | 13 | |
| notification | 11 | |
| site | 10 | |
| article/media/chat/user | 各 7 | user 另有 `compat.go` 5 处 |
| comment | 6 | |
| social | 4 | |
| ai / search | 3 / 1 | |

**每处都要核对：注解手写的形状 vs 真实 DTO 是否一致。**
不一致的地方**就是既有 bug**——要么注解错（前端照错的写），要么代码错（返回的和注解不符）。这是本阶段真正的价值，也是最容易被跳过的一步。

**验收**：`swagger.json` 里 required 比例 > 60%；schema 数量从 107 上升（因为一批从未进过契约的 DTO 被引入）。

### P2 · 列表泛型化（7 处）

7 个无类型 list，全在 article 模块：

```
/articles/category          /articles/category/options
/articles/favorite          /articles/favorite/contents
/articles/history           /articles/tags
/articles/tags/options
```

改用 `kernel.Envelope[kernel.ListData[XxxItem]]`。

**连带收益**：`api.ts` 的 15 个 `XxxListData` / `XxxListResponse` 包装类型可以直接换成契约类型。

### P3 · 修 null（22 处响应侧指针）

推荐做法：**响应 DTO 去掉指针，用零值表示"没有"**。

```go
// 前：CategoryID *ctype.ID `json:"category_id"`
// 后：CategoryID ctype.ID  `json:"category_id"`
```

理由：M7 已把 `ctype.ID` 变成 string，零值 `""` 本身就是"空 ID"，`IsZero()` 就是判 `""`。不需要再多一个 null 维度。

**两个必须注意的点**：

1. **去掉 `omitempty`**。留着的话 `""` 会被省略，前端拿到 `undefined` 而不是 `""`，等于换了个坑。
2. **前端判断要跟着改**：`x === null` → `!x`。只有 22 处字段，影响面可控。

备选方案（如果不想动后端）：前端在 `contract.ts` 里加补偿，已验证可行：

```ts
type Nullable<T, K extends keyof T> = Omit<T, K> & { [P in K]: T[P] | null };
export type ArticleDetail = Nullable<Schema<"....ArticleDetailResponse">,
  "category_id" | "cover_image_id" | "author_avatar_image_id">;
```

字段名写错、契约删字段都会编译报错（这三点都实测过）。但它只是"把契约的缺陷记在前端"，不如 P3 彻底。

### P4 · `api.ts` 迁移（80 个类型）

| 类别 | 数量 | 处理 |
| --- | --- | --- |
| 已被 `contract-guard` 证明字段名 1:1 | **30** | 直接换 `Schema<"...">`，实测只有 2 处报错 |
| 列表包装 | **15** | 依赖 P2 |
| 纯 UI 形状（`ThemeMode`/`ApiEnvelope`/`OptionItem`/`ChatSocketEnvelope` 等） | **6** | 永远保留 |
| 待逐个确认（列表项、请求体、前端枚举） | **29** | 逐个看能否映射 |

### P5 · 守卫退场

`contract-guard.ts` 的存在意义是"手写类型别漂移"。类型直接来自契约后，这层就多余了。

但 **`contract.ts` 要保留并加强**——因为 P0 的泛型 schema 名字很长：

```
myblogx_internal_kernel.Envelope-myblogx_internal_kernel_ListData-string
```

直接写在业务里没法看。在 `contract.ts` 里加短别名：

```ts
export type ListOf<T> = Schema<`...`>   // 具体写法在 P0 落地时确定
```

## 5. 不做什么

- **不追求 100% required**。请求侧 49 个指针是 PATCH 语义，"可选"就是它的事实。
- **不删 `api.ts` 里的纯 UI 形状**。`ApiEnvelope`、`OptionItem`、`ChatSocketEnvelope` 不对应任何接口，删了没地方放。
- **不给 `res.OkWithList` 加泛型**。swag 读不到，纯属自我感动。
- **不回到"生成后处理脚本"**。M7 刚删掉那个，理由是不想让"契约正确"依赖一个可能忘跑、可能写错的中间层。

---

## 6. 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **P1 是 119 处改动**，且每处要核对形状 | 不一致处会暴露既有 bug，处理它们的时间不可预估 | 按模块推进，每个模块一个 commit，可单独回滚 |
| 泛型 schema 名字丑陋 | `Envelope-myblogx_internal_kernel_ListData-string` | 在 `contract.ts` 里加别名收敛 |
| P3 改响应形状（`null` → `""`） | 前端所有 `=== null` 判断要改 | 22 个字段，逐个查引用点；旧字段先保留一版 |
| swag v2 仍是 rc | 泛型/注解解析可能有未覆盖场景 | P0 先做最小验证；每阶段都跑 `make openapi` + 两端 typecheck |

**建议顺序**：P0 → P2（小、收益立竿见影）→ P1（大、按模块拆）→ P3 → P4 → P5。

先做 P2 而不是 P1，是因为 P2 只有 7 处、能立刻验证泛型方案在真实场景下的表现，而 P1 需要一口气改 119 处。

## 7. 执行结果（2026-10-26，实际落地）

### 7.1 根因诊断被验证

`119` 个 `@Success` 全部手写 `object{...}` 得到确认，且它们分散在 13 个模块
（article 30 / analytics 14 / auth 13 / notification 11 / site 10 / media 7 / chat 7 /
user 12 / comment 6 / social 4 / ai 3 / search 1 / captcha 1）。

### 7.2 计划里有一条因果链是错的

原文说"注解引用 struct 之后，现成的 68 处 `binding:"required"` 会自动变成契约的 required"。
**实测不成立**：

| 事实 | 数据 |
| --- | --- |
| 响应侧字段总数 | 289 |
| 其中带 `binding` 的 | **2** |

那 68 处 `binding:"required"` 全在**请求** DTO 上（请求早就通过 `@Param body` 进契约了）。
**响应 DTO 不做校验，所以没有 required 可读**——Go 的响应 struct 本来就没有
"这个字段一定返回值"的表达方式。

结果：改完之后 required 比例从 6.9% 变成 **6.0%**（分母因新引入 92 个 schema 而变大）。
**required 不是本次的目标，也不该是**——见 7.5。

### 7.3 实际做法：三层前端工具，而不是裸用契约

原计划的 P4 是"把 `api.ts` 的类型换成 `Schema<>`"。实测直接换会得到 **33 个编译错误**，
根因是契约全字段可选 + 嵌套对象也全可选 + null 表达不了。

最终解法是在 `contract.ts` 里加三个工具，**不需要动后端**：

```ts
// ① 响应体：递归去掉 ? 和 | undefined
export type RequiredSchema<K> = DeepRequired<Schema<K>>;
export type DeepRequired<T> = T extends (infer U)[] ? DeepRequired<U>[]
  : T extends object ? { [K in keyof T]-?: DeepRequired<Exclude<T[K], undefined>> }
  : Exclude<T, undefined>;

// ② 后端会返回 null 的字段（swag 不表达 null，只能前端显式声明）
export type Nullable<T, K extends keyof T> = Omit<T, K> & { [P in K]: T[P] | null };

// ③ 后端确实可能不返回的字段
export type OptionalFields<T, K extends keyof T> = Omit<T, K> & { [P in K]?: T[P] };
```

用起来是这样：

```ts
export type ArticleDetail = Nullable<
  RequiredSchema<"internal_article_adapter_http.ArticleDetailResponse">,
  "category_id" | "cover_image_id" | "author_avatar_image_id"
>;
```

**这比原方案好**：字段名和字段类型都来自契约（后端改名/改类型都编译报错），
而"必填"和"可空"这两个契约表达不了的东西，用工具在前端显式补上。
`contract-guard.ts` 因此**可以删掉**——它本来就是为了弥补"类型不与契约挂钩"。

### 7.4 P3（改响应侧指针）取消

原计划把 22 个响应侧指针改成零值来消除 null。但 `Nullable<T, K>` 已经能用**显式声明**
表达同一件事，且：
- 不改 API 行为（`null` 继续是 `null`，不会突然变成 `""`）
- 不需要改前端所有 `=== null` 判断
- 谎言的边界（哪 3 个字段可能是 null）写在类型里，可见、可审计

所以 P3 不做。如果将来后端主动去掉指针，把 `Nullable` 去掉即可。

### 7.5 required 不作为指标

理由：
1. 响应 DTO 没有 required 的语义载体（7.2）
2. 实测影响极小——把最复杂的 `ArticleDetail` 从手写换成契约派生，**只有 2 处报错**
   （而且根因是 null，不是可选性）
3. `RequiredSchema` 已经在消费侧把"必填"表达出来了，契约侧再标一遍是重复

如果将来真需要，正确做法是给响应 DTO 加 `binding:"required"`（借 swag 的读取逻辑），
但那是 289 个字段的人工判断，收益不抵成本。

### 7.6 顺手发现的真实 bug

P1 要求"逐处核对注解形状与真实 DTO"——这一条抓出了一个**产品缺陷**：

`GET /articles/author_info` 的注解写 `data=object{}`（空），实际返回
`{id, username, nickname, avatar}`。而前端 `api.ts` 的 `ArticleAuthorInfo` 期望的是
`{author_id, article_count, article_visited_count, fans_count}`。

**字段名和内容都不一致**，后果是文章页右侧的「文章数 / 访问量 / 粉丝数」**恒显示 0**
（模板里写了 `|| 0`，所以不报错、只是永远是 0）。

后端已按真实返回补了 `ArticleAuthorInfoResponse`（并把 `id` 从 `uint64` 改成 `ctype.ID`，
符合 M7 的 ID 约定）。**但那三个统计值要不要后端补上，是产品决策，未擅自实施。**

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| 手写 `object{...}` 响应注解 | **119** | **0** |
| 契约 schema 数 | 107 | **199** |
| 接口响应解析失败 | — | **0**（123 个接口全部成功） |
| 无类型 list（`Record<string,never>[]`） | 7 | **0** |
| `api.ts` 中从契约派生的类型 | 0 | **30** |
| `contract-guard.ts` | 31 条断言 | **已删除** |
| `api.ts` 行数 | 751 | **约 470** |

### 7.8 仍然手写的部分（有意保留）

- **纯 UI 形状 6 个**：`ThemeMode`、`ApiEnvelope`、`ApiEmptyObject`、`OptionItem`、
  `ChatSocketEnvelope`、`ChatSocketOutgoingMessage` —— 不对应任何接口响应。
- **列表包装 15 个**（`XxxListData` / `XxxListResponse`）：契约里是
  `Envelope-...-ListData-...-Item` 这种超长泛型实例名，直接引用可读性极差。
  它们的 `list` 元素类型其实已经来自契约（P2 之后契约里有具体元素类型了），
  后续可以做成 `ListResponse<Item>` 之类的短别名收掉。
- **29 个待确认类型**：列表项、请求体、前端枚举字面量，需逐个核对。

### 7.9 两个踩过的坑（写给后来人）

1. **注解里引用跨包类型，那个包必须被文件 import**——注解是注释，不会让 import 生效。
   代码里不直接用该包时，要写 `_ "path"` 空白 import，swag 从 import 列表推断包名。
2. **批量替换注解时，pattern 一定要带上行首的 `//`**。我第一次漏了，结果 7 处注解变成
   `// // @Success ...`（被注释掉），swag 静默丢弃、生成 `"responses": {}`。
   更坑的是这会让"泛型不被支持"这种错误结论看起来很可信——**排查前先看一眼实际字节**。

### 7.10 golden 的变化（人工核对结论）

只有 **1 个** golden 变：`author_info.json`

```diff
- {"code":0,"data":{"avatar":"","id":100,"nickname":"作者甲","username":"author_a"},"msg":"成功"}
+ {"code":0,"data":{"id":"100","username":"author_a","nickname":"作者甲","avatar":""},"msg":"成功"}
```

两处差异，都在预期内：
1. `"id":100` → `"id":"100"` —— M7 的 ID 约定（ID 一律字符串），之前这里用
   `profile.ID.Uint64()` 绕过了约定，是漏网。
2. 字段顺序变成结构体声明顺序 —— 之前用 `map[string]any`，顺序不可控；改成 struct 后稳定。
   JSON 语义不受影响，但 golden 是逐字节比对，所以要重新生成。

其余 31 个 golden 文件逐字节未变。

## 8. 第二轮收敛（2026-10-26 晚）：api.ts 从 463 行 → 436 行，并修掉 9 处契约谎言

### 8.1 目标修正：不是"删掉 api.ts"，而是"它不再镜像 HTTP 接口"

先回答了一个问题：**能彻底不用 api.ts 吗？不能。** 有两类东西契约里永远不会有：

| 类别 | 数量 | 为什么必须留 |
| --- | --- | --- |
| 纯 UI 形状（`ApiEnvelope`/`OptionItem`/`ChatSocketEnvelope`/`ThemeMode`/`ApiEmptyObject`/`ChatSocketOutgoingMessage`） | 6 | 不对应任何 HTTP 接口 |
| 前端枚举字面量（`AiDiagnoseSeverity`/`AiArticleScoreLevel` 等） | 6 | 后端是 `string`，窄枚举是前端自己的需求 |
| 契约里**内联**、没有独立 schema 名的嵌套对象（`AiDiagnoseIssue`/`SearchTag`/`ArticleTopItem` 等） | ~12 | swag 不给内联对象起名，没有可引用的 key |

所以判据改成：**api.ts 里每个类型都要能回答"为什么契约里没有它"**。

### 8.2 这一轮实际做的

迁移 11 个类型到契约派生（调用方零改动，类型仍然同名）：

| 类型 | 指向 |
| --- | --- |
| `FavoriteFolderListData` | `kernel.ListData[FavoriteListItem]` |
| `CommentManageListData` | `kernel.ListData[comment_app.ManageItem]` |
| `CommentReplyListData` | `comment_http.ReplyListResponse`（新定义，见 8.3） |
| `FollowUserListData` / `FanUserListData` | `kernel.HasMoreListData[social_domain.*]` |
| `UserSessionListData` | `kernel.ListData[auth_http.SessionItem]` |
| `SiteMessageListData` / `GlobalNoticeListData` | `kernel.HasMoreListData[notification_http.*]` |
| `ChatSessionListData` / `ChatMessageListData` | `kernel.ListData[chat_domain.*]` |
| `ChatWsTicketData` | `chat_http.WsTicketResponse`（新定义，见 8.3） |

结果：**契约派生 31 → 42，api.ts 463 → 436 行**。

### 8.3 修掉 9 处"契约在撒谎"（第一轮批量迁移的遗留）

第一轮我用正则批量替换注解，**没有核对 handler 实际调用的是 `OkWithList` 还是 `OkWithHasMoreList`**，导致契约说 `{list,count}` 而实际返回 `{list,has_more}`。逐个修：

| 接口 | 之前（错） | 现在（对） |
| --- | --- | --- |
| `/articles/history` | `ListData`（count） | `HasMoreListData`（has_more） |
| `/articles/favorite/contents` | `ListData`（count） | `HasMoreListData`（has_more） |
| `/comments/replies` | `EmptyData`（空） | 新定义 `ReplyListResponse{root_id, reply_count, list, has_more}` |
| `/chat/ws-ticket` | `EmptyData`（空） | 新定义 `WsTicketResponse{ticket}` |
| `/site/{name}`、`/site/admin/{name}` | `EmptyData`（空） | `SiteConfigData`（具名 `map[string]any`）|

**为什么要紧**：前端读 `has_more` 会永远拿到 `undefined`（当 false 用），读 `root_id` 永远是 `undefined`。
这些是"契约写错 → 前端照着错的类型写 → 运行时静默失效"的典型，而且**编译器一个字都不会提示**。

### 8.4 两个新踩的坑

1. **swag 注解里不能写 `map[string]any`**。它会报
   `cannot find type definition: map[string]any`，然后**静默跳过整份契约的写入**
   （exit code 仍是 0，文件时间戳不变）。必须用具名类型（本项目加了 `kernel.SiteConfigData`）。
   → **验证生成是否成功，不能只看 exit code，要看文件时间或 grep 新内容。**

2. **写检测脚本时，子串判断要互斥**。我第一版用 `'ListData' in line` 判断，
   结果 `HasMoreListData` 也被算成 `ListData`，报出 13 处误报中的 5 处。
   正确写法：`'HasMoreListData' in line` 优先，再判断 `'ListData' in line and not says_more`。
   → **检测脚本本身也需要被验证**，否则会在错误的方向上"修 bug"。

### 9.4 一个新踩的坑：`omitempty` 指针字段是"缺席"，不是 `null`

`BaseInfoResponse.AvatarImageID` 是 `*ctype.ID` 且 tag 带 `omitempty`：

- 空值时**整个字段不出现在 JSON 里**
- 而 `RequiredSchema`（`DeepRequired`）强制它存在

后果是：任何构造该类型对象字面量的地方（比如加载失败时的兜底对象）**都编译不过**，
因为它被迫编造一个 `avatar_image_id`。正确做法是把它 `OptionalFields` 放回可选。

**这条要记住**：`RequiredSchema` 适用于"响应总是带全字段"的 schema；
一旦字段是 `omitempty` 指针，就必须显式标可选。它与 `Nullable` 是两个不同的问题：

| Go 写法 | JSON 里 | TS 应该 |
| --- | --- | --- |
| `T` | 一定有值 | `T`（`RequiredSchema` 即可） |
| `*T` | `null` 或值 | `T \| null`（用 `Nullable<T,K>`） |
| `*T` + `omitempty` | **可能整个不存在** | `T \| undefined`（用 `OptionalFields<T,K>`） |
