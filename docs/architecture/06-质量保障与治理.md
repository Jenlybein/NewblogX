# 06 · 测试体系重构与质量保障

> 本项目不缺测试数量（117 文件 / 2,357 断言），缺的是**让测试跑起来、跑得快、跑得准**。
> 本文给出彻底重做测试体系的方案：分层、隔离、确定性、契约、门禁。
> 日志模块的专项治理见 [07](./07-日志模块治理.md)。

---

## 1. 现状诊断

### 1.1 数量不缺，结构错位

| 指标 | 数值 | 问题 |
| --- | --- | --- |
| Go 测试文件 | 117 | 数量不少 |
| 断言 | 2,357 | 数量不少 |
| `t.Parallel()` | **3** | 几乎没有并行能力 |
| 依赖 `testutil.InitGlobals` / 全局变量的测试 | 绝大多数 | **无法并行、无法隔离** |
| `repository/` 核心 SQL | 449 行 **0 测试** | 数据层裸奔 |
| `frontend_admin` | **0 测试、无 test 脚本** | 后台完全无保障 |
| 前端组件覆盖 | 6/29 组件、0/15 页面 | 大量逻辑未测 |
| CI | **不存在** | 2,357 个断言从不自动执行 |
| `go test -race` | 从未在 CI 跑 | 并发缺陷不可见 |
| 集成测试 | 用 SQLite 模拟 MySQL | **假安全**：`ON CONFLICT`、`clause.Locking`、`JSON` 函数行为不同 |

### 1.2 最典型的一条：测试守的是"代码"，不是"规则"

`article_test.go` 里有一条测试专门构造了 `ArticleListRequest{Type: 1}`（此时 `Status==0`，正是匿名读草稿的触发条件），
但断言的是「`validateRequest` 不返回 error」——**它验证了实现按预期跑，却没验证业务规则没被破坏**。

> 结论：**测试要断言"结果符合规则"，而不是"函数返回了预期类型"。**

### 1.3 为什么现在写不出"对的测试"

因为业务规则不在可测试的位置：

- 规则散在 handler 的 `if` 里，要测就得起 HTTP + 真 DB
- 实体是 GORM `models.ArticleModel`，既是 DB 模型又是响应体，构造它要连库
- 依赖是 `Deps`（含 `*gorm.DB`），fake 不掉
- 时间/ID 直接 `time.Now()` / 雪花，结果不可复现

**测试体系重构的前提，是架构重构（domain/app/adapter + 端口注入）。两者必须一起做。**

## 2. 目标：测试金字塔 + 三条铁律

```
        ▲  E2E（黑盒 HTTP，少量）
       ╱ ╲       ~10%   登录→发文→搜索→评论 主链路
      ╱───╲  集成（app + 真 MySQL，中等）
     ╱     ╲     ~20%   事务、仓储 SQL、CDC、ClickHouse 写入
    ╱───────╲ 单元（domain + 纯逻辑，大量）
   ╱_________╲   ~70%   规则、值对象、脱敏、截断、采样
```

### 三条铁律

1. **规则测试必须零依赖**：domain 层测试不连 DB、不起 HTTP、不读环境变量，`go test` 毫秒级完成。
2. **一个测试只断言一件事**：不写"顺便也测了"；失败时能一眼看出哪条规则破了。
3. **测试不写全局状态**：没有 `InitGlobals`，没有包级变量覆盖；所有依赖从参数注入，测试可并行。

### 3.1 有状态 fake 优于 gomock

gomock 只能验"调了哪个方法、传了什么参数"，无法模拟**状态与故障**。本项目最需要测的恰恰是状态：

```go
// testkit/fake/article_repo.go
type ArticleRepo struct {
    mu       sync.Mutex
    byID     map[uint64]*article.Article
    failOn   map[string]error // "Save" -> ErrConflict
    calls    int
}

func (r *ArticleRepo) Save(ctx context.Context, a *article.Article) error {
    r.mu.Lock(); defer r.mu.Unlock()
    if err := r.failOn["Save"]; err != nil { return err }
    if _, ok := r.byID[a.ID]; ok { return article.ErrConflict } // 模拟唯一键
    r.byID[a.ID] = a.Clone()
    return nil
}
```

用途：
- 测"重复创建返回冲突"
- 测"事务回滚后仓储无副作用"
- 测"Outbox 发布失败时业务回滚"
- 测"第二次读能读到第一次写"（状态一致性）

### 3.2 确定性：时间、ID、随机

```go
type Service struct {
    clock  Clock   // 生产：RealClock；测试：FakeClock
    ids    IDGen   // 生产：ULID；测试：SeqID
}
```

- domain 层**禁止**直接调 `time.Now()` / `rand` / 雪花（archcheck 规则）。
- golden 测试用 `SeqID` 产生稳定 ID，输出可逐字节比对。
- 时间相关规则（草稿过期、登录会话 TTL）用 `FakeClock.Advance` 精确验证。

#### 3.2.1 golden 的口径：写死种子，不做归一化

**决策（2026-10-24，M4 起适用）**：golden 的稳定性靠**写死数据**，不靠"比对前把不稳定字段抹掉"。

- 种子 SQL 里显式写死 ID、`created_at`/`updated_at`、各类计数（M4：20 篇文章 × 6 张关联表），
  并在种子内 `SET time_zone='+08:00'`，避免换机器时区不同导致红。
- 断言**逐字节比对**，不替换 `<id>` / `<ts>` 占位符。
- 理由：golden 的价值不是"结构对不对"（那是契约测试的活），而是"同一个请求，重构前后输出是否一字不差"。
  一旦把 ID 和时间抹掉，就永远发现不了 `123` 变成 `"123"`、`+08:00` 变成 `Z` 这类**线上会炸、测试却绿**的错。
- 代价与对策：种子 SQL 是一次性成本（可脚本从现有数据导出）；业务加必填字段时要同步补种子，
  由契约测试（结构体 JSON 键 ⊆ 表列）和编译期字段检查共同兜底。

### 3.3 并行与隔离

- 所有测试默认 `t.Parallel()`。
- **不共享可变状态**：每个测试 `newArticleApp(t)` 构造独立 Service + fake。
- 集成测试（真 MySQL）用**每测试独立 schema**（`test_<random>`）或事务回滚；禁止共享一个库。
- `t.Cleanup` 负责关闭容器/连接/临时目录。

```go
func TestArticleCreate_Conflict(t *testing.T) {
    t.Parallel()
    repo := fake.NewArticleRepo()
    svc := articleapp.New(repo, fake.NewTx(), fake.NewOutbox(), testkit.NewFakeClock(), testkit.NewSeqID())
    // ...
}
```

## 4. 测试分层：测什么、在哪测

| 层 | 位置 | 依赖 | 数量 | 断言重点 |
| --- | --- | --- | --- | --- |
| **domain 单测** | `internal/<mod>/domain/*_test.go` | 无 | 最多 | 规则、值对象、不变量矩阵 |
| **app 用例测** | `internal/<mod>/app/*_test.go` | fake 端口 | 多 | 编排、事务边界、事件发布 |
| **adapter 契约测** | `internal/<mod>/adapter/*_test.go` | 真 MySQL（integration） | 中 | SQL 正确性、mapper、分页 |
| **HTTP 契约测** | `internal/<mod>/adapter/http_test.go` | httptest + fake app | 中 | 状态码、DTO、鉴权 |
| **E2E** | `test/e2e/` | 真栈（compose） | 少 | 主链路 |
| **前端单测** | `frontend/**/*.spec.ts` | vitest | 多 | 组件、composable、service |
| **前端 E2E** | `frontend/e2e/` | Playwright | 少 | 关键页面流 |

### 4.1 不变量测试（domain 的核心）

```go
func TestArticleVisibility(t *testing.T) {
    cases := []struct {
        name   string
        status article.Status
        viewer article.Viewer
        want   bool
    }{
        {"draft/author", article.Draft, author, true},
        {"draft/stranger", article.Draft, stranger, false},
        {"draft/admin", article.Draft, admin, true},
        {"draft/anonymous", article.Draft, anonymous, false},
        {"published/anonymous", article.Published, anonymous, true},
        {"rejected/stranger", article.Rejected, stranger, false},
        // ... 状态 × 角色 全组合，穷举而不是只测 happy path
    }
    for _, c := range cases {
        c := c
        t.Run(c.name, func(t *testing.T) {
            t.Parallel()
            if got := article.CanBeViewedBy(c.status, c.viewer); got != c.want {
                t.Fatalf("got %v want %v", got, c.want)
            }
        })
    }
}
```

**这类测试在现状结构下写不出来**——规则不在 domain，而在散落的 handler 条件里。这正是重构的直接动因。

### 4.2 契约测试（前后端一致性）

```go
// 用 swag 生成的 openapi.json 校验响应 schema
func TestArticleListResponseMatchesContract(t *testing.T) {
    resp := callList()
    require.NoError(t, contract.Validate("/api/articles", "get", 200, resp.Body))
}
```

- 契约来源：`backend/openapi.json`（swag 生成）。
- 前端不写 mock 类型，用 `openapi-typescript` 生成的 `api.gen.ts`。
- 后端改字段、前端 `tsc` 立刻失败；契约测试再兜一层运行时。

### 4.3 Golden file

- 对 **20 个真实文章 ID × 12 个接口** 录响应基线，逐字节比对。
- prompt / 日志序列化 / 搜索排序等"输出易漂移"的地方必须 golden。
- `UPDATE_GOLDEN=1 go test` 才允许更新，且 diff 必须人工 review。

### 4.4 日志管线测试（配合 07）

| 测什么 | 怎么测 |
| --- | --- |
| 丢弃策略 | `Emitter` 注入容量 1，灌 100 条，断言 `dropped_total==99` |
| 审计不丢 | Writer 注入"ClickHouse 失败"，断言全部落 WAL；恢复后重放条数一致 |
| 脱敏 | 表驱动：`password/token/cookie` 一律 `***`；body 限量 1MB、输出 ≤16KB；header 不采集 |
| 截断 | 20KB body → 输出 ≤16KB 且 `truncated=true` |
| 采样 | 令牌桶 100/s，灌 1000 条，断言保留量在 [90,110] |
| 序列化 | golden：给定事件 → 固定 JSON 行 |

## 6. CI：让失败成为可能

### 6.1 三档流水线

```yaml
# .github/workflows/ci.yml
jobs:
  fast:            # 每次 push，<2min
    - go vet ./...
    - go build ./...
    - go test -race -short ./internal/...
    - go run ./tools/archcheck --warn
    - (frontend) pnpm lint && pnpm typecheck
    - (frontend_admin) pnpm lint && pnpm typecheck

  full:            # PR，<10min
    needs: fast
    - go test -race ./...
    - (frontend) pnpm test && pnpm build
    - (frontend_admin) pnpm test && pnpm build
    - go run ./tools/archcheck --error --changed-since=origin/main

  nightly:
    - //go:build integration：testcontainers MySQL/ClickHouse/Redis
    - E2E（compose 起全栈）
    - 覆盖率报告 + 分层阈值
    - mutation testing（domain 关键规则）
    - pnpm audit
```

### 6.2 门禁自检（防止 CI 空转）

```yaml
sanity:
  - 注入一个必然失败的测试（`t.Fatal("canary")`），断言 CI 失败
  - 注入一个类型错误，断言 typecheck 失败
  - 若上述"没有失败"，则 CI 本身失效，直接 fail
```

> 这条 5 行自检，是防止 CI 变成下一个"永真守卫"的关键。本项目已经踩过"守卫永真"的坑。

### 6.3 分层覆盖率（不设整体数字）

| 层 | 目标 |
| --- | --- |
| `*/domain/` | ≥ 90% |
| `*/app/` | ≥ 85% |
| `*/adapter/`（契约测） | 每个方法至少 1 条 |
| `internal/platform/log` | ≥ 90%（纯逻辑） |
| 整体 | **不设**（避免垃圾测试） |

## 7. 变异测试：验证"测试是否真的在测"

对 domain 的关键规则（可见性、状态机、收藏计数）跑 mutation：
- 工具：`go-mutesting` 或 `greece`。
- 目标 mutation score ≥ 70%。
- 只在 nightly 跑，避免拖慢 PR。
- 若"删掉某行规则测试仍全绿"，说明测试没守住规则——这正是现状 `article_test.go` 的病。

## 8. Flaky 治理

| 来源 | 对策 |
| --- | --- |
| 时间 | 注入 `Clock`，禁 `time.Now()` |
| 随机 | 注入 `IDGen`，固定种子 |
| 端口/网络 | 用 `httptest` / 随机端口，禁用固定 8080 |
| 全局状态 | 测试不写包级变量；每测试独立实例 |
| 容器启动慢 | 集成测试单独 tag + 更长超时，不进 fast 档 |
| 顺序依赖 | 强制 `t.Parallel()` + 独立数据，禁止共享 fixture 可变状态 |

被标记 flaky 的测试：**隔离到 quarantine job**，限时修复，不允许长期 `retry` 掩盖。

## 13. 一句话总结

> 现状不是"没测试"，是**测试写在了错的位置、依赖了错的东西、从来没有被执行**。
> 重构的目标：**规则在 domain 被穷举、用例在 app 被 fake、SQL 在 adapter 被真库验证、契约在 CI 被一致性校验、所有测试都能并行且确定。**
