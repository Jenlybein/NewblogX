# ADR-0015：轮播取景存参数（焦点 + 缩放）、由 CSS 渲染，不存裁好的图、不做服务端裁切

- 状态：已交付
- 日期：2026-10-31
- 来源：2026-10-31 的取景 spec（[issue #44](https://github.com/Jenlybein/NewblogX/issues/44)），术语落点见 [GLOSSARY · 取景](../../GLOSSARY.md)。上游决策为 [ADR-0013](./0013-editorial-hero-cover.md)（首屏轮播并入编辑部式封面）与 [ADR-0012](./0012-neutral-glass-visual-system.md)（全站视觉立场）

## 背景与问题

首屏轮播面板此前没有锁定比例，运营上传的图什么样就渲染成什么样：同一张图在不同屏宽下被 `cover` 裁得不一样，竖图与超宽图则被裁得莫名其妙。运营侧更直接——后台只能选文件、传上去、填跳转链接，**无法决定这张图露出哪一块**；想让人脸别被切在边上，只能重做一张图再传。

于是有两个必须一次定下来的问题：

1. 取景的结果**以什么形式保存**——是文件，还是几个数？
2. 取景**在哪一层生效**——存储侧、服务端，还是读者端的排版层？

这两问看起来是"实现细节"，实际是硬约束：一旦选了存图或服务端裁切，取景就变成不可逆的破坏性动作，且把版式绑死到存储厂商；日后想改回来要迁移历史数据。属于"难反悔、后人会问为什么、且真的有三条路"的决策。

## 决策

1. **取景存参数，不存第二份图**：焦点（`focus_x` / `focus_y`，0–1 的相对坐标）加缩放（1–2 的倍数），三个数记在轮播封面上，原图只有一份。没有取景记录的图按「居中、缩放 1.0」处理，渲染结果与引入取景前一致。
2. **渲染在 CSS，服务端不裁切**：`object-fit: cover` 打底 + `transform-origin` 取焦点 + `transform: scale(zoom)`，由**一个纯函数**从取景参数算出样式对象，组件只消费它。后台取景窗的预览走同一份换算，所以"预览即最终效果"。
3. **容器比例固定，不随屏宽变化**：比例是设计常量（当前 16:9），写死在两端并由跨端静态断言锁住；不进运行时配置——一旦可调，历史图的裁切会随配置漂移。
4. **取景参数在契约里是可选字段**：不传即居中，老调用方无需改动；越界（焦点出 0–1、缩放出 1–2）由后端拒绝，不做"悄悄 clamp"。

## 理由与已否决方案

核心判断是：**取景是排版问题，不是图片处理问题**。它要回答的只是"在这个固定比例的框里露出原图的哪一块"，因此它应该由排版层（CSS）在渲染时算出来，而不是提前把像素烧进第二个文件。

三条路的比较：

- **存裁好的图**（上传时裁一张 16:9 的派生图，线上只发派生图）：最省前端、最省流量，但代价是取景变成一次性动作——改构图要重裁、重传，旧派生图变孤儿；面板比例若调整（换断点、换版式），所有历史派生图全部作废且无法回退；同一张图在"桌面 16:9 / 其他用途 4:3"下需要 N 份文件。原图与派生图之间还会出现"哪份是真相"的长期歧义。**否决**。
- **服务端裁切**（服务端裁，或用对象存储厂商的图片样式参数按需出图）：看起来折中，实际把渲染逻辑绑死到存储厂商——换存储、换域名、本地与测试环境都要复刻同一套变体规则；带参数的 URL 会让缓存键爆炸，取景调整后旧缓存还要逐条失效；而且它解决的仍是"提前生成一份图"，只是把生成挪到了请求时刻。**否决**，spec 里也把它与厂商样式参数一并列为 Out of Scope。
- **存参数 + CSS 渲染**（选中）：唯一真相是三个数，改取景只是改三个数——可逆、可回退、可批量；原图永远不动，运营不会因为"取景"而丢素材；跨端（读者站渲染、后台取景窗预览、后台列表缩略）共用同一份换算口径，不会出现"预览和线上不一致"；比例由容器决定，天然响应式。

同时被否掉的近似方案：

- **只存 `object-position` 百分比、不存缩放**：只能平移不能放大，远景图裁不出可用的特写；而"放大一档"正是运营最常提的诉求。
- **把比例做成运行时配置**（运营可调面板比例）：会让历史图的裁切随配置漂移，等于把设计决策外包给了一个下拉框。
- **在前端存"取景后的 dataURL"再上传**：其实就是"存裁好的图"的另一种写法，同样不可逆，还多绕一次上传。

## 代价 / 不做什么

- **读者下载的是原图**：没有按取景裁好的小图，首屏首字节体积更大。缓解靠上传侧的大小与 MIME 约束、容器尺寸与加载占位，而不是靠"存一份裁好的图"把问题提前解决。这是本决策明码标价的成本。
- **渲染正确性由前端承担**：焦点钳制没做好会在面板边角露底；缩放与首屏视差都动 `transform`，必须分属不同层，否则互相覆盖。缓解是把它压成纯函数 + 单测，不让组件自己算几何。
- **取景窗要自绘**：不引 cropperjs / fabric / sharp / jimp 一类图像库，交互（拖动、缩放、键盘微调、遮罩）自己实现并自己测。
- **多一条一对一记录**：取景参数不往既有表加列（本项目零 DDL 约束），因此多一张表、多一次读写；缺行即缺省，读路径要能容忍它不存在。
- **不做什么**：不做服务端裁切与厂商图片样式参数；不存"裁剪后的第二份文件"；不做人脸识别 / 主体检测 / AI 自动取景；不做按屏宽下发不同取景；不做旋转、镜像、滤镜；不做移动端专用比例；不做历史图的批量重裁。

## 当前生效约束

1. 取景只有一份真相：焦点两个相对坐标（0–1）+ 缩放倍数（1–2）；原图不得因取景被改写、替换或删除。
2. 禁止在服务端或存储侧裁切取景（含对象存储厂商的图片样式参数）；取景必须在 CSS 渲染层复现。
3. 轮播面板比例固定，所有断点同一比例；比例是设计常量，不进运行时配置，跨端由静态断言锁住一致。
4. 参数缺省即「居中、缩放 1.0」；没有取景记录的图，渲染结果与引入取景前一致。
5. 参数越界（焦点出 0–1、缩放出 1–2）由后端直接拒绝，不得静默 clamp 成合法值。
6. 缩放与视差必须分属不同层，任何一个都不得覆盖另一个的 `transform`。
7. 不引入图像处理或裁剪组件库；取景窗自绘，几何换算抽成纯函数并单测。
8. 取消取景＝中止本次上传：不产生图片、不产生轮播。

- 2026-10-31（#48）：**更新接口不传取景＝保留既有取景**，不是回到缺省。决策 4 的"不传即居中"只适用于创建请求、老客户端与"没有取景记录的历史图"；`PUT /banners/:id` 的 `crop` 为可选，缺省表示该字段不更新。这样老后台改一个跳转链接不会把运营已经取好的景抹掉。

- 2026-11-02（#118）：**取景表的形态变了，本 ADR 的结论一条不改**。旧的轮播专属取景表 `banner_crop_models` 并入通用取景表 `picture_crop_models`（键 `target_type` / `target_id`，覆盖轮播封面、文章封面与合集封面），见 [ADR-0020](./0020-zero-ddl-exception-and-generic-framing-table.md)。决策 1–4 与当前生效约束 1–8 **原样继续生效**：取景仍是"焦点两坐标 + 缩放"三个数、仍在 CSS 渲染、比例仍是设计常量、越界仍由后端拒绝；取景三列的名称、类型与语义不变。改动只有两处口径：① 表名改以"通用取景表"为准，`banner_crop_models` 属历史命名；② 代价段第 4 条里"本项目零 DDL 约束"的准确表述以 ADR-0020 为准——**零列变更 + 允许新增表**，通用取景表是首个登记例外（例外只到新建表，既有表列变更仍一律禁止）。契约字段 `crop` 与错误码 `banner.crop_invalid` 照旧不动。
