# ADR-004：架构守卫从符号匹配改为可执行的 AST 规则

## Status

**Proposed**（2026-10-24）

## Context

项目有一套架构守卫，但它是**永真的**。

### 现状

| 实现 | 位置 | 规模 |
| --- | --- | --- |
| PowerShell 脚本 | `scripts/arch_guard.ps1` | 110 行 / 9 条规则 |
| Go 测试 | `apps/api/test/architecture/{di_guard,no_global_refs}_test.go` | 260 行 / 6 个测试 |

两者检查同一批规则，重复维护。

### 它们检查的符号全都不存在

```bash
appctx:        0 处引用
global:        0 处引用
MustFromGin:   0 处引用
DepsFromGin:   0 处引用
mustApp:       0 处引用
```

对应目录也不存在（`ls apps/api/global` → No such file or directory）。

**13 条规则 + 6 个测试，全部永真通过。**

### 而真正的问题无人看守

| 问题 | 规模 | 有规则覆盖吗 |
| --- | --- | --- |
| 32 个 `Deps` 结构体（30 个含 `*gorm.DB`） | 32 | ❌ |
| handler 直接查库 | 61 文件 / 194 处 | ❌ |
| `article_sync.go` 1,547 行 | 1 | ❌ |
| 65 个 `enter.go` | 1,327 行 | ❌ |
| 12 个 handler 内手写事务 | 12 | ❌ |

### 唯一"有效"的规则也被绕过

规则「`api` 禁止 import `repository`」是唯一能真正阻断越层的。但：

```go
// service/top_service/query.go:1-8
type QueryService = repo.QueryService
var NewQueryService = repo.NewQueryService
```

四处纯别名 re-export 后，`api` 照样能用：

```go
// api/comment_api/comment_list_man.go:45
comment_service.NewQueryService(h.App.DB, ...)   // 实际就是 repo.NewQueryService
```

守卫看不到 `repository` 字面量，规则通过。

### 其他脆弱点

- `Assert-NoMatch` 用 `Select-String -Quiet` → **只给文件名，不给行号**
- 排除所有 `_test.go` → 测试代码不受约束
- `\*conf\.Config\)` 只匹配紧邻右括号 → `f(cfg *conf.Config, x int)` 漏掉
- 纯 PowerShell → **Linux / CI 无法运行**
- 无 CI、无 git hook → **从不自动执行**

## 备选方案

### A. 修补 PowerShell 脚本

加规则、加行号输出。

- 优点：改动小
- 缺点：
  - 本质仍是**正则匹配符号名**，别名、类型推导都绕得过
  - PowerShell 在 Linux CI 上跑不了（除非装 pwsh，仍慢且不稳）
  - 与 `test/architecture/` 依然重复
- 判断：**在错误的载体上做优化**

### B. 只用 Go 测试（`test/architecture/`）

把规则都写成 `go test`，删掉 ps1。

- 优点：跨平台、能进 CI、有行号（`t.Fatalf` 可带）
- 缺点：
  - 仍是**读文件做字符串匹配**（现状实现就是 `regexp.MatchString`）
  - 别名绕过的问题依然存在
  - 无法判断类型（`*gorm.DB` 出现在哪一层需要类型信息）
- 判断：**载体对了，方法还错**

### C. AST + 类型信息（推荐）

用 `golang.org/x/tools/go/packages` 加载完整类型信息，基于 **import 图 + 类型签名** 判断。

- 优点：
  - 别名绕不过（类型就是 `*gorm.DB`，不管叫什么）
  - 能判断"哪一层"
  - 能给精确的 `文件:行号`
  - 跨平台，一条 `go run` 或 `go test`
  - 可做**规则自检**（对人造违规必须报错）
- 缺点：
  - 首次加载类型信息较慢（约 2-5s，可缓存）
  - 需要写约 400 行工具代码

### D. 引入 golangci-lint 的 depguard / forbidigo

- 优点：现成工具，无需自研
- 缺点：
  - `depguard` 只能约束 import 路径，不能约束"结构体字段类型"
  - `forbidigo` 是正则匹配，回到方案 A 的问题
  - 无法表达"单文件 ≤800 行"
- 判断：**能覆盖 30%，剩下 70% 还得自研**

## Decision

**采用方案 C，并删除 A 与 B 两套实现。**

### 目录

```
tools/archcheck/
├── main.go        # CLI：--all / --changed-since / --warn / --error / --report
├── load.go        # packages.Load 加载类型信息
├── rules.go       # 规则定义
├── rules_test.go  # ★ 规则自检（核心）
└── report.go      # 输出 file:line
```

### 首批 8 条规则

| # | 规则 | 判定方式 | 现状应报 |
| --- | --- | --- | --- |
| R1 | 导出结构体不得含 `*gorm.DB` | 类型检查 | **32** |
| R2 | `adapter`/`platform/mysql` 之外不得出现 `*gorm.DB` | 类型检查 | **61 文件** |
| R3 | 禁止 `type Deps struct` | 类型检查 | 32 |
| R4 | `domain` 不得 import gin/gorm/redis/es | import 图 | 迁移中 |
| R5 | 模块之间不得互相 import | import 图 | 迁移中 |
| R6 | 单文件 ≤ 800 行 | 行数 | **4** |
| R7 | `enter.go` ≤ 50 行 | 行数 | **65** |
| R8 | `adapter` 之外不得调用 `Begin`/`Commit` | 调用图 | **12** |

### 双轨：`--warn` 与 `--error`

存量有 150+ 处违规，一次性阻断会让所有人无法提交。

```
--all --warn                  → 输出债务基线，不阻断
--changed-since=origin/main --error   → 只拦新增
逐模块清零后，该模块转全量 --error
```

### 规则自检（防止再演一遍）

```go
func TestEveryRuleDetectsViolation(t *testing.T) {
    for _, r := range rules {
        if got := r.Check(violationFixture(r)); len(got) == 0 {
            t.Fatalf("规则 %s 无法检测人造违规 —— 规则失效", r.Name)
        }
    }
}

func TestEveryRulePassesCleanCode(t *testing.T) {
    for _, r := range rules {
        if got := r.Check(cleanFixture()); len(got) > 0 {
            t.Fatalf("规则 %s 误报", r.Name)
        }
    }
}
```

**这两条测试是整个方案的地基**：没有它们，规则随时会退化成永真——本项目已经踩过这个坑。

## Consequences

### 变好的

- **别名绕过失效**：类型检查看的是实际类型，不是字面量
- **能进 CI**：跨平台 `go run`，Linux 上可用
- **有行号**：可定位、可修
- **双份维护消除**：删掉 ps1（110 行）+ test/architecture（260 行），只留一份
- **规则可自检**：有 `rules_test.go` 兜底

### 变差的

- **首次写约 400 行工具代码**（S1 的主要工作量）
- **`packages.Load` 有启动开销**（2-5s，可缓存）
- **存量违规 150+ 处**，清理需要跨多个阶段
- **规则会误报**（如第三方库的类型），需要 `//nolint:archcheck` 逃生口

### 需要跟进的

- 必须提供 `//nolint:archcheck R2` 逃生口，否则个别合理例外会挡住整个 CI
- 规则数量控制在 8-12 条；每加一条都要问"它会误伤什么"
- R6/R7 的行数阈值需要根据实际情况调整（800/50 是初值）

## 验证

```bash
# 1. 规则自检通过
go test ./tools/archcheck/... -v

# 2. 能报出真实存量违规（关键！）
go run ./tools/archcheck --all --warn | grep -c "R1\|R2\|R3"    # 期望 >= 100

# 3. 别名绕过不再有效（构造一个 type X = repo.X，期望 R2/R5 报错）
cat > /tmp/alias_test.go <<'EOF'
package foo
import repo "myblogx/repository/comment_repo"
type Q = repo.QueryService
var _ *gorm.DB
EOF
go run ./tools/archcheck --path=/tmp/alias_test.go --warn   # 期望命中

# 4. 输出含行号
go run ./tools/archcheck --all --warn | head -1 | grep -E "\.go:[0-9]+"

# 5. 进 CI
grep -q "archcheck" .github/workflows/ci.yml
```
