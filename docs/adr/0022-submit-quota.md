# ADR-0022：投稿配额按自然日计数、按提交动作计量

- 状态：已交付
- 日期：2026-11-08
- 来源：parent spec [#302](https://github.com/Jenlybein/NewblogX/issues/302)（发布治理一期）· 落地票 [#304](https://github.com/Jenlybein/NewblogX/issues/304)（每日投稿配额）· 来自 2026-11-07 的发布治理设计评审 §2.3

## 背景与问题

站点此前**没有任何文章侧配额**：私信有按对限流（`site.chat.rate_daily_max`）、AI 有 `daily_quota`，文章提交却没有上限。任何账号都可以无限次提交，而每次提交在闸门落地后都要真实付一次模型调用的成本。

要防的灌水形态很具体：**反复「提交 → 被打回 → 改两个字 → 再提交」**。这条路径不需要写出好文章，只要一直重投就能一直触发评分、一直占审核队列。

因此有三件事必须一起定义清楚，否则"15 篇/日"只是个愿望：

1. **数什么**——提交动作，还是发布成功的文章？
2. **谁受限**——管理员要不要豁免、要不要按信任等级分档？
3. **计数放哪**——新建一张账本表、Redis 日桶，还是数审核任务行？

## 决策

1. **计量单位是提交动作**，不是"发布成功的文章"。被驳回的提交**照常计数**——提交这件事已经真实发生（一次模型调用、一条审核任务）。只有"没有发生提交动作"的等价操作才记 0：存草稿、退回草稿、"已发布 + 站点跳过审核"的幂等提交。
2. **边界必须闭合**：编辑一篇已发布/审核中的文章所触发的**自动重新送审**同样记 1 次。它和显式重投产生同样的副作用，不计就等于留下一条"反复保存即可无限重审"的绕过路径。
3. **额度上限是运行期配置** `site.article.submit_daily_max`，默认 **15**，后台可调、下一次请求即生效。越界 / 0 / 负数在生效值模块里回落到默认值 15——按字面执行会让全站当天一篇文章都提交不了。
4. **管理员豁免是固定规则**，不随站点配置开关变化。判定在用例层（`actor.IsAdmin()`），Redis 层不认识角色。
5. **Redis 日桶计数**：键 `article:submit:daily:<yyyymmdd>:<userID>`，按日期分桶。跨零点**靠键的 TTL 自然过期**，不依赖定时任务；TTL 取 26 小时，与私信日额度键同一条口径。
6. **预占 / 释放两段式**：先原子占位再做事，失败释放。原子性收在一次 Lua 调用里完成「读计数 → 判额度 → 自增 + 设 TTL」——分开做会出现两个并发提交都读到 14 于是都放行、当日实际用掉 16 次的竞态。
7. **因系统不可用的失败不占额度**：预占之后如果这次提交因为系统故障失败（评分不可用、数据库写入失败），调用方释放预占。释放是幂等的，因此可以同时用显式归还与 `defer` 兜底。
8. **新增错误码** `article.submit_quota_exceeded`，与 `article.forbidden` / `article.publish_disabled_by_site` 分开。混用会让作者去查自己的账号或找管理员改开关，而正确动作是"明天再来"。
9. **零 DDL**：不新建账本表、不给既有表加列。

## 理由与已否决方案

- **否决「数审核任务行」**：语义上确实能一账两用（配额 + 每次提交的时间线），但它有一个前提——**每次提交都建一条审核任务**。而默认配置是 `skip_examining: true`，跳过审核时根本不建任务，账本恒为 0。要修就得让默认配置也永远建任务，代价是管理员在审核列表里看到一堆自己"已经处理过"的自动通过行。
- **否决「新建 `article_submit_log_models`」**：语义最干净，但要多一条 ADR 指名 + 建表脚本与测试夹具两处登记，而它解决的问题和 Redis 日桶完全重合。
- **否决「数发布成功的文章」**：这正是灌水者要的口径——被打回不消耗额度，等于把 15 次额度刷成无限次评分。
- **否决「只写进内存计数器」**：进程一重启就归零，防灌水最怕的正是这个。
- **否决「按信任等级分档 / 被举报者降额」**：两者都需要举报体系、申诉流程或等级模型，而当前仓库一个都没有；先做对单值 + 管理员豁免，等出现职业灌水者再谈分档——那时手里已经有真实数据。
- **否决「定时任务在零点重置」**：键里已经带日期，跨零点用的是另一个键，旧键只需自己过期。多一个定时任务就多一个"任务没跑成功于是额度没重置"的故障面。

## 代价 / 不做什么

- **Redis 计数不是绝对 durable**：AOF 与持久化目录都已就位（`deploy/state/redis/data` + `appendonly yes`），但 `flushdb`、换实例、误删目录仍会清空当日计数。缓解是告警（当日计数键缺失或骤降时报警）——让"丢失可观测"，而不是假装它不会发生。
- **上限只有一个数字**：不支持按用户分档、不支持按天/周多窗口。
- **不记录提交历史**：配额只回答"今天用了几次"，不回答"提交过几次、什么时候"。
- **不在配额里做内容判定**：配额只管次数，写得好不好由质量闸门的评分回答。
- **多实例下的计数一致性依赖 Redis 单点**：与私信限流同一个前提，不额外引入分布式协调。

## 当前生效约束

1. `site.article.submit_daily_max` 是唯一定义处：`backend/config/site_default_settings.yaml` 写字面量 15，`conf/site` 承载类型；生效值模块负责把越界 / 0 / 负数回落，不在别处再写第二份默认值。
2. 计量单位**只能是提交动作**。新增任何"会真实产生模型调用或审核任务"的提交路径（含自动重新送审）时，必须同步在这里预占额度；新增"不产生副作用"的保存路径时不得预占。
3. 预占失败即拒绝提交，返回 `article.submit_quota_exceeded`；不得改写成通用 forbidden。
4. 预占之后的系统性失败必须释放。释放必须幂等。
5. 管理员豁免在用例层判定，Redis 包不得认识角色或读配置。
6. 键格式 `article:submit:daily:<yyyymmdd>:<userID>` + 26 小时 TTL 是口径的一部分：改键名等于让当日计数清零，改 TTL 必须仍然跨过零点。
7. 零 DDL 口径不变：不加表、不加列。
