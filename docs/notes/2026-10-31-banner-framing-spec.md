# 轮播封面取景：固定 16:9，后台上传即取景（存参数，不存第二份图）

- 状态：待实现
- 日期：2026-10-31
- 上游：[ADR-0012 中性玻璃视觉系统](../adr/0012-neutral-glass-visual-system.md)・[ADR-0013 首屏编辑部式封面](../adr/0013-editorial-hero-cover.md)（首屏封面例外区）；建议新提 ADR-0014「轮播取景存参数、CSS 渲染」
- 术语：取景 / 焦点 / 缩放 / 轮播封面（见 `GLOSSARY.md`）

## Problem Statement

首屏轮播面板现在没有锁定比例：容器宽度随布局变化，运营上传的图什么样就渲染成什么样。结果一是**同一张图在不同屏宽下被裁切得不一样**，二是比例差得远的图（竖图、超宽图）在面板里"看着变形"——其实是被 `cover` 裁得莫名其妙。

运营侧的痛点更直接：后台「媒体运营」只能选文件、传上去、填个跳转链接，**完全无法决定这张图露出哪一块**。想让人脸别被切在边上、想让主体别贴着左边框，只能重新做一张图再传。

## Solution

1. **锁定比例**：首屏轮播面板固定 **16:9**，任何屏宽下比例不变（移动端也不换比例）。
2. **上传即取景**：后台选完图先在浏览器里读像素尺寸；比例差在 **±1%** 以内视为合规，直接上传；否则自动弹出 **16:9 取景窗**——图可拖动、可缩放（1.0–2.0），确认后才上传。取消＝中止本次上传，什么也不产生。
3. **只存参数，不存第二份图**：取景结果以「焦点 + 缩放」三个数记在 banner 上，阅读站用 CSS 复现同一取景。原图只有一份，随时可以改取景而不重传。
4. **合规的图也能手动取景**；列表里每张已存在的轮播图都能「重新取景」。
5. **历史图不动**：没有取景记录的图按「居中、缩放 1.0」渲染，行为与今天完全一致。

## User Stories

1. 作为读者，我希望首屏轮播图在任何屏幕宽度下都是同一个形状，这样同一篇首页不会在手机和显示器上看起来是两张不同的图。
2. 作为读者，我希望轮播图里的主体不会因为容器比例变化而被裁得莫名其妙。
3. 作为读者，我希望轮播图加载时不会先闪一下原图再跳成裁切后的样子。
4. 作为读者，我希望轮播图在没有配置任何图时，首屏版式依然成立、不发白不塌。
5. 作为读者，我希望轮播图在减少动态偏好下不动视差，但仍然按取景显示。
6. 作为运营，我希望上传一张比例不对的图时立刻知道并要求我取景，而不是先传上去再发现问题。
7. 作为运营，我希望取景窗口给我一个固定的 16:9 取景框，让我拖图决定露出哪一块。
8. 作为运营，我希望取景窗口支持放大（最多 2 倍），这样一张远景图也能裁出一个可用的特写。
9. 作为运营，我希望取景窗口的预览和线上最终效果完全一致，不用猜。
10. 作为运营，我希望在取景窗口里点取消就真的什么都不发生：不产生图片、不产生轮播，避免我误以为已经上传成功而重复操作。
11. 作为运营，我希望比例已经合规的图也能手动取景，因为构图合规不等于比例合规。
12. 作为运营，我希望上传流程里那一步"取景"是可跳过的（比例合规时），不要每次都强制我拖一遍。
13. 作为运营，我希望在轮播列表里对任何一张已存在的图点「重新取景」，不用重传。
14. 作为运营，我希望取景改动保存后立即生效，不需要清缓存或等下次发布。
15. 作为运营，我希望取景只影响显示，不会偷偷把我上传的原图改动或删掉。
16. 作为运营，我希望后台上传面板明确告诉我"推荐比例 16:9"，这样我第一次传图就能传对。
17. 作为运营，我希望看到某张图的原始尺寸与比例是否合规，方便我判断要不要重做素材。
18. 作为运营，我希望取景时不会把图拖出取景框导致露出空白。
19. 作为运营，我希望缩放滑块有明确的上下限，不会出现无限放大变成马赛克。
20. 作为运营，我希望键盘也能操作取景（方向键平移、加减号缩放），不想被迫用鼠标精细拖拽。
21. 作为开发者，我希望「16:9」只在一处定义、由测试锁住跨端一致，避免阅读站、后台取景框、后端校验三处漂移。
22. 作为开发者，我希望取景参数有不言自明的取值范围（焦点 0–1、缩放 1–2），越界由后端直接拒绝而不是靠前端兜。
23. 作为开发者，我希望取景参数存在独立的新表里，而不是往既有表加列（本项目零 DDL 硬约束）。
24. 作为开发者，我希望接口契约里取景是可选字段，老客户端不传也能正常工作。
25. 作为开发者，我希望阅读站的渲染只依赖一个纯函数（取景参数 → 样式），这样不必为了验证裁切结果去挂载整个首屏。
26. 作为开发者，我希望视差与缩放不打架：两者都动 `transform`，必须分层而不是互相覆盖。
27. 作为开发者，我希望没有取景记录的图（历史数据）走缺省分支，渲染结果与今天完全一致。
28. 作为开发者，我希望取景相关的边界（拖到角落、缩放到极限、图片比容器还窄）都有确定的钳制规则，而不是"浏览器自己会处理"。
29. 作为测试者，我希望比例合规判定的容差被明确成 ±1%，并且有 1919×1079 这类噪声用例。
30. 作为测试者，我希望取景窗口的"确认/取消"语义有断言：取消不产生任何副作用。

## Implementation Decisions

**比例与常量**

- 轮播面板固定 `16:9`，所有断点同一比例。阅读站的面板容器从当前 `16/10` 改为 `16/9`。
- 比例常量不进入运行时配置：写死在两端源码 + 一条跨端静态断言（沿用 `tokens.css` 同源门禁的形式）。理由：比例是设计决策，不是运营可调项；一旦可调，历史图的裁切会随配置漂移。

**数据模型**

- 新增一张一对一表存取景参数：以 banner 主键为外键，字段为 `focus_x`、`focus_y`（0–1 的浮点）与 `zoom`（1–2 的浮点）。
- 不修改任何既有表（本项目零 DDL 硬约束：ES 投影按列名解析，改既有表列会破坏 CDC）。
- 没有对应行的 banner 视为「居中、zoom 1.0」。

**契约**

- banner 的创建/更新请求与列表返回都用**可选的嵌套 `crop` 对象**表达：`{ focus_x, focus_y, zoom }`。可选是为了让老调用方不传也合法，缺省即居中。
- 更新走已存在但后台当前未调用的 `PUT /banners/:id`。
- 走正规契约链路：改 swagger 注解 → 重新生成 openapi → 两端生成类型（CI 的 contract 门禁会校验契约未过期）。

**后端**

- 创建/更新时校验：`0 ≤ focus_x ≤ 1`、`0 ≤ focus_y ≤ 1`、`1 ≤ zoom ≤ 2`；越界返回 400，不做"悄悄 clamp"。
- 取景参数的读写挂在既有 `site` 应用的 banner 用例上，不新建应用服务。
- 图片宽高已落库（头像/图片表有 `width`/`height`，上传确认时由存储侧 `imageInfo` 探测），作为比例判定的权威兜底；但**上传前的判定在浏览器本地完成**，避免为一张比例不合的图先占一份存储。

**后台（媒体运营）**

- 上传流程：选文件 → 本地读像素尺寸 → 判定比例（容差 ±1%）→ 合规：直接上传并允许事后「手动取景」；不合规：先开取景窗 → 确认才上传。
- 取景窗是一个固定 16:9 的框，图在框内可拖动、可缩放（默认居中、zoom 1.0，步进 0.05）；遮罩区压暗，预览即最终效果。
- **取消＝中止上传**（不产生图片、不产生 banner）。
- 列表每行提供「重新取景」，保存走更新接口，立即生效。
- 取景逻辑抽成纯函数（比例合规判定、参数钳制、锚点与缩放边界换算），组件只负责交互与上抛参数。

**阅读站**

- 渲染 = `object-fit: cover` + `transform-origin` 取焦点 + `transform: scale(zoom)`；这些由**一个纯函数**从取景参数算出样式对象，组件只消费。
- 视差与缩放分层：视差只动一层、缩放只动另一层，避免两个 `transform` 互相覆盖。
- 焦点与缩放要做钳制，保证 `cover` 之后仍然铺满面板、不露出面板底色。

**术语**

- 取景（framing）、焦点（focus）、缩放（zoom）、轮播封面（banner cover）写入 `GLOSSARY.md`；刻意避免把这件事叫"裁剪"（crop 指对文件做像素手术，我们不做）。

## Testing Decisions

好的测试只断言**外部行为**：给定输入（图片尺寸、取景参数、请求体）得到什么可观察结果（渲染样式、落库值、HTTP 状态），不断言内部实现细节，也不断言 CSS 类名。

确认采用的 4 条缝（优先用既有缝，尽量不新建）：

1. **后端（沿用既有 seam）**：挂在 `site` 应用的 banner 用例上（仓库已有带状态 fake 的 apptest 方式）。覆盖：缺省 = 居中 + zoom 1、合法参数落库并在列表返回、越界在 HTTP 层 400、更新走 `PUT`。
2. **后台（一条纯函数 seam）**：比例合规判定（含 ±1% 容差与边界用例）、参数钳制、锚点/缩放换算。取景框组件只测三条：拖动与缩放产出什么参数、取消不上抛、确认上抛 `{focus_x, focus_y, zoom}`。
3. **阅读站（一条纯函数 seam）**：「取景参数 → 样式对象」的函数直接断言返回值；例外是面板比例的**设计静态断言**（`aspect-ratio: 16 / 9`），因为那是一个跨组件约束，没有运行时可观察点。
4. **跨端一致（一条静态 seam）**：16:9 常量在阅读站与后台两处一致，形式沿用现有同源门禁（先例：两端 `tokens.css` 逐字节一致的门禁与其 canary）。

先例参照：`site` 服务既有用例（stateful fake）、`frontend/test/design/*` 的静态断言（用于比例这种结构约束）、`frontend_admin` 的 `app/utils/**` 单测（用于纯函数）。

## Out of Scope

- 不做服务端裁切，也不引入七牛 `imageMogr2` 之类的厂商样式参数（渲染留在 CSS，避免把排版绑死到存储厂商）。
- 不保存"裁剪后的第二份文件"，只保存取景参数。
- 不修改任何既有表结构（零 DDL）。
- 不做批量重裁/批量迁移历史图。
- 不做人脸识别、主体检测、AI 自动取景。
- 不引入 cropperjs / fabric / sharp / jimp 等图像库（取景窗自绘）。
- 不改上传链路本身（仍是浏览器直传对象存储 + 后端签发），不改七牛 MIME/大小限制。
- 不做移动端专用比例（不做 4:3、1:1 等变体）。
- 不提供"按屏宽下发不同取景参数"的响应式裁切。
- 旋转、镜像、滤镜等图像编辑能力不在本次范围。

## Further Notes

- 这轮改造已经在集成分支上把面板改成过 `16/10`，实现时统一收敛到 `16/9`，别留两套。
- `GLOSSARY.md` 当前有使用者未提交的改动，术语要在实现落地时单独提交，避免混提交。
- 已知实现风险：视差用 `transform`、缩放也用 `transform`，两者必须在不同层；焦点钳制没做好会在面板边角露底。
