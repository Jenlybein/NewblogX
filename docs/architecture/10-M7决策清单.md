# 10 · M7 决策清单（方案 E：ID 类型即真相）

> 拍板时间：2026-10-26
> 决策：**采用方案 E**（ID 类型底层改 string），不走方案 A（`.swaggo` 覆盖）。
> 理由：A 买的是"这次对了"，E 买的是"以后都对"。用户明确选择彻底性。
> 完整论证见 `adr/ADR-007-ID类型统一为string底层.md`。
>
> **状态：P0 / E1–E6 全部交付（2026-10-26）。** 执行结果与偏差见 §7。

## 0. 一句话概括

**让 Go 里的 ID 类型和它在 JSON 里的样子是同一个东西**——类型是 `string`，JSON 就是 `"123"`，`swag` 读类型声明时不可能印错。数据库那边照旧走 int64，DDL 一行不改。

代价：约 240 处改动 + 6 处语义风险要人工审 + golden 重生成。
收益：删掉后处理脚本，契约**一次生成就对**，且以后不会重犯。

### 验收结果（可复跑）

```bash
cd backend && swag init -g cmd/server/main.go -o docs --parseDependency --parseInternal
# swagger.json 里字段名匹配 ID 语义、type 仍是 integer ⇒ 0 处
# path/query/form 参数里 type 仍是 integer 的 ID ⇒ 0 处

cd backend && go build ./... && go vet ./...     # 干净
# 必须带 tag 再跑一遍：go vet ./... 不编译 //go:build integration 的文件
cd backend && CGO_ENABLED=1 go vet -tags integration ./...
cd backend && go test ./... -count=1             # 82 包全绿（需 CGO_ENABLED=1）
cd backend && go run ./tools/archcheck --skip-tests=false .   # 0 违规（R12 基线 0）
test ! -f backend/.swaggo
test ! -f frontend/scripts/fix-openapi-id-types.mjs
```

## 1. 为什么不选方案 A

| | 方案 A（`.swaggo` 覆盖） | 方案 E（ID 改 string） |
| --- | --- | --- |
| 契约一次生成就对 | ✅ 但只覆盖 `ctype.ID` 那 61 处 | ✅ 全部 |
| 能删修补脚本 | ❌ 还差 75 处没覆盖 | ✅ |
| 隐式转换层（类型数字 / 传输字符串） | **还在** | **消失** |
| 新写个 `uint64` ID 字段 | 契约会再错一次 | 只要用 `ctype.ID` 就自动对 |
| 工作量 | 约 119 处 | 约 240 处（E 的 2 倍） |
| 额外风险 | 无 | 6 处大小比较语义 + golden 重生成 |

**E 比 A 多付的一半工作量，买的是"根因消失"。**

## 2. 实测数据（不是估算，来自 `/tmp/be-probe` 副本实验）

| 阶段 | 处数 | 内容 |
| --- | --- | --- |
| 10 个 ID 类型定义改 string | 40 | 含 `article/domain/id.go` 的 `type (...)` 块 |
| 业务代码主体 | 148 | `uint64(x)` → `x.Uint64()`、`x == 0` → `x == ""` |
| 迭代第二轮才暴露 | 10 | 修完第一批才露出来 |
| 仍是 uint64 的 ID 字段 | 22 | `HomeStyleID`、`account.ID`、`row.UserID`、JWT claims |
| 测试文件 | ≥21（低估） | `go vet` 只查到 3 个就停了 |
| **合计** | **≈240** | 45+ 个文件 |

**关键发现：192 → 22。** 只改 `ctype.ID` 时残留 192 处转换错误；10 个类型统一后塌缩到 22 处。说明"10 套 ID 类型并存"本身就是债。

### P1 · E1 类型定义

| # | 任务 | 要点 |
| --- | --- | --- |
| E1-1 | `ctype.ID` 底层改 `string` | 补 `Uint64()` / `Uint64OrZero()` / `IsZero()` / `ParseID()` / `String()` |
| E1-2 | `Value()` / `Scan()` 保持 int64 转换 | **零 DDL**：列名类型一律不动 |
| E1-3 | `MarshalJSON` / `UnmarshalJSON` 兼容 | 反序列化要**同时接受数字与字符串**（存量客户端 / DB 导出 / 测试夹具） |
| E1-4 | 其余 9 个 ID 类型收敛为 `ctype.ID` 别名 | `type ArticleID = ctype.ID` 之类 |
| E1-5 | 单独一个 commit，允许此步编译不过 | 方便回滚与 diff 审阅 |

### P2 · E2 业务适配（约 148 处）

| # | 任务 | 要点 |
| --- | --- | --- |
| E2-1 | `uint64(x)` → `x.Uint64()` | 编译器会逐个指出，按包推进 |
| E2-2 | `x == 0` → `x == ""` 或 `x.IsZero()` | 建议统一走 `IsZero()`，语义更清楚 |
| E2-3 | `return 0` → `return ""` | 同上 |
| E2-4 | 迭代到 `go build ./...` 通过 | 第二轮会暴露约 10 处，别以为一轮就完 |

### P3 · E3 剩余 ID 字段收编（实测 175 处，不是 22 处）

| # | 任务 | 结果 |
| --- | --- | --- |
| E3-1 | `HomeStyleID`、`account.ID`、`row.UserID`、JWT claims 等改成 `ctype.ID` | ✅ 全仓 175 个裸整型 ID 字段 → 实际收编 **149 个**（含 gorm row、domain 实体、port 输入结构、JWT claims、kernel.IDRequest/IDListRequest） |
| E3-2 | 这些字段原本就在丢精度，收编是治 bug 不是擦屁股 | ✅ 26 个按理由豁免（见下） |
| E3-3 | 契约侧：41 个 ID 字段仍是 integer、32 个 `@Param` 仍是 int | ✅ 全部转 string；`swagger.json` 里 integer 型 ID 归零 |

**26 个豁免（不是"懒得改"，每条都有理由）**

| 范围 | 数量 | 为什么不改 |
| --- | --- | --- |
| `internal/platform/log/**` | 6 | ClickHouse 落盘事件结构，列是 `UInt64`。外部真相在 `01-logs.sql` 里，Go 侧改成 string 反而与列类型不一致，且可能让 `JSONEachRow` 摄入失败——那是"日志丢数据"，比契约印错严重得多 |
| `internal/testkit/schema/**` | 17 | 同上，CH 表测试行结构 |
| `ServerID`（conf ×3 + canalbase ×1） | 4 | MySQL 复制协议的 `server_id` / 雪花机器号，uint32 节点编号，不是业务实体 ID，也不进 HTTP 契约 |
| `initializedID`（platform/idgen） | 1 | 雪花 worker 编号 |

**顺带修掉的隐性缺陷**（编译器抓不到，靠人工审 / 规则抓）

- `internal/chat/domain/chat.go` `BuildSessionID`：字符串比较会让 `"10" < "9"` 成立，双方算出不同 session_id → 消息串号。已改数值比较。
- `internal/site/domain/site.go` `Banner.CoverImageID`：早期人工审计脚本因行尾有注释漏掉，是 R12 上线当天抓出来的。

## 6. 回滚

| 阶段 | 回滚方式 |
| --- | --- |
| P1 单独 commit | `git revert` 该 commit 即可，其余阶段还没开始 |
| P2 之后 | 按 commit 逆序 revert；golden 基线一并回退 |
| 全程失败 | 回到 `refactor-start` 之后的最新 tag；契约侧退回方案 A（`.swaggo` 已验证可用） |

**保底路线**：E 若在中途发现牵连面远超 240 处，**立即降级到方案 A**（`.swaggo` 一行 + 89 处字段收编 + 30 处注解），A 已经实测可行，不会白做——89 处收编在两条路线上都是要做的。

## 7. 风险

| 风险 | 概率 | 应对 |
| --- | --- | --- |
| 牵连面远超 240 处 | 中 | 降级方案 A；89 处字段收编是两条路的公共部分 |
| 6 处大小比较漏改导致排序错 | 中 | 人工逐处审 + golden 兜底；这是唯一编译器抓不到的 |
| `UnmarshalJSON` 不接受数字导致存量数据解析失败 | 中 | E1-3 必须同时兼容数字与字符串输入 |
| golden 基线重生成后掩盖真实回归 | 低 | 重生成时必须人工 diff 一遍排序变化，确认只有顺序变 |
| 换 swag v2（E5-4）引入 rc 版不稳定 | 低 | 独立排期，不与 E 主干绑定 |
