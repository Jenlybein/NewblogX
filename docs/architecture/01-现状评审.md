## 1. 分层：目录建了三层，但只有一层在工作

### 1.1 真实的调用路径

名义上是 `api → service → repository → models`。实际情况：

```
HTTP handler (api/, 138 个非测试文件 / 10,494 行)
   ├── 61 个文件直接 import gorm.io/gorm，194 处直接查库
   ├── 部分调用 service/（131 文件 / 17,732 行）
   └── 部分绕过 repository 直接写 SQL
   
service/
   ├── 40 个文件 import gorm，91 处查询，111 个函数首参是 *gorm.DB
   └── 12 处调用 repository/（仅 2,076 行，service 的 9%）

repository/
   └── 全是 func X(db *gorm.DB, ...)，连接由上层传入
```

**三层都在做数据访问。** 这不是分层，是三个平行的 SQL 存放处。

### 1.2 证据

**handler 直接查库（194 处，`api/` 61 个文件）：**

| 位置 | 代码 |
| --- | --- |
| `api/article_api/article_detail.go:85-87` | `h.App.DB.Model(&models.ArticleDiggModel{}).Where(...).Count(...)` |
| `api/article_api/article_digg.go:37-40` | `app.DB.Where(map[string]any{...}).Delete(&models.ArticleDiggModel{})` |
| `api/data_api/data_sum.go:21-31` | **handler 内拼接 6 个子查询的原生 SQL** `app.DB.Raw(...)` |
| `api/data_api/article_status_helper.go:18-21` | `db.Table("article_models").Where(...)` |
| `api/article_api/category/category_create_update.go:28` | `h.App.DB.Create(&category)`（另有 12 处写操作同样在 handler 内） |

**更严重的信号**：`api/article_api/article_write_service.go`（279 行）——
在 `api` 包内定义了一个叫 `newArticleWriteService(*gorm.DB, ...)` 的"服务"。**业务逻辑为了绕开 service 层，在 api 包里又造了一个 service。**

### 1.3 模块粒度完全错配

`api` 与 `service` 文件数都是 170，但这是巧合：

| api | service | 倍数 |
| --- | --- | --- |
| `article_api` 55 文件 / 6,012 行 | `article_service` **1 文件 / 99 行** | **61×** |
| `comment_api` 15 / 1,832 | `comment_service` **1 / 11** | — |
| `log_api` 2 / 595 | `log_service` 17 / 2,489 | 0.24× |
| `ai_api` 12 / 1,824 | `ai_service` 27 / 2,835 | 0.64× |
| `banner_api`、`data_api`、`global_notif_api`、`captcha_api` | **无对应 service** | — |

`comment_service` 只有 **11 行**——它甚至不够放一个业务判断。

结论：**不存在"业务层"。业务逻辑就在 handler 里**，`service/` 只是那些"恰好被抽出来"的函数集合。

## 2. 伪依赖注入：`Deps` 装箱

这是本项目最具代表性的架构问题。

### 2.1 规模

```
32 个 type Deps struct
30 个包含 *gorm.DB
```

也就是说，**30 个不同包里的结构体，都能拿到整台数据库。**

### 2.2 同一份依赖被抄了 N 遍

```go
// apideps/deps.go:17  —— 18 个字段
type Deps struct {
    Version, ConfigFile string
    System conf.System; JWT conf.Jwt; Log conf.Logrus
    ClickHouseConfig conf.ClickHouse; ES conf.ES; QQ conf.QQ
    Email conf.Email; QiNiu conf.QiNiu; Upload conf.Upload
    Logger *logrus.Logger
    DB *gorm.DB; Redis *redis.Client; ClickHouse *sql.DB
    ESClient *elasticsearch.Client
    RuntimeSite *site_service.RuntimeConfigService
    ImageCaptchaStore base64Captcha.Store
}

// api/enter.go:32  —— 17 个字段，与上面逐字相同，只少了 ConfigFile
type Deps struct { /* 同样的 17 行 */ }
```

`app/wiring_http.go` 更直接：**同一个函数里手工抄写两遍**（`routerDeps` 在 `:18-37`，`httpDeps` 在 `:39-57`），17 个字段逐行复制。

### 2.3 六层传递链

```
Infra (app/bootstrap.go:22, 9 字段)
  → apideps.Deps (18 字段)
    → api.Deps (17 字段)
      → article_api.Deps (api/article_api/enter.go:17, 5 字段)
        → category.Deps (api/article_api/category/enter.go:11, 4 字段)
          → view_history.Deps (api/article_api/view_history/enter.go:7, 1 字段)
```

`api.New` 从 `api/enter.go:70` 到 `:167`，**逐字段展开拆出 15 个子 Deps**，全程没有接口、没有生命周期、没有可替换实现。

### 2.4 为什么这比 `global.DB` 更糟

| | 裸 global | Deps 装箱 |
| --- | --- | --- |
| 依赖可见性 | 不可见（要看函数体） | **看起来可见**（有结构体签名） |
| 实际耦合 | 任意模块可取 DB | **同样任意可取 DB**（30 个 Deps 都含 `*gorm.DB`） |
| 测试替换 | 只能改全局变量 | 要构造完整 Deps，**比改全局变量更麻烦** |
| 认知成本 | 低（一眼看出是全局） | **高（误以为已解决）** |
| 新增依赖 | 加一个全局变量 | 改 6 层结构体 + 15 处展开 |

**最关键的一行**：它让人以为重构已经完成了。这比坦率的 `global.DB` 危险——因为没人会再去修一个"已经改过"的问题。

## 3. 空壳抽象层

### 3.1 `platform/` 共 63 行

```go
// platform/dbx/init.go:13
func Init(...) *gorm.DB { return core.InitDB(...) }      // 一行转发

// platform/cachex/init.go:12
func Init(...) *redis.Client { return core.InitRedis(...) }

// platform/searchx/init.go:12
func Init(...) *elasticsearch.Client { return core.EsConnect(...) }
```

无接口、无第二实现、无 mock 点。**抽象层的全部价值在于"可替换"，而这里没有任何东西可以被替换。**

唯一的副作用：`cachex/deps.go` 的两字段包装 `{Client, Logger}` 被 13 处引用，成了把 Redis 塞进 repository 的通道。

### 3.2 `app/` 有两条死路径

```go
// app/bootstrap.go:89
func Bootstrap(...)   // ← 全项目 0 个调用点（main 用的是 InitInfra + InitRuntimeServices）

// app/lifecycle.go:32
func (l *Lifecycle) OnStop(...)   // ← 全项目 0 个调用点
```

`OnStop` 没人注册 ⇒ `stopHooks` 永远为空 ⇒ `WaitForShutdown` 只打印一行日志，**没有任何优雅停机逻辑**。

### 3.3 `repository/` 是静态函数库

- 总 **2,076 行**，是 service 的 **9%**
- `repository/article_repo/` **只有一个 `.gitkeep`（2 字节）**——文章是这个系统最核心的聚合，它的仓储目录是空的
- 签名清一色 `func X(db *gorm.DB, ...)`，**不持有连接**
- 内部互相依赖：`chat_repo`、`comment_repo`、`favor_repo`、`follow_repo`、`top_repo` 全部 `import read_repo` ⇒ `read_repo` 已退化为公共工具包
- 33 个 service 文件、91 处查询完全绕过它

## 4. 架构治理：一场永真的表演

> 这一节是本次评审最意外的发现，也是"架构很差"最直接的证据。

### 4.1 两套重复的守卫

| 实现 | 位置 | 规模 |
| --- | --- | --- |
| PowerShell 脚本 | `scripts/arch_guard.ps1` | 110 行，9 条规则 |
| Go 测试 | `apps/api/test/architecture/{di_guard,no_global_refs}_test.go` | 260 行，6 个测试 |

**两者检查的是同一批东西**（禁止 appctx、禁止 Service Locator、service 不 import gin、repository 不 import service、api 不 import repository）。同一份规则维护两遍。

### 4.2 它们检查的符号全都不存在

```bash
$ for p in appctx global MustFromGin DepsFromGin mustApp; do
    echo -n "$p: "; grep -rn "\"myblogx/$p\"" --include="*.go" . | wc -l
  done
appctx:        0
global:        0
MustFromGin:   0
DepsFromGin:   0
mustApp:       0
```

对应目录也不存在（`ls apps/api/global` → No such file or directory）。

**结论：13 条规则 + 6 个测试全部永真通过。** 它们守的是一年前就已经不存在的敌人。

而真正的问题——32 个 Deps、61 个 handler 直接查库、空 repository、1,547 行的单文件——**没有任何一条规则覆盖**。

### 4.3 唯一"有效"的规则被别名绕过

规则「`api` 禁止 import `repository`」是唯一能真正阻断越层的。但：

```go
// service/top_service/query.go:1-8
type QueryService = repo.QueryService
var NewQueryService = repo.NewQueryService
```

`service/{top,favorite,comment,read}_service/query.go` 四处都是纯别名 re-export。于是：

```go
// api/comment_api/comment_list_man.go:45
comment_service.NewQueryService(h.App.DB, ...)   // 实际就是 repo.NewQueryService
```

**api 依然直接构造 repository 的 QueryService，只是绕了一层改名。** 守卫看不到 `repository` 字面量，规则通过。

### 4.4 守卫本身的脆弱性

- `Assert-NoMatch`（`:35-54`）用 `Select-String -Quiet`，**只返回文件名，不返回行号**
- `Get-GoFiles`（`:31-32`）排除所有 `_test.go` ⇒ 测试代码不受约束
- `\*conf\.Config\)` 规则只匹配**紧邻右括号**，`f(cfg *conf.Config, x int)` 会漏掉
- 纯 PowerShell + `powershell -ExecutionPolicy Bypass` ⇒ **Linux/CI 上无法运行**
- 无 `.github/workflows`、无 git hook ⇒ **从不自动执行**

### 4.5 一句话

> 这个项目花了 370 行代码建立架构治理，
> 结果治理的是一个已经不存在的架构，
> 而真正的架构在无人看守下继续腐化。

## 6. 前端与前后端边界

### 6.1 同一个后端，三个别名

```ts
// apps/web/server/routes/api/[...path].ts:6          → apiUpstream
// apps/web/server/routes/_backend/[...path].ts:7-8   → 同一个 apiUpstream
// apps/web/server/routes/_origin/[...path].ts:6      → 同一个 apiUpstream
```

`deploy/docker/nginx/nginx.production.conf` 又复制了 3 份 location（`:74` `/api/`、`:115` `/_backend/api/`、`:124` `/_origin/`），全部指向 `blogx_api_upstream`。

**同一个功能维护了 4 份**（Nitro 3 + nginx 3 + devProxy）。`app/utils/avatar.ts:51-53` 里还专门写了把 `/_backend/x` 改写成 `/{assetProxyBase}/x` 的兼容代码——说明这是历史包袱，且没人敢删。

### 6.2 `packages/` 是空声明

`pnpm-workspace.yaml:6-7` 声明了 `packages/*`，但**该目录不存在**。

### 6.3 两份幽灵 lockfile

```
aaba985a12cd34ae26f1505e21fc8304  apps/admin/pnpm-lock.yaml  (6,704 行)
```

### 6.4 两个 app 重复约 500 行

| 文件 | web | admin |
| --- | --- | --- |
| `services/http/client.ts` | 103 行 | 72 行 |

### 6.5 openapi 契约无人消费

```
openapi/myblogx.openapi.json: 14,462 行 / 90 path / 118 operation / 131 schema
```

目前未泄漏（`runtimeConfig` 只暴露白名单 5 个），但这是结构性风险：一次 `NUXT_PUBLIC_` 手误就会外泄。

## 7. 工程化：写了但不执行

### 7.1 无 CI，无 hook

```
git log --all 共 60 次提交，从未出现 .github/ workflow / jenkins / husky / eslint
.git/hooks 只剩样例文件
```

**后果**：117 个测试文件、2,357 处断言、13 条架构规则、6 个架构测试——**全部只在开发者手动执行时才运行**。

### 7.2 `pnpm lint` 是空转

```json
"lint": "pnpm -r --if-present lint"
```

5 个 workspace 的 `package.json` **没有一处定义 `lint`**，`--if-present` 让它们全部跳过 ⇒ **退出码永远是 0**。

仓库中 0 个 eslint / prettier / stylelint 配置。后果肉眼可见：`apps/web/.../client.ts` 用双引号加分号，`apps/admin/.../client.ts` 用单引号无分号。

### 7.3 typecheck 不在构建链路上

`nuxi typecheck` 只被根脚本手动调用，没编入 turbo `build` 的 `dependsOn`。两个前端 Dockerfile 直接 `pnpm exec nuxt build` ⇒ **整条发布链路一次类型检查都不跑**。

讽刺的是 `prototype/web/package.json:6` 的 build 反而包含 `vue-tsc --noEmit`。

### 7.4 测试分布失衡

- 117 测试文件 / 20,577 行 / 2,357 断言，但 **只有 3 处 `t.Parallel`**（全在 `cron_service/log_cleanup_test.go`）
- `repository/`（449 行核心 SQL）**0 测试**
- `apps/admin` **0 测试、无 test 脚本**
- 前端只覆盖 6/29 组件、0/15 页面；`vitest.config.ts:29` 无 `thresholds`
- 好消息：测试是自包含的（SQLite 内存库 + miniredis + httptest），**能跑，只是没人跑**

### 7.5 构建与发布

- `buildinfo/version.go` 是 46 字节的 `const Version = "1.0.0"`，**无 `-ldflags` 注入** ⇒ 无法从运行实例追溯 commit
- Docker **完全绕过 turbo**（不 COPY `turbo.json`，`.dockerignore` 排除 `.turbo`）⇒ 缓存复用为 0
- `deploy/docker/admin/Dockerfile:16` 在 `pnpm install`（`:18`）**之前**就 COPY 源码 ⇒ 任何改动击穿依赖层（web 版做对了，两者不一致）
- 只有 `deploy/compose/local/`，**没有生产 compose / k8s / 部署流水线**

## 8. 数据层：有真实进步，但仍有硬伤

### 8.1 已经做对的部分

**ES 同步已经统一为单通路（river/canal）**：

```
river_service/article_search_projection.go:41-77
   ├── SyncESDocsByArticleSnapshots
   ├── UpdateESDocsByArticleDeltas
   └── SyncArticleSearchProjection
```

应用侧（`api/`）不再直接写 ES。这修复了"应用双写 + binlog 双通路互相覆盖"的老问题，是**实质性改进**。

另有 `service/cdc_dead_letter_service/`（死信处理），说明 CDC 失败有兜底。

### 8.2 仍存在的问题

| 问题 | 证据 |
| --- | --- |
| **`article_sync.go` 1,547 行 / 42 函数** | 单文件承担快照加载、delta 计算、文档构建、bulk 提交、失败解析全部职责 |

**AI 侧补充**：`conf_ai.go` 的 `TimeoutSec` / `Temperature` / `DailyQuota` / `ReasonModel` 四个字段此前是死配置，需确认本版是否已接线。新增的 `ai_service/article_score_service` 是第六个 AI 用例，同样走手写 HTTP。

## 10. 值得保留的部分

评审不应只挑毛病。以下部分**质量良好，应保留**：

| 模块 | 理由 |
| --- | --- |
| **ES 同步的单通路设计** | `river_service/article_search_projection.go` 把 ES 写入收口到 CDC，是正确方向 |
| `cdc_dead_letter_service` | 死信处理意识，说明考虑过失败路径 |
| `service/redis_service/*` | 分域清晰（article/comment/tag/user/site/...），key 构造与读写封装完整 |
| `es_service/enter.go`（517 行） | 纯 ES 客户端封装，无业务泄漏 |
| 测试基建（SQLite 内存库 + miniredis + httptest） | 自包含、能跑，是难得的资产 |
| `models/ctype.ID`（uint64 → JSON string） | 规避前端精度丢失，设计正确 |
| `test/architecture/` 的存在本身 | 至少有人意识到要用测试守架构——问题只是守错了目标 |
| web 的 `services/http/client.ts` | 统一收口，组件内直接 `$fetch` 仅 1 处 |

**这个项目的代码不是"能力不足"，是"缺少会让错误暴露的机制"。** 一个人能写出单通路的 CDC 同步、死信处理、自包含的测试基建，说明工程能力在线；但因为没有 CI、守卫永真、lint 空转，所有问题都能安静地活到线上。
