# ADR-0040：发布判定改为木桶（六项都要过线）+ 评分口径做成运行时策略文本 + 内容形态硬封顶

- 状态：已交付
- 日期：2026-11-10
- 来源：线上的真实误判（一篇两行祝福语的投稿拿到 51 分并被发布）· 修订 [ADR-0032](./0032-quality-gate.md) 的判定口径 · 沿用 [ADR-0030](./0030-runtime-policy-skills.md) 的策略文本机制

## 背景与问题

站点开着质量闸门时，一篇只有两行的「受邀留言，祝愿网站越来越好」拿到了 **51 分**并被放行。事后读代码，能看出这不是模型偶然抽风，而是三处结构性问题的叠加：

1. **展示分数是加权平均**。模型自己给的总分会被丢弃，系统按 20 种文体的权重表重算六维加权分。短文本在 `clarity`（清晰）与 `language`（没有语病）上确实能拿高分——**因为它没有东西可错**——加权后就把总分抬过了线。
2. **判定只有一个数**。闸门只看 `TotalScore >= pass_score + gray_band_width`，没有任何维度级判定。于是"某一项崩了、其余五项不错"与"六项都不错"会被同一把尺子放行，而前者的读者感受是**这篇什么都没讲**。
3. **提示词没有形态底线**。原提示词只有"保守、不虚高、按分档给分"，没有一句关于篇幅、信息量、空洞程度的要求；缺维度时兜底分还是 50（等于白送及格）。评分口径也写死在 `ai_scoring_prompt.go` 里，改一次要发版。

第 1 条与第 2 条必须一起改：只改提示词，模型仍会如实说"这段话清晰、没语病"，问题出在**加权允许短板被长板抵消**这条规则本身。

## 决策

1. **判定改木桶**：总分 ≥ 发布线（`pass_score + gray_band_width`）**且**六个维度**每一项** ≥ `pass_score`。上限复用既有配置，不新增第二个数字。
2. **灰带只作用于总分**，维度下限就是及格线本身。两个数字各管一件事，不共用——否则调灰带会顺手抬单项线。
3. **两个驳回理由分开表达**：`gap` 只表示总分差额（总分过线时归零，不给负数），`weak_dimensions` 只列 `< pass_score` 的维度（分最低的排最前）。作者侧因此分两种文案，而不是一句含糊的"未达标"。
4. **评分口径做成运行时策略文本**：新增 `skills/scoring/SKILL.md`，在 `ai.scene_skills.scoring` 绑定。代码只保留**解析契约**（JSON 形状、维度键名、分档数字）与一条不可让渡的底线，宽严判断交给运营可改的正文。
5. **口径冲突时以更严的为准**：策略正文注入时会明确写"与内置规则冲突时以更严的那条为准"。这条是为了防止换上一份宽松文案就把底线抹掉。
6. **代码侧形态硬封顶**（不依赖模型自觉）：
   - 正文 < 100 字或 < 3 个自然段 → `completeness` ≤ 30、`structure` ≤ 45、总分 ≤ 40；
   - 整篇基本是寒暄 / 祝福 / 致谢 / 链接文本（短 + 段落少 + **多数句子**命中礼节词）→ 总分 ≤ 30、`completeness` ≤ 20。
7. **总分与维度自洽**：总分不得高于「最低维度 + 15」。这条对形态正常的文章也生效，是"长板补短板"的统一堵口。
8. **端口形状补齐**：`QualityGateScore` / `GateScoreResult` 都带上六维得分；拿不到维度分时（旧记录、实现未填）退回"只看总分"，**不**把所有人的提交一起拒掉。
9. **缺失维度的兜底分从 50 降到 40**。原来的 50 在"只看总分"的年代无害，但木桶下它正好压在默认及格线上——模型漏给一项就等于白送过关。兜底分必须稳定低于任何合理的及格线。
10. **不重算存量**：已发布文章不重算、不下架，只影响新提交；要重算走作者「重新评分」入口（吃 `scoring` 每日额度）。

## 理由与已否决方案

- **否决"只把 pass_score 从 50 抬到 60"**：两行祝福语在清晰与规范两项上照样能到 60+，抬线只是让**边缘**文章更难发，拦不住"没有信息量"这类文本——它的高分恰恰集中在不衡量信息量的维度上。
- **否决"只改提示词"**：提示词是请求不是保证。这次事故本身就证明模型会给出与常识冲突的分；一个能被"这次没遵守"绕过的判定不算判定。
- **否决"新增独立的 `dimension_min_score` 配置"**：多一个数字就多一处要解释的相互作用，而"每项都要及格"正是"及格线"这个词的直觉含义。代价是放弃了"总分 50、单项只要 40"这种组合，目前没有任何场景需要它。
- **否决"木桶替代总分"**：那样"六项都 51"与"六项都 90"会被同一标准放行，分数失去区分度；总分仍是"整体值不值得读"的粗粒度信号。
- **否决"把评分提示词整体搬进 skill"**：JSON 形状与维度键名是**解析契约**，写进可热改的文本等于让运营一次手滑就让所有评分解析失败。分工按 moderation 的老规矩：代码管形状，文本管宽严。
- **否决"用行数/字数的软提示（只写进提示词）"**：与上一条同因——可数的硬事实就该在代码里判，且它天然可测。
- **否决"按文体豁免完整度下限"**：本站是个人博客，「通知 / 邮件」这类标签很容易被拿来当绕过口子；所有文体同一套维度底线。

## 代价 / 不做什么

- **短而好的文章会被误伤**：一条三行的精炼笔记也会被封顶到 40 分。这是有意的取舍——闸门开着时，本站更愿意让"不够一篇"的东西留在草稿里。
- **礼节词判据是启发式**：`祝愿 / 感谢 / 支持` 这类词在真正的文章里也会出现，所以判据是"短 + 段落少 + 多数句命中"，缺一条就不触发。仍可能漏判（比如纯表情符号），漏判时退回"过短"那条封顶。
- **作者可能收到两条驳回理由**：总分不够 + 某一项不够会同时出现。这是真实情况，不做合并。
- **策略文本可以放松口径，但放不过硬封顶**：运营改 skill 能把"完整度 ≤ 30"的**提示**去掉，但去不掉代码里的封顶。
- **不做**：按文体的差异化维度权重（维持现有 20 套权重表）、评分历史留档、AI 分与人工分的一致性校准、按读者反馈回流调阈值。
- **不重算存量**：历史文章维持原分数与可见性。

## 当前生效约束

1. **放行 = 总分过线 AND 六项都 ≥ `pass_score`**。不得只判其中一侧；也不得给维度下限单独加灰带。
2. **`weak_dimensions` 只列 `< pass_score` 的维度**，分最低的排最前；`gap` 只表示总分差额，被维度卡住时必须是 `0`（不是负数）。
3. **维度中文名只在前端一处映射**（`frontend/app/utils/scoreDimensions.ts`），后端只传英文键。
4. **形态封顶的数字只在 `backend/internal/ai/scoring/ai_scoring_shape.go` 声明一次**；改动必须同步 `skills/scoring/SKILL.md` 里的表格与测试。
5. **提示词的解析契约（JSON 形状、维度键名、分档）不得进入 skill 正文**；运营可改的只有宽严判断。
6. **策略与内置规则冲突时以更严的为准**，这句必须留在提示词里，不得删。
7. **摘掉 `scoring` 绑定不等于关掉底线**：内置形态下限必须始终在提示词与代码里；绑定缺失不报错（否则一个配置手滑会让全站发不出文章）。
8. **拿不到维度分时退回只看总分**，不得因此拒绝所有提交，也不得假装它过了木桶。
9. **缺失维度的兜底分必须低于及格线**（当前 40），不得改回 50——那等于"模型漏给一项就自动过关"。
10. **不重算存量文章**。
