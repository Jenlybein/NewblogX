# ADR-003：前后端契约以代码生成为单一来源

## Status

**Proposed**（2026-10-24）

## Context

现状：

```
openapi/blogx.openapi.json   14,462 行 / 90 path / 118 operation / 131 schema
```

它是一份**手写文档**（`info.description` 自述"已按当前 router 实际注册路由对齐"，非 codegen 产物）。

而全仓对它的引用：

```bash
$ grep -rn "openapi" --include=*.{ts,json,yaml} . | grep -v "myblogx.openapi.json:" | grep -v node_modules
（空）
```

**唯一命中是文件自身。**

前端类型则是手写的：

| 文件 | 行数 | interface 数 |
| --- | --- | --- |
| `frontend/app/types/api.ts` | 736 | 80 |
| `apps/admin/app/types/...` | 269 | 28 |

### 后果

1. **118 个后端 operation ↔ 108 个前端手写 interface，零机械校验**
2. 字段改名（如后端 `digg_count` → `likeCount`）只会在**运行时**暴露为 `undefined`，或者 500
3. 三处需要同步维护：后端 struct、openapi json、前端 interface。手工同步必然漂移
4. 字段风格已经混杂：`site_title`（蛇形）与 `ThemeMode`（帕斯卡）并存
5. 那份 14,462 行的 json 因为没人用，改了也不会有人发现——它已经是"文档负债"

### 额外成本

因为类型不可信，前端只能靠运行时防御：
- `services/*.ts` 里大量 `as any` / 可选链默认值
- 测试用手写 mock（`frontend/test/`），而不是契约校验

## 备选方案

### A. 保持手写，只做人工对齐

- 优点：零改造
- 缺点：已经证明会漂移；14,462 行文档无人消费
- 判断：**维持现状等于接受漂移**

### B. 后端注解 → openapi → 前端类型（推荐，即"像 FastAPI 那样自动维护"）

```
Go handler + struct + swag 注解          ← 单一来源：后端代码
        │  make openapi  (swag init)
        ▼
backend/openapi.json                     ← 自动生成产物（可入库供工具消费）
        │  openapi-typescript   （每个前端各自跑）
        ├──────────────▶  frontend/src/api/generated/api.gen.ts
        └──────────────▶  frontend_admin/src/api/generated/api.gen.ts
```

> **回答"有没有像 FastAPI 那样自动维护"**：有，这正是做法。FastAPI 读 Python 类型推导生成 OpenAPI；
> Go 这边用 `swag` 读 handler 上的 `// @Summary` 等注解 + struct tag 生成 `openapi.json`——**原理完全一致：代码即契约，文档/lint 都从代码派生，不再有手写文档需要人工同步**。
> 若想进一步摆脱注解、做到"零标注自动推导 schema"，可评估 `go-fuego`（泛型 handler 自动出 OpenAPI），但需替换 Gin 路由层；本次不换框架，故 `swag` 为首选。

- 优点：
  - 单一来源（后端 struct）
  - 漂移从"运行时 500"变成"编译期报错"
  - 前端删除 1,005 行手写 interface
  - openapi json 重新变成有用的东西（可做 Mock、SDK、文档站）
- 缺点：
  - 需给 118 个 operation 补注解（一次性工作量）
  - `swag` 对泛型、复杂嵌套支持有限，可能需要手工补充 `$ref`
  - 生成产物入库，需要 CI 校验"生成结果与提交一致"

### C. 后端直接输出 TS 类型（不用 openapi）

用 `tygo` 之类工具从 Go struct 直接生成 TS。

- 优点：少一层，更简单
- 缺点：
  - 只覆盖 struct，无法表达路由、状态码、参数位置
  - 丢失 openapi 作为"对外契约"的价值（若将来有第三方接入）
- 判断：**只适合纯类型共享，不适合 API 契约**

### D. tRPC / Connect 之类 RPC 框架

- 优点：端到端类型安全，无需 codegen
- 缺点：需要改后端路由层（Gin → 支持 RPC 的框架）、改前端调用方式。83k 行项目的迁移成本远超收益
- 判断：**大炮打蚊子**

## Decision

**采用方案 B。**

### 落地方式

**第一步（S2）：只做类型生成，不动页面**

```
1. 后端引入 swag，补 general API info
2. 按模块补注解（先 article / comment / user 三个高频模块）
3. make openapi（在 backend/）      → 生成 backend/openapi.json
4. 每个前端各自 make gen-api        → 生成 src/api/generated/api.gen.ts
5. 前端先只在一个页面试用生成类型
```

**第二步（S5）：替换全部手写类型**

```
- frontend/app/types/api.ts        (736 行)  → 删除
- frontend_admin/app/types/**     (269 行)  → 删除
```

### CI 校验（关键）

```bash
# 生成产物必须与提交一致，防止有人手改 json/d.ts
( cd backend && make openapi && git diff --exit-code openapi.json )
( cd frontend       && make gen-api && git diff --exit-code src/api/generated/ )
( cd frontend_admin && make gen-api && git diff --exit-code src/api/generated/ )
```

没有这条校验，生成产物迟早会被手工覆盖，然后再次漂移。

### 说明

**不追求"消灭所有手写类型"**。以下仍然手写：
- 纯前端状态类型（`ThemeMode`、UI 组件 props）
- 后端未暴露的内部结构

目标是：**凡是跨网络传输的类型，都必须来自生成**。

## Consequences

### 变好的

- **漂移在编译期暴露**：后端改字段名，前端 `tsc` 直接报错
- **删除 1,005 行手写 interface**
- **openapi 从文档负债变成有用资产**：可生成 Mock Server、Postman collection、第三方 SDK
- **前端 `as any` 可以清理**（类型可信后不需要到处兜底）
- **契约测试有据可依**：可以用生成的 schema 校验响应

### 变差的

- **一次性补 118 个 operation 的注解**，是实打实的工作量
- **生成产物入库**，PR 会多出 diff 噪音
- **swag 的局限**：泛型响应（如 `List[T]`）需要手工模板或改用 `oapi-codegen`
- **构建多两步**（`make openapi` + 各前端 `make gen-api`），需要在 `backend/Makefile` 与各前端 `package.json` script 里编排

### 需要跟进的

- 若 `swag` 无法表达泛型响应，改用 `github.com/oapi-codegen/oapi-codegen` 或手写 `$ref` 补充
- 生成产物放 `frontend/src/api/generated/`（及 `frontend_admin` 同名目录），与手写类型分目录，避免被误改
- 前端 lint 加规则：禁止从 `generated/` 之外 import API 类型

## 验证

```bash
# 1. 契约可复现
( cd backend && make openapi && git diff --exit-code openapi.json )
( cd frontend && make gen-api && git diff --exit-code src/api/generated/ )

# 2. 前端无手写 API 类型
! test -f frontend/app/types/api.ts
grep -rn "interface.*Response" frontend/app/ | grep -v generated | wc -l   # 期望 0

# 3. 漂移能被发现（故意改后端字段名，前端应编译失败）
sed -i 's/DiggCount/LikeCount/' backend/models/article_model.go
( cd frontend && pnpm typecheck )   # 期望失败
git checkout backend/models/article_model.go
```
