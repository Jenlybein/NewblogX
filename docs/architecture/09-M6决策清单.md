## 1. 决策一（最大）：`models/` 删到什么程度？

### 现状

| 包 | 引用文件数 | 说明 |
| --- | --- | --- |
| `models/ctype` | **125** | `ctype.ID` 全站通用的 ID 类型 |
| `models/enum`（含 4 个子包） | **36** | 角色、文章状态、可见性、消息类型等 |
| `models`（顶层 row 结构） | **25**（非测试） | 见下 |

顶层 `models` 的 25 个引用点分布：

```
internal/platform/cdc/imageref      5   ES 图片引用投影（读写 ImageRefModel/ImageModel）
internal/platform/es/articlesync    3   构建 ES 文档（用完整 ArticleModel）
internal/platform/cdc/river         2   binlog → 事件
internal/platform/cdc/deadletter    2   死信表
internal/platform/readmodel         2   评论/用户快照投影
internal/platform/{es,config,cdc/outboxrelay}  各 1
app                                 2   装配层
cmd/cli                             3   建库 / ES 索引 / 建用户
testkit + testutil + archcheck      3   测试与规则自身
```

### 为什么这不是"把结构体搬进各模块 adapter"就能了事

文档原口径是"row 结构应放本模块 adapter"。但**剩下的引用几乎都不在业务模块里**，而在 `internal/platform/`：

- `imageref` / `articlesync` 是**平台级投影**，它们读的是全库的表（article / image / banner / favorite / user）。
  把它们塞进某个业务模块的 adapter，等于让 `article` 模块替平台持有 `image_models` 的 row —— 更糟。
- `ArticleModel` 上还挂着 `Mapping()/Index()/Pipeline()` 三个方法，指向 `models/es_settings/*.json`
  （`go:embed` 的 ES mapping 与 pipeline）。删 models 必须把这几个 JSON 与索引名逻辑一起搬走。
- `cmd/cli` 的 `flag_db.go` 用 `models` 做 AutoMigrate（本地建库），`flag_es.go` 用 `ArticleModel` 建文档。

### 三个选项

| | A. 只搬 row | B. row + ctype/enum 全迁（**推荐**） | C. B + 换强类型 ID |
| --- | --- | --- | --- |
| 做什么 | 25 处 row 迁到使用者自持，`models/ctype`、`models/enum` 原地不动 | 在 A 之上把 ctype/enum 迁到 `internal/kernel/{ctype,enum}`，改 161 个文件的 import | 在 B 之上把 `ctype.ID` 换成各域自有 ID（`article.ID` 等），跨层显式转换 |
| `models/` 目录 | **仍然存在** | 消失 | 消失 |
| 解决什么 | 消除"一个共享 models 包" | 彻底消除共享 models，且 `ctype`/`enum` 站到"kernel 共享类型"的正确位置上 | 顺带消除"全站共用一个 ID 类型"，让域边界在类型层面成立 |
| 改动面 | ~25 文件 | ~161 文件的 import 行（机械替换，`ctype.ID` → `kernel.ID` 之类） | 预估 **500+ 处**，因为每个 row/domain/adapter/DTO 都要跟着换 |
| 风险 | 低 | 低（纯改 import，编译器全程兜底） | 中高：JSON 序列化、`uint64` 转换、零值语义都要逐个确认 |
| 验收 | `archcheck --error` 全绿 | 同上 + `models/` 目录不存在 | 同上 + 无 `ctype` 字样 |

**推荐 B，C 单独排期。** 理由：B 的收益是"架构上真的没有共享 models 了"，成本是机械替换，编译器兜底、可分批提交。C 属于"类型系统洁癖"，500+ 处的收益是"更漂亮"，但它会把 M6 拖成 M7，而且和 L6–L9 没有关系。如果坚持"理想化、不考虑成本"，C 可以做，但要接受它是独立的一大块。

### 附带必须做的一件事：列名契约

零 DDL 约束下，MySQL 的列名是**权威**（ES 投影按 binlog 列名解析）。搬 row 结构体时改一个字段名 = 改列名 = 投影静默错位，而所有测试都可能照样绿。

建议加一个 `testkit` 级契约测试：用 `information_schema.columns` 读出真实列，与 row 结构体经 `gorm` schema 解析出的列做逐列比对，不一致即失败。**这是唯一能挡住"重构改了列名但测试全绿"的手段**，成本约半天。

## 2. 决策二：平台投影的 row 结构放哪？

这是决策一的子问题，但它决定 M6 之后 `internal/platform/` 长什么样。

| | A. 各包自持（**推荐**） | B. 统一 `platform/projection/rows` | C. 建 `platform/schema` |
| --- | --- | --- | --- |
| 做法 | `imageref` 自己定义 `imageRefRow`/`imageRow`；`articlesync` 自己定义 `articleRow` | 所有投影共用一个行结构包 | 把 `models` 整体改名搬过去 |
| 解决什么 | row 归属于**使用它的** adapter，符合项目既定口径 | 避免同一张表出现两份定义 | 迁移成本最低 |
| 代价 | 同一张表可能有两份 row 定义（如 article 在 articlesync 与 river 各一份） | 又造出一个"共享 row 包"，只是改了名字；依赖方向仍然是从平台各处指向它 | 等于**没删 models**，只改了个名，R10 的存在意义被掏空 |
| 风险 | 重复定义可能漂移 → 靠决策一的列名契约测试兜底 | 会慢慢长出第二个 `models` | — |

**推荐 A + 列名契约测试。** C 是典型的"假重构"（目录变了，问题原样保留），不推荐。

## 3. 决策三：`router/`（1298 行 / 17 文件）怎么收？

`common/res`（400 行，29 个文件在用）的处理没有争议：搬 `internal/platform/http/res`。这里只需要决定 **router**。

现状：`router/` 只被 `app/*_wiring.go` 引用（是纯装配目标，没有反向依赖），17 个文件按模块分。

| | A. 目录平移到 `platform/http/router`（**推荐**） | B. 路由注册下放到各模块 adapter |
| --- | --- | --- |
| 做法 | 整目录搬家，改 import | 每个 http adapter 导出 `Register(g, auth)`，`router` 包消失，`app` 里逐个调 |
| 解决什么 | 满足"删旧目录"，且承认"路由表是装配层"这个事实 | 模块自洽：一个模块的路由前缀、中间件、鉴权规则都归自己 |
| 代价 | `router` 仍然认识所有模块（它本来就是组装点） | 17 个文件要改；跨模块中间件顺序、`/api` 分组要在 app 里重新理；`sitemsg_router_test.go`（385 行）等测试要跟着搬 |
| 风险 | 低 | 中：路由顺序/中间件挂载点错了，表现是"某些接口 401 或 404"，只有 e2e 能发现 |

**推荐 A。** "router 认识所有模块"不是缺陷 —— composition root 本来就该认识所有人。B 的收益是概念纯度，代价是引入一类只有 e2e 能发现的错误，而当前 e2e 覆盖并不完整。

## 4. 决策四：`write.vue`（2045 行）拆到什么程度？

结构：`script` 38 KB / `template` 12.5 KB / `style` 15 KB。目标 S5.6 是"主文件 <200 行"。

| | A. 拆子组件 + composable（**推荐**） | B. 顺便换编辑器重写 | C. 只抽 composable |
| --- | --- | --- | --- |
| 做法 | 拆成编辑器/工具栏/元信息（标题、标签、分类、封面）/发布与审核/草稿恢复 等 5–7 个组件 + 3–4 个 composable，交互不变 | 换掉现在的 markdown 编辑器（新依赖、新交互） | 逻辑抽走，模板仍在一个文件 |
| 解决什么 | 行数达标，且以后改这块不再"动一个 bug 撞三个" | 顺带解决编辑器本身的陈旧问题 | 只解决"逻辑难测" |
| 代价 | 纯搬运，无新依赖 | 需要重新对齐全部交互（快捷键、选区 AI、预览滚动同步、粘贴图片），工作量和回归风险都是 A 的数倍 | **行数降不到 200，验收过不了** |
| 风险 | 中（视图回归，靠 vitest + 手点） | 高 | 低但无效 |

**推荐 A，并且先补一层安全网**：现在 `frontend/test/` 已有 components / composables / stores 的 vitest 用例，但**写作页一个都没有**。建议先给"草稿保存/恢复""发布前校验""标签选择"这三个纯逻辑补 composable 测试，再动模板。

## 5. 顺带要定的一个小决策：日志 `event_id` 用什么

`internal/platform/log/writer/log_base.go:54` 现在每条日志调 `idgen.Next()`（雪花）。07 文档 L4 的诊断是"日志路径依赖 ID 服务，高并发下争用、故障时整条链路退化"。CH 里 `event_id` 是 `UInt64` 且被用作去重键。

| | A. 时间戳 + 进程内单调计数（**推荐**） | B. 随机 uint64 | C. 保留雪花 |
| --- | --- | --- | --- |
| 唯一性 | 单进程严格单调；多实例靠"起点注入实例号"错开 | 概率唯一，碰撞概率可忽略但无法证明 | 全局唯一 |
| 成本 | 零依赖，几十行 | 零依赖 | 现状 |
| 风险 | 多实例需正确注入实例号，否则会撞 | CH 合并期若真撞会丢行 | 日志路径仍与 ID 服务耦合（正是要解的） |

**推荐 A**，实施时把实例号从已有的 `System.ServerID` 取（配置里已有），不需要新配置项。

## 7. 需要你确认的一个口径理解

"零 DDL 硬约束"我理解的范围是：**不能改/删既有 MySQL 表的列**（因为 ES 投影按 binlog 列名解析）。
ClickHouse 的日志表不在这个约束内（L.8 的 TTL / CODEC 就是 `ALTER TABLE`，且 `01-logs.sql` 里已经写了
`TTL ... INTERVAL 120 DAY` 与 `CODEC(ZSTD(9))`）。

如果你的理解是"任何 ALTER 都不许"，那 L.8 就只能改初始化脚本、不能对已上线的 CH 库执行 —— 请明确一下。
