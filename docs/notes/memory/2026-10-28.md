## 教训
- **不要 import 第三方库的内部构建产物**(尤其带哈希的 chunk 名):会把构建钉死在一个
  精确版本,违背 semver,升级即炸,而且 lint/typecheck 抓不到,只有 bundle 时才暴露。
- 需要"按需/白名单"时,优先公开 API + 动态 import(code-splitting),别抠内部 chunk。

## ES 容器无限重启的根因与修复(2026-10-28 部署中)
- 现象:`es` 一直 unhealthy、`Restarts=165`;日志 `AccessDeniedException
  /usr/share/elasticsearch/data/nodes`;`blogx_server` 跟着报 `dial tcp ...:9200 connection refused`。
- 根因:**bind mount 打破"镜像自带属主"这个隐式前提**。ES 镜像无 USER 指令(root 启动),
  entrypoint 用 `chroot --userspec=1000:0` 降权;镜像 Dockerfile 里 `chown -R 1000:0
  /usr/share/elasticsearch`,并声明 `VOLUME .../data` —— 用 named volume 时 docker 会把
  镜像内目录**内容和属主一起**复制进卷,属主天然正确;换成 bind mount 就是宿主机目录
  **原样透传**,首次 `up` 由 docker 创建成 `root:root`,uid 1000 写不进去。
- 正解:**官方 entrypoint 早就留了开关** —— `TAKE_FILE_OWNERSHIP` 非空时执行
  `chown -R 1000:0 /usr/share/elasticsearch/{data,logs}`(注释原文 "mutate the ownership
  of bind-mounts")。两份 compose 的 es 服务各加一行即可,不改 entrypoint。
  注意判定是「非空」不是「等于 true」,写 `'false'` 照样生效,想关只能删整行。
- 曾走过弯路:自己写 entrypoint 覆盖成 `sh -c "chown ...; exec docker-entrypoint.sh eswrapper"`。
  两个问题:①**丢掉 tini**(真 ENTRYPOINT 是 `["/bin/tini","--","/usr/local/bin/docker-entrypoint.sh"]`,
  PID 1 的信号转发与僵尸回收靠它);②属主写成 `elasticsearch:elasticsearch`(1000:1000),
  与镜像自身的 1000:0 + umask 0002 约定不一致。已回退。
- 手工止血(chown 1000:1000)只是巧合生效(部署用户 uid 恰好 1000),`rm -rf deploy/state`
  或换机器即复发 → 属"止血"不属"修复",不能写进文档当方案。
- 判据(以后所有服务同理):**先查上游 entrypoint/文档有没有留开关,再考虑自己包一层**。
  自己包 = 接管了上游的启动流程,以后升级镜像要重新对齐一遍。

## ES 索引定义 + 看门狗(2026-10-28 晚,提交 8b14959 / 9ec2a89)
- `article_mapping.json`:`settings` 加 `auto_expand_replicas: "0-1"`(单节点→0 可到
  green,多节点→1 自动有副本,比写死 0/1 都正确);删掉 `created_at/updated_at` 的
  `null_value: "null"`(date 类型不接受 "null",ES7 只打 DEPRECATION 后忽略 = 从没生效,
  ES8 直接建不出索引)。mapping 是 //go:embed 静态 JSON 不能写注释 → 约定记在 `rows.go`
  的 embed 指令上方。
- **EnsureIndex 只在索引不存在时创建,存在即 return nil** → mapping 改动只影响新建索引,
  线上已存在索引必须单独 `PUT /article_index/_settings`。**服务启动路径里没有任何索引
  存在性检查**;索引若丢失,ES `auto_create_index` 会建裸索引(无 IK、无 pipeline、
  动态 mapping),而 /health 一直 200、探针一直 healthy,唯一症状是搜不到文章。
- `deploy/docker/api/es-watch.sh`(新增):entrypoint 在 exec 前 `&` 拉起,60s 采样
  `_cluster/health` + JVM uptime,只在变化时写 `[es-watch]` 行。**uptime 变小是唯一可靠的
  "重启过"信号**(重启落在两次采样之间也能发现)。判据是 `depends_on: service_healthy`
  只是启动瞬间快照——实测 compose 报 es Healthy 后 6s 后端就连不上 9200。
- `wait_for_es` 的 wget 补 `-T 15`(看门狗 `-T 10`):端口拒绝会立刻失败,但"接受连接却不
  响应"(GC 卡死/磁盘挂起)无超时会永久挂住,容器永远起不来。
- 验证手法:用**假 wget**(按 URL 返回预置 JSON + 计数器模拟第 3 次不可达、第 9 次 uptime
  倒退)实跑整个循环,比只读代码可靠。
