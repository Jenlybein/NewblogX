## 先说最重要的一句

**这 12 篇里，评分报告反复说的「代码示例已省略」「代码缺失」不是真的缺。**

评分器在打分前会把正文里所有 ` ``` ` 代码块替换成「代码示例已省略」再交给模型
（`backend/internal/ai/scoring/ai_scoring_chunk.go:20`）：

```go
cleaned := fencedCodeRegexp.ReplaceAllString(content, "\n代码示例已省略\n")
```

这个设计本意是「别让代码噪音影响语言质量评分」，但**教程类文章的主体就是代码**。
抽走代码后模型看到的是「只有骨架没有血肉」的提纲，于是 `completeness` 集体掉到
26–48，全部卡在 50 的下限外。

我核对过数据库：这 12 篇入库后代码块**完好无损**（10–54 个代码围栏），读者打开看到的是完整文章。

所以：**不要照着评分报告的「请补回代码示例」去改**——代码本来就在，你会白干一遍。
下面把 AI 的建议分成「评分器失真，直接忽略」和「真实可改」两类。

## 一、可以直接忽略的建议（评分器失真）

以下三类在 12 篇里反复出现，全部**不需要改**：

| AI 的说法 | 真相 |
| --- | --- |
| 「全文 N 处代码示例已省略，教程主体被掏空」 | 代码块在库里完好，只是评分时被临时替换掉了 |
| 「图 1 到图 4 只有引用与图题，没有实际内容」 | 图是内联 SVG，在正文里正常渲染；评分器只读纯文本，看不到 SVG |
| 「正文中多处 HTML 实体（`&#34;`、`&gt;`、`&amp;`）未转义，显示为乱码」 | 那是 SVG 内部的 `&#39;`（单引号）正常转义，在页面上显示为引号，不是乱码 |
| 「表格被压平成一串连续文字，读者无法对应」 | 表格在页面上是正常表格；评分器用 `MdToPlainText` 把结构压平了 |

**判断方法**：如果一条建议的核心是「这里缺东西」，先打开文章页确认——大概率东西都在。

## 三、根因不在文章，在评分口径

12 篇的 `completeness` 分布：26、32、35、36、38、40、42、45、45、46、46、48 —— 全部低于 50，
而其余五个维度大多在 55–80。这个形态本身就是「代码被抽走」的指纹。

同类文章（第一批的 TypeScript / JavaScript / 前端基础 50 篇）也走同一个评分器，
但它们的正文密度更高、代码占比更低，抽掉代码后仍然过得去。这批 Webpack / Golang
笔记的代码占比平均 24.3%（通过篇是 15.2%），所以更吃亏。

可选的处置（都属于运营口径，需要你决定，我没有擅自改）：

1. **调整评分器**：让评分器保留代码块的**结构信号**（例如替换成「[代码块 N 行]」而不是
   一句「已省略」），这样模型知道「这里有 40 行代码」而不是「这里什么都没有」。
   这是我认为最正确的修法，但要改代码走 PR。
2. **给教程类调低 `completeness` 下限**：在 `skills/scoring/SKILL.md` 里写明
   「代码块不计入完整性扣分」。改配置即可，不用发版。
3. **文章侧补文字**：在代码块前后各加一两句说明（「这段做 X，注意 Y」），
   提高正文密度。这是唯一不改系统就能过的路，但 12 篇工作量不小。
