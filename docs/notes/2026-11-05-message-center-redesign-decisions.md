## 决策树

> 每行 = **结论** + 一行理由 / 依据；按主题分组，编号即会话里的 Q 号。

### A. 文案清理（Q1、Q2、Q3、Q5、Q9、Q10、Q14、Q31）

- **Q1**｜**结论**：删除消息中心 / 私信 UI 里**全部**面向用户的实现细节提示。 —— 依据：读者看到的是消息，不是通道、草稿、上传或落库流程。
- **Q2**｜**结论**：删「预备会话」badge 与「首条消息发出后才会创建真实会话并拉取历史记录。」「这个预备会话只保存在前端，首条消息发出前不会请求后端。」；且「预备会话」**不是第二个领域概念**，GLOSSARY 只留「会话」、内部仍叫 draft session，该词从全部用户可见文案消失。 —— 依据：术语的单一权威不因界面占位而分叉。
- **Q3**｜**结论**：删「当前会话会自动拉取历史消息，并尝试连接实时推送。」「文本与 Markdown 走草稿框，图片会先上传到对象存储再发出。」「HTTP 收发与落库，WebSocket 只推新消息与已读通知。」。 —— 依据：双通道、上传顺序与草稿形态不属于用户文案。
- **Q5**｜**结论**：删「这个会话还没有消息」「先发出第一条消息，这里就会切换成真实会话。」；空会话**完全空白**（无图标、无文字、无卡片）。 —— 依据：空态不需要解释自己。
- **Q9**｜**结论**：删「选中左侧会话后才能查看或发送消息。」「从左侧选择一个联系人后，这里会展示消息历史与实时状态。」；未选中会话时右栏留白。 —— 依据：右栏不该描述自己的状态机。
- **Q10**｜**结论**：删「可以发一段文本、一张图片，或切到 Markdown 发送富文本。」「输入 Markdown，支持标题、列表、代码块…」「发送第一条消息后开始对话」（`last_msg_content` 数据字段）与另外四个 tab 的「按时间倒序排列。」；placeholder 简化为「输入消息…」。 —— 依据：数据字段、格式说明与排序方向都不进文案。
- **Q14**｜**结论**：删页面级说明副标「评论、互动、系统与全局通知，以及私信会话都聚合在这里。」；页面标题「消息中心」与五个子项标签 / 路由保持不变。 —— 依据：五个 tab 自己说明自己，标题不重复一遍信息架构。
- **Q31**｜**结论**：保留加载态反馈（「正在拉取消息记录…」等）但去掉「实时状态」一类实现词；失败态 = 短错误 + 「重试」按钮；连接 pill「实时已连接」在 `connected` 时**隐藏**，仅在 `idle` / `connecting` / `error` 或 `socketError` 非空时低调渲染并带「重连」，恢复后自动消失；不用 toast / 全局横幅。 —— 依据：健康状态不该占用注意力，异常才提示。

### B. 视觉重构（Q4、Q11、Q12、Q20b、Q36、Q37）

- **Q4**｜**结论**：五个 tab **全部可重设计**，信息架构**可以改**。 —— 依据：问题在骨架与阅读顺序，不在逐条文案。
- **Q11**｜**结论**：新骨架 = **顶部**分段导航 tab bar（带未读数）+ **一张共享内容卡**；私信在卡内仍是「会话列表 + 消息区」两栏。 —— 依据：五个子项共用一张卡，而不是五套页面外壳。
- **Q12**｜**结论**：移除页内 220px 左竖子导航；AppHeader 的悬浮面板留在顶栏原位、继续读同一份 `messageCenterNavItems` 表。 —— 依据：导航表只留一份，位置随容器而变。
- **Q20b**｜**结论**：设计门禁断言**更新成新事实**（顶部导航 + 单卡），canary 与不变量全部保留：不新增颜色、只用 5 档圆角、亮 / 暗对比度、`ssr:false`、路由与语义不变。 —— 依据：门禁要钉住新事实，而不是继续断言旧 DOM。
- **Q36**｜**结论**：视觉语言 = 克制的暖白分层（留白、细线、选中态、头像）；自己气泡为深墨面 + 浅字、对方气泡落 `--color-surface`；不加重边框；会话选中 = 细左条 + 轻微抬升；输入区 = 紧凑悬浮条；日期分隔 = 极细居中线。 —— 依据：层次靠留白与细线，不靠边框。
- **Q37**｜**结论**：现有 `--color-*` / 5 档 `--radius-*` / `--motion-*` token 与暗色全部保留；不新增颜色、不引新 UI 库、不写裸 hex / rgba，WCAG 对比度门禁保持绿；五条 tab URL 与语义不变，`/messages/**` 的 `ssr:false` 渲染边界不变；AppHeader 悬浮面板共用同一视觉语言但保持位置与尺寸；面板动效 = 120ms 淡入 + 小位移（`--motion-fast` / `--motion-ease`），`prefers-reduced-motion` 下禁用。 —— 依据：视觉改造不得改 token 系统与设计门禁。

### C. 排序（Q8、Q13、Q15）

- **Q8**｜**结论**：确认根因 = 后端 `ORDER BY send_time DESC`（最新在前）+ 前端原样渲染、既不反转也不排序，所以后发的消息显示在上面。 —— 依据：两处代码证据见「已确认根因」。
- **Q13**｜**结论**：后端只加 `id` 作**确定性并列 tiebreaker**（不是时序），DESC 契约保留；前端维护**唯一升序数组**（最新在底部）：首页反转、旧页反转后前插；**绝不按 id 单独排序**。 —— 依据：`send_time datetime(3)` 会同毫秒并列，而 client-key 消息的 FNV hash ID 落在 `[2^62,2^63)`、本身不递增。
- **Q15**｜**结论**：日期分组 = 自然日居中分隔（今天 / 昨天 / 日期）；同一发送人、同一天、2 分钟内的连续消息合并成一组（组头才出头像与时间、组内收紧间距），悬停任意气泡显示完整时间戳；**只有私信**这样，其余四 tab 保持最新在前。 —— 依据：聊天自下往上读、通知自上往下读，顺序需求相反。

### D. 已读语义（Q7、Q16、Q17、Q23、Q24、Q27、Q28）

- **Q7**｜**结论**：进入会话即把**整个会话**标已读（不是只标已加载的 7 条），会话 badge 与消息中心 badge 立即清零。 —— 依据：只标 7 条时更早的未读还在，红点不会消失。
- **Q16**｜**结论**：自己发的消息只在**最后一条**保留极小的「已送达 / 已读」。 —— 依据：逐条回执是噪音，一条足够。
- **Q17**｜**结论**：已读失败静默重试一次、不弹错误提示。 —— 依据：已读不是用户主动动作，失败不该打扰。
- **Q23**｜**结论**：另外**四个 tab 也改成「进入即已读」**：首页加载成功后按当前 tab 的分组批量标记（复用既有 `POST /api/sitemsg {t}` 与 `POST /api/global_notif/read`，**不新增端点**），清行未读 + badge；保留「全部已读」按钮作手动兜底；幂等、失败静默重试一次、无提示。 —— 依据：五个子项的已读语义必须一致。
- **Q24**｜**结论**：四个通知 tab 的列表**仍不订阅 WS、也不轮询**，记为已知边界、本批不改。 —— 依据：列表实时性不在本批范围，别把批次扩成实时改造。
- **Q27**｜**结论**：修根因 —— 后端已读请求 DTO 从 `[]uint64` 改成 `[]ctype.ID`（**绝不转成 JS number**，ID 超过 `2^53`），重生成 swagger 与两端 `openapi.d.ts`，停止吞掉错误。 —— 依据：string ID 撞 `[]uint64` 得到 Gin 400/1001，被 `.catch(() => undefined)` 吞掉后 `is_read` / badge 一直陈旧。
- **Q28**｜**结论**：已读接口扩展 `session_id` 模式，一次标记全部符合条件的行（receiver = 我、`msg_status < read`、清除水位之上），`msg_id_list` 保留兼容；成功后同时 `refreshSummary()` 与 `loadChatSessions()`。 —— 依据：整会话已读要一次写、两处 badge 一起刷。

### E. 分页（Q6、Q6b、Q6c、Q18、Q19）

- **Q6**｜**结论**：进入会话加载**最新 7 条**并滚到底；上滚到顶再加载 **7 条更旧的**，用 `scrollHeight` 差值锚点保住阅读位置；全部加载完只显示一次「没有更早的消息」。 —— 依据：聊天按时间正序、从下往上读历史。
- **Q6b**｜**结论**：新消息追加到底部，且**仅当用户本来就在底部时**自动跟随（读历史时不把视图拽回）。 —— 依据：不能抢走用户正在看的位置。
- **Q6c**｜**结论**：后端改复合游标 `(before_send_time, before_id)`，条件 `WHERE (send_time < ? OR (send_time = ? AND id < ?))`，取 7+1 算 `has_more`，响应返回 `has_more` + `next_cursor`；**不再用 offset**。 —— 依据：上翻期间新消息落库会让 `LIMIT/OFFSET` 之后的每一行整体错位。
- **Q18**｜**结论**：前端只维护一个升序数组，WS 通知**增量 append** 而不是整表替换已积累列表，`requestId` 防陈旧响应覆盖。 —— 依据：整表替换会丢掉已经翻上来的历史页。
- **Q19**｜**结论**：四个通知 tab 保留各自 **20 / 页 + 滚到底加载更多**（方向随阅读习惯：私信从下往上、通知从上往下）；只统一视觉与骨架，**不动分页代码、不抽共享分页 composable**。 —— 依据：两类列表方向本就相反，共用只会把逻辑耦在一起。

### F. 清除水位（Q21）

- **Q21**｜**结论**：`clear_before_msg_id` 的 `id > ?` 换成**基于 `send_time` 的时间水位**，消息过滤与未读对账公式同步改，并补测试；**本批就修，不留后续票**。 —— 依据：hash ID 非单调，按 id 过滤会破坏 #266「清空会话 → 未读不复活」的并账口径。

### G. 顶栏 AppHeader（Q20、Q31–Q40；Q31 见 A 组，Q36 / Q37 见 B 组）

- **Q20**｜**结论**：AppHeader 仍是默认布局挂在**每一页**的全站顶栏（logo、首页 / 搜索 / 合集 / 项目、搜索、创作 / 消息 / 历史、头像）；「消息」悬浮面板与消息中心页共用同一份 `messageCenterNavItems`。 —— 依据：导航表只有一份，避免两处漂移。
- **Q32**｜**结论**：创作 / 消息 / 历史**三个按钮共用一个类**，固定 min-width、同一套 padding / gap / 字号 / 高度 / 圆角，全部显示文字标签；创作收窄到等宽。 —— 依据：宽度差异只来自 `.site-header__write` 在 ≥640px 多出的 padding。
- **Q33**｜**结论**：悬浮面板只列既有五个子项 + 未读数，**不做内容预览**。 —— 依据：它是导航，不是收件箱。
- **Q34**｜**结论**：点子项立即跳到对应 `/messages/{tab}` 并关闭面板。 —— 依据：一次点击就该完成导航。
- **Q35**｜**结论**：200ms 离开宽限 + 重入即取消 + 透明桥，鼠标**可以进入面板**。 —— 依据：`top: calc(100% + 0.375rem)` 留下的 6px 透明缝让外层 `@pointerleave` 在跨越时先触发，是面板消失的根因。
- **Q38**｜**结论**：完整键盘 / 触控支持：`aria-expanded` / `aria-haspopup`、`role=menu` / `menuitem`、Tab 与方向键、Esc 关闭并把焦点送回触发按钮、focus-out 关闭、触控点按打开。 —— 依据：悬浮面板不能只有鼠标一条路径。
- **Q39**｜**结论**：面板动效沿用 B 组的低调淡入 + 小位移，不新增动效档位。 —— 依据：动效预算与 `prefers-reduced-motion` 已在 Q37 定案。
- **Q40**｜**结论**：**优先复用既有 popover / dropdown 组件**，不合适才手写，**不引新依赖**。 —— 依据：与「不新增 UI 库」一致，也少一份要维护的交互代码。

### H. 文档、交付与验收（Q22、Q25、Q26、Q29、Q30、Q41）

- **Q22**｜**结论**：只写**一条 ADR（0027）**，覆盖难以逆向的契约改动（排序口径 + 复合游标 + 整会话已读）以及「id 不是时钟」「offset 不安全」的理由。 —— 依据：契约改错要前后端一起回滚，文案 / 视觉类可逆向改动不进 ADR。
- **Q25**｜**结论**：文档动作 = 新 ADR-0027 + ADR-0022 文末「后续修订」+ GLOSSARY 只补**一句概念性**说明 + 本决策日志 + 发布说明 + 两份 README 索引。 —— 依据：词汇表只放概念，取舍留在 ADR 与笔记。
- **Q26**｜**结论**：整批**一个 PR**，契约（swagger + 两端 `openapi.d.ts`）与两端前端必须同时交付。 —— 依据：拆开会让中间态 CI 红。
- **Q29**｜**结论**：部署**之前**先在本地 dev server 出截图给用户过目：亮 / 暗、顶部导航、空白会话、7 条消息窗口、日期分组、异常连接 pill。 —— 依据：视觉类改动沿用「先截图核对、效果对了再走」的既有习惯。
- **Q30**｜**结论**：生产**串行**部署 backend → 按需 `-db`（**本批无新表，不需要**）→ `blogx_web` → `blogx_admin` → nginx；本批无新表、无 ALTER。 —— 依据：契约先行、前端随后，顺序错会让旧前端吃到新响应。
- **Q41**｜**结论**：用**两个浏览器（其中一个无痕）**跑验收清单。 —— 依据：自己收不到自己发的通知，整会话已读与红点清零必须有两个账号才能验。

## 已确认根因

1. **顺序倒置**：`backend/internal/chat/adapter/mysql/chat.go:364` 以 `ORDER BY send_time desc` 返回，`frontend/app/composables/useInboxCenter.ts:185` 把 `payload.list` **原样赋值**、不 reverse 也不 sort → 后发的消息显示在前一条上方；`send_time datetime(3)` 的同毫秒并列不确定，client-key 消息的 FNV hash ID 落在 `[2^62,2^63)`、不是时序（[ADR-0022](../adr/0022-chat-dual-channel-http-write-ws-notify.md) 决策 4），所以 `id` 永远不能当时钟。
2. **已读请求类型不符**：`frontend/app/services/inbox.ts:113` 按 `ctype.ID` 发 JSON 字符串 ID，`backend/internal/chat/adapter/http/handler.go:93` 的 `IDListRequest` 却绑定 `[]uint64` → Gin 400/1001 被 `.catch(() => undefined)` 吞掉 → `is_read` 与两处 badge 一直陈旧。
3. **分页无游标**：`backend/internal/chat/domain/chat.go:177` 的 `Page.Normalize()` 默认每页 10，`backend/internal/chat/adapter/mysql/chat.go:341` 是纯 `LIMIT/OFFSET`、只返回 `count` 而无 `has_more` / 游标 → 上翻读历史时任何一条新消息落库都让 offset 之后的行整体错位。

## 已知边界 / 不做

- **Q24**：四个通知 tab 的列表**不订阅 WS、不轮询**（也不做 WS 列表刷新），本批不改；只统一视觉与骨架，不改分页代码。
- **零 DDL**：本批**不新增表、不给既有表加列、不做 ALTER**；部署序列里的 `-db` 仅在确有需要时执行，本批不需要。
- **不抽共享分页 composable**：四个 tab 保留各自 20 / 页 + 向下滚动加载更多，方向与私信相反。
- **不新增 UI 库 / 新颜色 / 裸色值**：`--color-*`、5 档 `--radius-*`、`--motion-*`、暗色、WCAG 对比度门禁与所有设计门禁 canary 全部保留；五条 tab 路由 / 语义、页面标题、「消息中心」与 `ssr:false` 渲染边界不变。
- **不做浏览器 E2E**，也不做 WS ack/retry、消息编辑 / 撤回、举报队列（沿用 ADR-0022 / ADR-0026 的非目标）；不为四个通知 tab 新开批量已读端点。
- **Q21 不是边界**：清除水位改时间口径**在本批修掉**（含消息过滤、未读对账公式与测试），不许留到后续票。

## 交付与验收

- **文档**：本决策日志 + [ADR-0027](../adr/0027-message-center-ordering-pagination-and-read-receipt.md) + [ADR-0022](../adr/0022-chat-dual-channel-http-write-ws-notify.md) 文末「后续修订（2026-11-05，消息中心重构）」+ [GLOSSARY](../../GLOSSARY.md) 一句概念性说明 + 两份 README 索引 + 发布说明。
- **一个 PR**：契约与两端前端同发（Q26），不可拆分。
- **部署前截图**：本地 dev server 的亮 / 暗、顶部导航、空白会话、7 条消息窗口、日期分组、异常连接 pill，先给用户看过再部署（Q29）。
- **串行部署**：backend → 按需 `-db`（本批无新表，跳过）→ `blogx_web` → `blogx_admin` → nginx（Q30）。
- **两浏览器（一个无痕）验收清单**：五个 tab 路由与未读数、进入即整会话已读并同时清两处 badge、上翻保位与「没有更早的消息」、新消息仅在底部时跟随、时间水位下清空会话后未读不复活、亮 / 暗对比度、面板的鼠标 / 键盘 / 触控路径（Q41）。
