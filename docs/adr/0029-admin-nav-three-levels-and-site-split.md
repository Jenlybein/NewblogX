# ADR-0029：后台菜单三级化；内容生产成链、站点配置按受影响方分组

- 状态：已接受
- 日期：2026-11-27
- 来源：后台信息架构重组（2026-11-27，票 481）· 关联 [ADR-0020](./0020-config-section-registry-and-named-sections.md)（配置段注册表与具名端点：拆段与迁移都走它）· [ADR-0032](./0032-content-filter.md)（`content_filter` 段与关键词风险）· [ADR-0033](./0033-captcha-configurable-and-redis-store.md)（验证码闸门原归 `site.login`）
- 术语：[GLOSSARY · 后台信息架构](../../GLOSSARY.md)

## 背景与问题

后台的编辑面本身就是一份信息架构：菜单怎么分组、路由怎么命名、配置段怎么切，三者讲的是不是同一个故事。上一版（2026-11-10）只解决了"一张页面塞太多卡"——把「站点」拆成四页、把「媒体运营」拆成两页，但分组逻辑照抄了旧站点段的形状，于是留下三个问题：

1. **内容生产链被拆散在三个角落**。「发布与审核」在「站点配置 → 站点」三级下，「内容过滤」平铺在「站点配置」下，「文章审核」在「审核」组里。它们其实是同一条链上的三步：**改**（词表决定文本长什么样）、**发**（发布策略、质量闸门、配额、人工审核开关）、**审**（人工队列放不放行）。管理员改完发布策略，要跨三个分组才能看到另外两半。
2. **「站点配置」按"哪段配置"分，而不是按"谁受影响"分**：登录开关、发码限流、第三方登录、验证码参数、通道凭据平铺在同一层，"改一个登录开关"要在五六个页面里找。
3. **`site.login` 是按"同一个段"而不是按"通道"聚合的**：邮件凭据在 `mail` 段、短信凭据在 `sms` 段，但它们各自的登录开关、发码限流、验证码闸门全在 `site.login`；一个通道的"能不能用、码多久过期、限流多严"因此分散在两段，后台又把它们画在两个页面。反过来，`site` 段有匿名可读端点，把这些开关留在那里等于给读者站一份"半个通道"的视图。

另外两件一并处理的事：路由与菜单语义长期不一致（页面在 `/site/*` 却属于"发布"语义）；左侧栏与内容区曾共用一个滚动容器，切页后左栏滚动位置会漂。

## 决策

### 一、菜单：内容生产成链、站点配置按受影响方分组

1. **新增一级分组「内容修改与发布」**，下辖三项：
   - **关键词过滤** → `/content/keywords`。原「站点配置 → 内容过滤」改名迁入。改名的原因是「内容过滤」与「关键词风险」并排时会混：前者是**配置**（词表 + 两层白名单），后者是**命中记录与处置**。
   - **文章发布** → `/content/publish`。原「站点配置 → 站点 → 发布与审核」。
   - **文章审核** → `/content/review`。原「审核 → 文章审核」。
   - 原位置的三项全部移除；「审核」组只留**图片审核**与**关键词风险**。

2. **「站点配置」新增两个三级父**（与既有的「站点」同构，本身无页面）：
   - **用户操作**：登录设置 `/site/login`（只剩登录失败限流与用户名密码登录开关）、私信设置 `/site/chat`、第三方登录 `/site/oauth`（含 `qq_login` 开关）；
   - **验证码与通知**：图形验证码 `/site/captcha`（渲染参数 + 总开关 + 四个入口闸门，共五个闸门）、邮件 `/site/mail`（凭据 + `email_login` / `email_register` + 码有效期与发码限流）、短信 `/site/sms`（与邮件同构：凭据 + `phone_login` + 码有效期与发码限流）。
   - 「邮件」「短信」从站点配置的原位置**移走**，唯一入口在新分组下。

3. **分组判据**：内容侧按**生产链**分（改 / 发 / 审）；站点配置按**谁受影响**分——用户操作（用户能不能登录、能不能私信）、验证码与通知（发得出去的那条通道，以及它的人机验证）、站点（站点自身的基础信息）、存储 / AI / 装饰（各是一个独立能力）；日志与右栏卡片仍平铺在「站点配置」下。

4. **三级菜单机制照旧**：分组 key 用**层级链**（`group:站点配置 / 用户操作`）而不是只取标签名——两层同名前缀共用一份展开态会在收起一层时塌掉另一层；第三层只补 `padding-left`，不重做侧栏结构。

5. **保存仍走「读-改-写」**：站点相关页面共用 `applySiteSectionPatch`（取最新整段 → 只覆盖本页拥有的顶层块 → 写回）。拆页 + 每页各自整段回写必然互相覆盖，且 `about` / `project` / `reconcile` 三块**后台没有 UI**（靠原样往返保住），任何"只提交自己那几块"的保存都会把它们清成零值。

6. **一个页面 = 一个薄壳 + 一个配置组件**，页面只 import 自己那一个 `components/settings/*` 组件（既有结构对账门禁继续生效）。

7. **「媒体运营」仍是两页**：轮播运营 `/media/banners`、图片资源库 `/media/images`，各拉各的分页；`/media` 保留为跳转页（不进菜单，但登记在跳转页白名单）。这是上一版结论，本次不动。

8. **左栏与内容区独立滚动**：shell 固定 `100vh`，两栏各自 `overflow-y: auto`；滚动行为显式只作用于内容区（`scrollBehavior`），切页后左栏滚动位置不变。

### 一·修订（2026-11-27 晚，第二版）

同一批工作里，运营把上一版的菜单又动了一次 —— 上一版把**改 / 发 / 审**三步全塞进一级分组「内容修改与发布」，实际用起来有两个问题：

1. **审核是处置，不是配置**。"改词表 → 调发布线 → 审文章"读起来像一条流水线，但前两步是"改完就生效"的配置（有事才去调），第三步是"有事才进来处理"的队列。把队列和配置放同一组，每次改完配置都会顺手看到"待审 N"，于是被当成配置的一部分去理解。
2. **发布与审核的规则混在一页**。「文章发布」一页里既有"谁能发、对谁可见"，又有"免审核 / 投稿配额 / 质量闸门"，前者是发布策略，后者是审核规则；一个页面同时回答两类问题时，找到其中一类要翻过另一类。

第二版：

- 「内容修改与发布」**降为「站点配置」下的三级分组**：**关键词过滤**（+ 新拆出的**关键词白名单**）、**文章发布**、**文章审核设置**（"发布与展示" + 标签上限这种发布约束）；
- **新增「文章审核设置」页**（`/site/article-review`）：内容审核（免审核开关）、投稿配额、质量闸门、质量达标自动放行 —— `site.article` 块的审核规则入口。它**挂在「内容修改与发布」组下**（该组第 4 项）：改词表 → 定发布线 → 定审核规则是同一条内容生产链的三步，规则跟链走比跟配置段走更符合"谁在用这一页"。路由前缀仍是 `/site`（它编辑的是 `site.article` 块）—— 菜单归属与配置段归属是两件事。命中词自动处置住在 `content_filter` 段，因此留在关键词过滤页的设置面板（一个页面只碰一个配置段）；
- **「文章审核」回到「审核」组**（`/review/article`，旧地址 `/content/review` 留跳转页）：处置队列与图片审核、关键词风险并列；
- **新增「站点界面」三级分组**：装饰与右栏卡片收进去（改外观的与改策略的分开）；
- 「文章管理」新增**评论管理**页（`/articles/comments`，见 [ADR-0035](./0036-comment-moderation.md)）。

两页共写 `site.article` 块的保存语义随之升级：块级替换升级为**字段级补丁**（`utils/siteSectionSave.ts` 的 `applySiteBlockFieldPatch`），否则后保存的那页会把兄弟页刚改的免审核开关 / 质量闸门写回旧值。

未被推翻、继续成立的部分：路由带旧地址跳转、"站点配置按受影响方分组"、"邮件 / 短信按通道拆段"、左栏独立滚动。

### 二、路由：一律带旧路由重定向

9. 三项迁移都留旧地址跳转，且是**一跳到底**：旧路由不再保有自己的页面，只做跳转（见下方「当前生效约束」的重定向清单）。不做 301——后台是 SPA，服务端没有对应路由入口。

### 三、配置段：`site.login` 按通道拆开

10. **`site.login` 的字段按通道迁出**，四段各自拥有自己那条通道的策略：`mail`（凭据 + 邮箱登录 / 注册开关 + 码有效期与发码限流）、`sms`（同构 + 手机号登录开关）、`oauth`（第三方登录开关）、`captcha`（总开关 + 四个入口闸门 + 渲染参数）。

11. **`site.login` 只留两件事**：登录失败限流、`username_pwd_login`。

12. **迁移用 CLI `-migrate-runtime-config`**：默认只读（打印将要发生什么），`-apply` 才写；迁移后**物理删除旧键，不保留任何回退读取**。
    迁移是另一个进程直写数据库，**改不到运行中进程的配置缓存** —— 所以 `-apply` 之后必须
    `docker compose restart blogx_server`。漏了这一步的现象是"库里已经搬好、接口还在按旧值
    回答"（生产实测：迁移后 `login_capabilities` 仍报 `email=false`，重启才变 `true`）。
    命令的 `-apply` 分支会打印这条提醒。

13. **新增公开只读端点 `GET /api/site/login_capabilities`**，只暴露 `login_methods` 与 `captcha_required` 两组布尔。拆段之后 `site.login` 不再含这些开关，而 `mail` / `sms` / `oauth` / `captcha` 四段**含凭据或运营参数、不能公开读**，所以补一个只含布尔的能力面给读者站（决定画不画某个登录方式、画不画验证码框）。

## 理由与已否决方案

- **这次推翻了上一版的什么**：上一版把「发布与审核」塞在「站点配置 → 站点」三级下、把「内容过滤」平铺在「站点配置」下、把「文章审核」留在「审核」组。当时的理由只有一条：发布策略住在 `site.article` 里，就跟着 `site` 段走。**推翻的理由**是这条理由站不住——菜单分组回答的是"谁在用这一页"，不是"这段配置归档在哪个 JSON 里"。发布与审核的读者是写文章的人和审文章的人，不是"配置站点的人"；`site` 段只是它们碰巧住的地方。同理，`site.login` 能放哪些字段也应由**通道**决定，而不是"它一直是 `site` 的子对象"。
- **否决「只改菜单、不改路由」**：菜单写着"内容修改与发布 → 关键词过滤"，地址却是 `/site/content-filter`，路径与菜单语义长期不一致；收藏夹、文档、`grep /site/publish` 全部指向"站点配置"，后人按路径找代码一定找错层。
- **否决「邮件 / 短信留在原位置做双入口」**：两处心智——同一个开关出现在两个页面，改完 A 页回 B 页看到旧值（或反过来覆盖），而且"哪个才是真的"没有任何界面能回答。
- **否决「闸门留在 `site.login` 不拆」**：留一半等于没拆——`captcha` 段管渲染参数、闸门在另一段，后台还得在两页之间跳；而通道凭据搬进 `mail` / `sms` 后，它们的登录开关与发码限流留在 `site.login` 就是同一类撕裂。
- **否决「拆段后让读者站继续读 `GET /api/site/site` 拿这些开关」**：`site` 段是匿名可读的整段视图，把通道开关塞进去等于把"公开读面"和"凭据所在的那几段"重新黏在一起；某天有人往 `mail` / `sms` 加字段，就会顺着公开读漏出去。
- **否决「保留旧键的只读回退」**：迁移只跑一次，回退读取会掩盖"迁移没跑"这件事；两处数据不一致时没人能判断哪个生效。宁可数据不全被立刻发现。
- **否决「两栏共用一个滚动容器」**：左栏比内容长时，滚到内容区底部会把菜单滚出视野；切页后左栏停在奇怪的位置。
- **否决「为 `/content/*` 另造一套后端端点」**：文章发布编辑的仍是 `site.article` 块，关键词过滤仍用 `content_filter` 段的具名端点。菜单分组与配置段归属是两件事，不该为了菜单形状去改契约。

## 代价 / 不做什么

- **「站点」三级下只剩「站点基础」一页**：登录与发码、发布与审核、私信都迁走了，于是出现"一个只有一页的三级分组"。这是有意的——`site` 段仍有基础信息与 SEO 一页，`about` / `project` 若将来补上编辑 UI 也落在这里；把「站点基础」提成二级反而会让"站点段还剩什么"更难回答。
- **页面所在分组与它所编辑的配置段不再是同一件事**：「文章发布」页面在「内容修改与发布」里，编辑的却是 `site.article` 块，所以它照样要走读-改-写、照样出现在 `OWNED_BLOCKS` 对账里。认知成本换来的是菜单语义正确。
- **旧路由多一跳**：三个旧地址各留一个跳转页，它们不进菜单但必须被结构对账承认。
- **迁移是一次不可逆的配置搬家**：`-apply` 之后旧键物理消失，回滚只能靠部署前对 `runtime_config_models` 的备份。
- **`login_capabilities` 是第二套公开面**：只含布尔。一旦有人往里加"通道是否配置好""限流阈值"这类信息，能力面就变成了信息面。
- **不做**：菜单项级权限（`AdminNavNode` 仍无权限字段）、后台 i18n、菜单动画、`about` / `project` / `reconcile` 的编辑 UI（仍无 UI，只原样往返）。

## 当前生效约束

1. **新路由清单**（菜单唯一来源是 `frontend_admin/app/utils/menu.ts`，每个 path 必须有真实页面文件）：
   - 内容修改与发布：`/content/keywords`、`/content/publish`、`/content/review`
   - 用户操作：`/site/login`、`/site/chat`、`/site/oauth`
   - 验证码与通知：`/site/captcha`、`/site/mail`、`/site/sms`
   - 不变：`/site`（站点基础）、`/site/storage`、`/site/ai`、`/site/log`、`/site/deco`、`/site/sidebar-cards`、`/review/images`、`/review/content-filter`、`/media/banners`、`/media/images`
2. **旧路由重定向清单**（一跳到底，不保留旧页面）：`/site/content-filter` → `/content/keywords`；`/site/publish` → `/content/publish`；`/review` → `/content/review`。
3. **`site.login` 只允许放两件事**：登录失败限流、`username_pwd_login`。任何"某条通道能不能用、验证码要不要、发码限流多严、码多久过期"的字段都属于通道段（`mail` / `sms` / `oauth` / `captcha`），不得加进 `site.login`。
4. **新开关进哪个段**的判断：问"它坏了谁会受影响"——影响能否登录 / 私信 → 用户操作相关段；影响消息发不发得出去或人机验证 → `mail` / `sms` / `captcha`；影响第三方登录 → `oauth`；只影响站点自身 → `site`；独立能力 → 各自的段。**含凭据的段一律不给公开读。**
5. **公开可读面只有三处**：`site` 段、`deco` 段、`GET /api/site/login_capabilities`（只含 `login_methods` 与 `captcha_required` 两组布尔；不得含凭据、阈值、通道配置状态）。
6. **菜单结构对账继续生效**：每个菜单 path 有页面文件、每个页面（除 `login` / `setup` 与登记过的跳转页）都有入口、path 不重复、分组 key 用层级链（不得退回只传标签名）。
7. **每页只能 import 一个** `components/settings/*` 组件；页面里不得出现 tab 容器或活动态内存变量。
8. **站点相关页保存必须调用 `applySiteSectionPatch`**，`OWNED_BLOCKS` 与 `utils/siteSettings.ts` 的声明一致；新增 / 调整归属要同时改两处与对账测试。
9. **媒体两页各自持有加载与分页状态**，不共享同一份 list 数据；`/media` 只作跳转页、只登记在 `ADMIN_REDIRECT_PAGES`。
10. **两栏独立滚动**：shell 固定 `100vh`，左栏与内容区各自 `overflow-y: auto`；滚动只对内容区生效，切换路由不得复位左栏滚动位置。
