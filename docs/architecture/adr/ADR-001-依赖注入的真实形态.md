# ADR-001：用能力接口取代 `Deps` 结构体装箱

## Status

**Proposed**（2026-10-24）— 已确认：`Deps` **直接废弃，不保留过渡态**，handler 只持有 3-5 个能力接口。

## Context

项目做过一轮"去全局化"改造，把 `global.DB` 换成了 `Deps` 结构体传递。结果：

- **32 个 `type Deps struct`，30 个含 `*gorm.DB`**
- `api.Deps`（17 字段）与 `apideps.Deps`（18 字段）**逐字相同**，只差一个 `ConfigFile`
- `app/wiring_http.go:18-37` 与 `:39-57` 在同一函数里手工抄写两遍
- 最长传递链 6 层：`Infra` → `apideps.Deps` → `api.Deps` → `article_api.Deps` → `category.Deps` → `view_history.Deps`
- `api.New` 从 `:70` 到 `:167` 逐字段展开拆出 15 个子 Deps

**问题不是"没用 DI"，而是用了一个看起来像 DI、实际是 Service Locator 的东西。**

### 为什么比裸 global 更糟

| | `global.DB` | `Deps{DB}` |
| --- | --- | --- |
| 依赖可见性 | 不可见 | **看起来可见**（有签名） |
| 实际能力 | 任取 DB | **同样任取 DB** |
| 测试替换 | 改全局变量 | 构造完整 17 字段结构体，**更难** |
| 新增依赖 | 加一个变量 | 改 6 层结构体 + 15 处展开 |
| 认知影响 | 一眼看出是坏味道 | **误以为已解决** |

最后一行是关键：它让"重构"这件事在账面上完成了。

## 备选方案

### A. 保留 Deps，只做瘦身

删掉重复的 `apideps.Deps`，把字段从 17 降到 8。

- 优点：改动小
- 缺点：治不了根本——**只要 Deps 里还有 `*gorm.DB`，任何包都能查任何表**；依赖依然不可见（8 个字段也看不出这个 handler 用哪 2 个）
- 判断：**换个尺寸的创可贴**

### B. 能力接口（推荐）

handler/service 的构造函数只接收**窄接口**，每个接口 1-3 个方法。

- 优点：
  - 依赖可见（3-5 个字段，一眼看清）
  - **能力受限**（`DiggCounter` 只有一个 `Count`，调不到 `Delete`）
  - 可测试（fake 只实现 1 个方法）
  - 拿不到 DB 连接，想写 SQL 也写不了
- 缺点：
  - 接口数量增加（12 模块 × 约 4 个端口 = 约 50 个接口）
  - 每模块多约 200 行 mapper

### C. 引入 wire / dig

- 优点：减少手写装配
- 缺点：wire 让启动流程不可读、出错提示晦涩；dig 把编译期错误推到启动期。本项目模块数 12，手写约 150 行足够
- 判断：过度

## Decision

**采用方案 B。**

### 形态

```go
// internal/article/app/port.go —— 端口由使用方定义
type Reader interface {
    FindByID(ctx context.Context, id kernel.ID) (*article.Article, error)
    ListPublished(ctx context.Context, q ListQuery) ([]article.Article, int, error)
}

type DiggCounter interface {
    CountByArticle(ctx context.Context, id kernel.ID) (int64, error)
}

// internal/article/app/service.go
type Service struct {
    reader Reader
    diggs  DiggCounter
    tx     platform.TxManager
    outbox platform.Outbox
}

func New(r Reader, d DiggCounter, tx platform.TxManager, ob platform.Outbox) *Service
```

### 配套约束

1. **`Deps` 结构体全部删除**，archcheck R3 规则禁止新增
2. **`gorm.DB` 只能出现在 `*/adapter/` 与 `platform/mysql/`**，archcheck R2 强制
3. 端口定义在**使用方**包内（`app/port.go`），不是实现方
4. 跨模块调用时，消费方定义自己需要的接口（如 `comment` 定义 `ArticleGate`），**不 import 别的模块**

### 迁移方式

不一次性删。按模块推进：
- 迁完的模块用接口
- 未迁的模块继续用 Deps
- `Deps` 字段随模块迁移逐个变空，最后整个结构体删除

这样任何时刻代码都能编译。

## Consequences

### 变好的

- **越权访问被消除**：只有 adapter 能拿到连接，其余层想查库都查不了
- **依赖图可读**：构造函数签名即依赖清单
- **可测试**：`repository/` 449 行核心 SQL 第一次可以写测试（注入 fake 或内存库）
- **测试能并行**：不再需要构造全局状态，`t.Parallel()` 可用

### 变差的

- **构造函数参数变长**（4-5 个）
- **接口数量增加**（约 50 个）
- **mapper 样板**：领域实体与持久化模型分离，每模块约 200 行转换代码
- **迁移期双轨**：接口与 Deps 并存，直到 S5

### 需要跟进的

- archcheck R1/R2/R3 必须先以 `--warn` 列出全部存量（应为 150+ 处），否则无法衡量进度
- 需要 `testkit` 提供 fake 生成辅助，否则每个模块手写 fake 成本高
