# ADR-008：死信重投（DLQ Replay）——让"同步失败"有闭环

## Status

**Accepted**（2026-10-26）

## Context

现状（证据见 [12 §7](../../architecture/12-重构收尾审查.md)）：

- 三个 CDC 子链路（`es_projection` / `outbox_relay` / `image_ref_river`；
  当时还有第四个 `es_river`，已于 2026-10-26 随通用规则路径一并删除，见 [ADR-009](./ADR-009-删除通用规则同步路径.md)）
  在重试耗尽后都会调 `deadletter.SaveBatch` 写 `cdc_dead_letter`，状态一律 `pending`；
- 但**没有任何代码把状态改成别的值**、也**没有任何代码去读它重做一次** ——
  死信表是个只进不出的黑匣子，出问题只能人工进 MySQL 翻，然后手动补数据；
- 展示端半成品更误导人：`replay_event_logs` 的**读端**（analytics `/logs/replay`）
  和写入函数 `writer.EmitReplayEvent` 都写好了，但**没有任何地方调用它**，
  表永远是空的，而且前端一个页面都没调过这两个接口。

一句话：**"失败留证据"做了，"照证据补救"没做。**

## Decision

建一套最小但完整的死信重投闭环，分四层：

```
管理端页面（列表 + 勾选重投 + 回放日志）
      ↓
POST /logs/dead-letter/replay        GET /logs/dead-letter
      ↓ 端口 domain.DeadLetterReplayer
platform/cdc/dlq.Service  ── 编排：取记录 → 分派执行器 → 更新状态 → 写回放日志
      ├── es_projection   → 按死信里的行主键重算投影文档（幂等）
      ├── image_ref_river → 删除类：重新清理该对象的图片引用
      └── outbox_relay    → 把 outbox 行从 dead 重置为 pending（交给中继自己重投）
```

### 一、状态机只用已有列，零 DDL

```
pending ──重投成功──> resolved（终态，不再参与重投）
pending ──重投失败──> pending（retry_count+1、error_code/error_msg 覆盖为本次失败）
```

**不引入 `replaying` 中间态**。理由：重投是人工、低频、单实例的管理操作；
中间态会带来"进程崩溃留下僵尸 replaying"的恢复逻辑，而它防的问题
（两人同时点同一个按钮）最坏结果是**重投两次**——而两个执行器都是幂等的
（ES 按文档 id index/delete；outbox 重置是纯状态写），重复执行无害。
**用"幂等执行器"换掉"分布式互斥"，代价低得多。**

### 二、支持范围按 payload 自洽性划定，不支持的要讲清原因

| stream | 死信 payload 里有什么 | 重投怎么做 | 支持 |
| --- | --- | --- | --- |
| `outbox_relay` | `{payload}` + `CdcJobID=outbox:<id>` | 把该 outbox 行 `dead → pending`、`attempts=0`，由中继按自己的退避重投 | ✅ |
| `es_projection` | `{schema,table,action,rowCount,ids}` | 按 `ids` 重算投影（`SyncArticleSearchProjection`），只动受影响的文档 | ✅ |
| `image_ref_river` · 删除 | `{owner_id, ref_type}` | 直接重新清理该对象的图片引用（payload 自洽，类型刚好是两个字符串/枚举） | ✅ |
| `image_ref_river` · 新增/更新 | `{table,row}` / `{table,before,after}` | `row` 是 `[]any`，JSON 往返后数字变 float64、时间变字符串，重建行快照会**静默算错**候选图 | ❌ 返回 `unsupported` + "重新保存该业务对象" |

**`es_projection` 的 payload 必须带 `ids`。** 没有主键就只能全量重建索引
（几分钟、期间新旧文档混杂）；带上主键后，重投是"重算这几篇"而不是"重建全库"。

（历史上还有一条 `es_river`：payload 是完整的 ES bulk body，原样重发。它随通用规则路径
一起删除了 —— 那条路对本文档所描述的所有表都不可达，见 [ADR-009](./ADR-009-删除通用规则同步路径.md)。
保留一条记录在这里，是因为历史死信里还能看到这个 stream 名。）

不支持的流不是"以后再说"，而是**当场告诉操作员该改用什么办法**。
`POST /replay` 对这类记录返回 `unsupported` + 一句人话，**不改数据库、不涨 `retry_count`** ——
"不支持"和"这次失败"是两件事，前者再点一百次也是同一个结果，记成失败只会诱导人反复点。

### 三、"不支持"与"失败"必须是两种结果

`deadletter.ErrUnsupported` 这个哨兵就是为这条边界存在的：

| 执行器返回 | 结果 | 状态 / retry_count | 界面 |
| --- | --- | --- | --- |
| `nil` | `success` | `resolved` | 绿色"成功" |
| `ErrSkipped` | `skipped` | 不动 | 灰色"跳过" |
| `ErrUnsupported` | `unsupported` | **不动** | 橙色"不支持重投" |
| 其它 error | `failed` | 仍 `pending`，`retry_count+1` | 红色"失败" |

### 四、回放日志：把闲置的写端接上

每次重投尝试（成功、失败、跳过、不支持）都 `writer.EmitReplayEvent` 写一条到 ClickHouse
`replay_event_logs`，字段直接取自死信记录：`cdc_job_id/stream/source_table/action/
target_key/retry_count/result`。这样：
- 管理端「回放日志」页第一次真正有数据；
- 同一条死信的"失败→重投→再失败→再重投→成功"有完整时间线（`cdc_job_id` 可串）；
- "点了没反应"也能查：跳过与不支持同样留痕。

### 五、幂等与安全边界

- **已 `resolved` 的记录不再重投**，返回 `skipped`（避免重复打 ES）。
- 更新状态用条件更新（`WHERE id=? AND status<>'resolved'`），不引入锁。
- **不自动重投**。死信可能是"代码 bug 导致必然失败"，自动重投只会把 ES 打热。
- 重投不修改死信里的 payload —— 失败证据保持原样，便于事后比对。
- 删除类（`image_ref_river`）的重投是"清掉该对象**当前**的所有引用"，不校验对象是否还在。
  **先重新保存过对象、再点旧死信，会把刚重建的引用一起删掉。** 幂等 ≠ 无害：
  这条只通过对操作口径的约束（重建过就别点旧死信）来规避。

## Consequences

**变好的：**

- 同步失败的处置从"进 MySQL 手改"变成"页面上勾选重投，结果立刻可见"。
- 死信状态有了终态，运维能区分"还没处理"和"已经补上了"。
- `replay_event_logs` 从死代码变成有数据的时间线。
- **投影失败不再拖垮整个同步**：因为死信带主键、补得回来，`OnRow` 里从
  "失败即 `cancel()`"改成"记死信 + 继续跑"。以前一篇文章投影失败会让
  MySQL→ES 同步**永久停摆**（`River.Run` 只在装配时调用一次，没有重启监督），
  而 API 照常服务、没人会知道。

**变差的 / 需要接受的：**

- 多了 2 个契约接口和 2 个管理端页面，需要维护。
- `outbox_relay` 的重投是"重置状态"而非"立即执行"，最长要等一个中继轮询周期
  （当前默认 2s 退避起步）。这是有意的：复用中继自己的重试与背压，不另开一条投递路径。
- **重投的力度是"重算"，不是"重放一行"**：改一篇文章只影响 1 篇；改一个用户昵称
  会影响他名下所有文章（几十到上百篇，见下条）。这个代价是"展示字段冗余进 ES 文档"
  换来的，在那个量级上仍然划算。
- **`es_projection` 现在可重投，但它依赖一个前提：投影与业务表在同一个库。**
  文档组装要跨 `article / user / category / tag / article_tag / user_top_article`
  六张表做应用层批量查询（不是 SQL JOIN）。**一旦拆库或拆服务，这条路径必须改成
  "订阅各服务事件 + 本地读模型"，不能靠改连接串对付过去。**
- 旧版本的 `es_projection` 死信（没有 `ids`）仍然只能全量重建，接口会明确告知。

## Alternatives

### A. 只给页面，重投仍靠人工 SQL

- 成本最低，但"看得见补不上"，等于把问题挪个地方。**否**。

### B. 自动重投（定时扫描 pending 死信重试）

- 听着省事，但死信多半是"改之前必然失败"的（字段不兼容、索引不存在）。
  自动重投会在故障期间把 ES 打出一片 400，且掩盖真实原因。**否**。
  人工触发天然带"我先看看为什么失败"这一步。

### C. 重投走消息队列（每条死信投给 MQ，由消费者慢慢重放）

- 引入新基础设施，收益是把重投变成异步可削峰；但当前死信量级（人工处理）
  完全用不上。**否，等真有量再说**。

## 执行口径

- 零 DDL：只用 `cdc_dead_letter` 已有列（`status` / `retry_count` / `error_*` / `updated_at`）。
- 新增契约接口的响应必须用 `kernel.Envelope[ListData[T]]`（后端注解引用真实 DTO）。
- 门禁：`TestContractMatchesRoutes` 会自动要求这 3 个新接口在路由表里存在。
