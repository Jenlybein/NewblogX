# ADR-0032：发布前的质量闸门——评分即闸门、失败关闭、事务外评分

- 状态：已交付
- 日期：2026-11-08
- 来源：parent spec [#302](https://github.com/Jenlybein/NewblogX/issues/302)（发布治理一期）· 落地票 [#306](https://github.com/Jenlybein/NewblogX/issues/306)（质量闸门）· 决定过程见 [grill 记录 §2.1 / §2.2 / §三](../notes/2026-11-07-publish-gate-and-moderation-grill.md)

## 背景与问题

评分原本**已经存在**，但方向相反：它是文章发布之后由事务型发件箱触发的**异步补评分**，只用于展示（"文章质量总分 82"）。投稿路径则完全没有把关——站点默认 `skip_examining: true`，提交即发布。

要变成"发布前的硬闸门"，有五个必须先回答的问题：

1. **闸门与人工审核是什么关系？** 同一条流水线的两段，还是两道独立的门？
2. **AI 不可用时怎么办？** 而 `ai.enable` 默认是 `false`——"AI 不可用"是默认状态，不是边界情况。
3. **评分调用能不能放在事务里？** 一次模型调用 5–30 秒。
4. **"分数不够"与"系统挂了"是不是同一件事？** 对作者来说，这两种失败的下一步动作完全不同。
5. **及格线与分数档名谁说了算？** 现有提示词把 31–59 叫"不合格文章"，而及格线是 50。

## 决策

1. **闸门与人工审核是两道独立的开关**，四种组合都合法；默认闸门**关闭**、人工审核维持现状。顺序固定为：配额预占 → 评分 → 分数判定 → 落库 →（可选）建审核任务 → 发事件。评分永远排在人工之前——它的价值就是把垃圾挡在人工队列之外。
2. **开启闸门这个动作本身要求 AI 可用**。总闸关闭或没有启用的模型配置时，后台保存直接失败（`article.quality_gate_requires_ai`）。把失败面从运行期挪到配置期：保存不了，这个状态就不存在。
3. **失败关闭，但失败分四类**：配额超限、系统不可用、分数不达标、合规违规，各一个错误码。前端据此给不同文案。
4. **"拿不到可用分数"才算系统失败**：网络错、超时、限流、5xx、返回非 JSON、缺总分。拿到分数（哪怕 23 分）一律算有效结论，走"不达标"。
5. **评分必须在数据库事务之外**。Create 与 Update 都先算出"这次会不会提交"，再据此在事务外评分；写事务重新读文章、以它读到的状态为准。
6. **评分温度固定为 0**，只影响评分场景，不跟随站点级 `ai.temperature`。评分是要拿去做放行判定的，需要的是可复现而不是创造性。
7. **灰带做在及格线之上**：实际放行线 = 及格线 + 灰带宽度。只有把放行线整体抬出抖动量程（±2 分），"同一篇文章今天能发、明天不能发"才不会发生；两侧各留一半等于在阈值正上方留一条窄缝，抖动照样命中。作者看到的"还差几分"按实际放行线算。
8. **及格线与四个档界都自由可配、不做交叉校验**（spec 决策 11）。允许保存"及格线 50 而 31–59 叫不合格文章"这类自相矛盾的组合；作者侧照旧显示档名，因此可能看到"不合格文章 · 55 分 · 已通过"。这是有意接受的代价。
9. **被拒的文章落草稿**（而不是"已拒绝"）：作者能继续改、能立刻重投。拒绝时带结构化数据（分数、放行线、差额、档名、问题列表），错误码仍由 apperr 一处映射。
10. **评分结果落库**（复用既有的单行 Upsert 记录）：不落库的话，同一次提交会被异步补评分再评一次，等于一次提交烧两次模型调用。
11. **article 用例层引入一个同步端口 `QualityGatePort`，打破「article app 不依赖 AI 模块」的既有格局**（票 306 验收标准 4）。

    既有约定是：article 的副作用一律走**事务型发件箱**，app 层不认识 AI、message、read 这些别的模块。闸门不适用这条——它必须**同步**给出结论：提交还没落库，评分结果决定"这次提交落不落、落成什么状态"，没有后面可以补的时机。所以第一次在 article app 上开了一个"调用别的模块"的窄口子：端口由**使用方定义**（`QualityGatePort`，一个方法），实现在 `backend/app/article_wiring.go`，跨模块的具体形状（`ScoreForGate`）只活在装配层。

    这条张力是这次改动**最容易被后人"顺手改回去"的地方**：把评分挪回 outbox 看起来更"合规"，但那样闸门就不再是闸门，退化成事后展示。因此它同时写进「当前生效约束 10」。

    反过来，合规判定（ADR-0033）仍然是异步的：它只影响"审核员的排序与标红"，不决定请求成败，所以继续走 outbox——**同一个模块里两种接法，判据是"结论要不要影响本次请求的结果"。**

    （**2026-11-09 修订**：新发布口径下模型结论会改变文章的最终可见性——`clean` 才转 `visible`，`suspect` / 判定失败则改回审核中；但它仍**不决定本次请求成败**，所以依旧走 outbox。判据没变，只是"影响请求结果"扩展为"影响最终落点"。见 [ADR-0035](./0035-risk-gated-publish.md)。）

## 理由与已否决方案

- **否决"闸门与人工审核串成一条流水线"**：两者失效模式完全不同——闸门会因 AI 额度/网络/模型不发 JSON 而失效，人工审核会因管理员不在而积压。绑死等于"AI 一挂投稿全停"或"管理员休假垃圾稿照发"。
- **否决"AI 不可用时放行"（fail-open）**：默认配置下闸门从未生效，且灌水者只要探测到"AI 一挂就全放行"就会主动去打它。
- **否决"AI 未配置就当闸门不生效"**：与失败关闭的语义自相矛盾，且会让"配置缺失"变成一条静默的旁路。
- **否决"评分留在事务内"**：一次 5–30 秒的模型调用占着事务等于钉死连接池；这是当前实现里最容易在重构时被顺手挪回去的一条。
- **否决"灰带上下各留一半"**：见决策 7，它挡不住阈值正上方的抖动。
- **否决"阈值必须锚定档界（防矛盾配置）"**：会话明确要求两者各自自由；矛盾从"作者看不到档名"处消解（该条最终也被否决，改为接受矛盾可见）。
- **否决"多次采样取中位数"**：成本是每人每天 45 次调用；抖动改由固定温度 + 灰带抑制。
- **否决"分数不落库、只实时算"**：与异步补评分路径重复计费，且作者看不到自己被拒时的分数。

## 代价 / 不做什么

- **提交会变慢 5–30 秒**：前端必须有"评分中"状态与幂等保护，否则双击会变成双份配额 + 双篇文章。
- **误判不可复盘**：不保留分数历史（#302 已定），评分误判是不可申诉的黑箱；唯一缓解是灰带与人工复核。
- **可保存自相矛盾的配置**：作者可能看到"不合格文章 · 已通过"。
- **闸门依赖 AI 可用性**：AI 额度耗尽、上游故障时，开启闸门的站点投稿会被拒（这是失败关闭的有意代价，需靠运维告警而不是静默放行）。
- **不记录"因闸门被拒几次"**：拒稿次数只有审核任务与配额计数侧面反映。
- **不做采样校准**：不做 AI 分与人工分的一致性评估，不做阈值回归调优。
- **零 DDL**：评分记录沿用既有表，不加列、不加表。

## 当前生效约束

1. **闸门默认关闭**；零值配置 = 关闭，提交路径与引入之前逐行为一致。
2. **开启闸门的保存动作必须校验 AI 可用**（总闸 + 至少一条启用模型），不满足即拒绝保存并返回 `article.quality_gate_requires_ai`。不得改成"警告后继续"。
3. **评分调用不得进入数据库事务**。新增任何"提交"路径时，评分必须发生在 `WithinTx` 之前；事务内只做落库与判定结果的写入。
4. **失败分四类错误码，不得合并**：`article.submit_quota_exceeded`、`article.score_unavailable`、`article.quality_rejected`、以及合规相关码。低分不是"失败"。
5. **评分场景温度恒为 0**，不得改为跟随站点配置。
6. **实际放行线 = pass_score + gray_band_width**，UI 与文案都按这个线算差额；只改其中一个数字都会改变放行口径，必须同时改文案与测试。
7. **及格线与四个档界自由可配、不做交叉校验**；不得在保存路径加"档界必须递增"之类的校验。
8. **评分结果必须落库（单行 Upsert）**，否则异步补评分会重复计费。
9. 零 DDL 口径不变。
10. **闸门判定必须同步**，不得挪回发件箱。它是唯一允许 article app 直接调用别的模块的地方（`QualityGatePort`）；新增"影响本次请求结果的跨模块判定"时才可复用这条通道，其余副作用继续走 outbox。

| 原条款 | 现在的口径 |
| --- | --- |
| 决策 1–9 隐含的"总分过线即放行" | 总分过线**且**六个维度**每一项**都要 ≥ `pass_score`。总分再高，只要一项不够就不放行。 |
| 约束 6「实际放行线 = pass_score + gray_band_width」 | 灰带仍只作用于**总分**；维度下限就是 `pass_score` 本身，**不加**灰带。两个数字各管一件事，不共用。 |
| 决策 9「拒绝时带结构化数据」 | `QualityRejectionDetails` 增加了 `min_dimension_score` 与 `weak_dimensions`；`gap` 只表示**总分**差额，被维度卡住时归零（不再给负数）。 |

新约束（不属于本 ADR 原条款）：`weak_dimensions` 只列 `< pass_score` 的维度，与 `gap` 相互独立，两者可以同时成立；作者侧因此分两种文案（"有几项低于及格线" / "还差几分"），后端不拼含糊句子。

这份修订没有改变"闸门默认关闭、评分在事务外、失败关闭、零 DDL"这四条根基，也没有改变错误码集合。
