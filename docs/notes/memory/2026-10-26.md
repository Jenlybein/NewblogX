**实测结论（推翻了之前几个模糊判断）**
1. **`.swaggo` 全局类型覆盖有效**（swag `--overridesFile`，默认读仓库根的 `.swaggo`）：
   `replace myblogx/internal/kernel/ctype.ID string` 一行，把 schema 里 ID 字段
   integer 106 → 45（61 处已转 string），切片 `[]ctype.ID` 也生效。
   生成 5.6s，`docs.go` diff 仅 134 行且全是 `"type":"integer"→"string"`（纯字符串常量，安全）。
2. **剩下 45 处 integer 不是配置的锅，是代码的锅**：这些字段在 Go 里声明为
   `uint64/int64` 原生类型（comment / media / user / social），**JSON 里真的是数字**。
   → 契约是对的，错的是代码（且前端会丢精度）。改类型是唯一正解（不能用
   `swaggertype:"string"` 掩盖：那会让契约撒谎）。
3. **`fix-openapi-id-types.mjs` 其实干两件事**：schema 字段 + **@Param 注解里的 ID 参数**
   （swagger.json 里 32 处 integer 参数）。后者 `.swaggo` 完全管不到，只能改注解
   （源码里 `@Param ... (path|query|form) int` 的 ID 有 11 处，另有一批来自 struct 展开）。
4. **"47 处 data=object{}" 是诚实的，不是缺口**：逐个比对函数体，**0 处**实际返回了 data

### 结果：契约流水线 4 步 → 3 步 → **2 步**

- `openapi-typescript` **只认 `$ref`**，于是 `status: 1|2` 被放松成 `ArticleStatus`（`1|2|3|4`）
- 修法：给这 5 个字段加 `swaggertype:"integer"` / `swaggertype:"string"`
  → v2 改输出 `{"enum":[1,2],"type":"integer"}`，前端恢复 `status: 1 | 2`
- **只在需要收窄的字段上用**，不要全局加（会丢"这是 ArticleStatus 类型"的语义）

### 【纠错】"直接用契约类型会到处判空"——高估了
我先前断言：契约 636 字段只有 44 必填（6.9%），所以直接当业务类型会让每个字段多出
`undefined`、业务代码到处判空。**实测推翻了这个判断。**

实验：把最复杂的 `ArticleDetail`（29 字段）从手写 interface 换成
`type ArticleDetail = Schema<"internal_article_adapter_http.ArticleDetailResponse">`，
跑 `nuxi typecheck` → **只有 2 个错误**，且都出在 `studio/write.vue:180/182`：
```
Type 'string | null' is not assignable to type 'string | undefined'
```
**没有出现任何 "possibly undefined" 报错。**

为什么？因为 `ArticleDetail` 只用在这几处：`services/article.ts` 的
`request<ArticleDetail>`（API 边界，类型不外溢）、`pages/article/[id].vue`、`studio/write.vue`。
页面拿到的本来就是 `Ref<ArticleDetail | null>`，那里已经做了 null 处理；
模板里的字段访问 vue-tsc 也不会因 optional 报错。
→ **可选性缺失主要影响"组件 props 里传播的大对象"，而这个项目里没这种用法。**

### 但实验暴露了一个更硬的问题：契约不表达 null
那 2 个报错的根因是：`category_id`/`cover_image_id` 在 Go 里是 `*ctype.ID`（JSON 可能是 `null`），
而契约写的是 `{"type":"string"}`。实测全仓：
- `nullable: true` 的字段：**0 处**
- `type` 含 `null` 的字段：**0 处**

也就是说 **swag 完全没表达可空性**（v2 出 OpenAPI 3.1 本可以写 `type: ["string","null"]`，
但没做）。这跟 M7 修 ID 类型之前是同一类问题：**契约在事实层面写错**，只是这次错在 null。

### 修正后的结论（替代 MEMORY.md 里的方案 D→B）
「能不能直接用 openapi.d.ts」的答案是**能**，障碍按真实影响排序：
1. **契约不表达 null**（0 处）→ 事实错误，必须先修（注解补 `extensions:"x-nullable"` 或

## 契约可用性调研（2026-10-26 傍晚）：找到真正的根因

用户问「怎么改到前端能直接用 openapi.d.ts」，规划出 `docs/architecture/11-契约可用性方案.md`。

### 根因（比 required 缺失更根本）
**119 个 `@Success` 注解全部手写 `object{...}`，0 个引用真实 Go 类型。**
→ 响应契约根本不是"生成的"，是"人手抄的"。这一条解释全部症状：
- required 44/636（6.9%）：注解里没有 struct，`binding:"required"` 无处生效
- 7 个 list 是 `Record<string, never>[]`：注解写了 `list=[]object{}`
- 契约 `nullable` 0 处：手写形状里没有 null 语法
- 改 Go struct 契约不变：注解与代码零机械关联

### 三个实测通过的关键点
1. **swag v2 读 `binding:"required"`**（`field_parser.go:515` `IsRequired()`）
   → 项目现成有 68 处 `binding:"...required..."`，只要注解引用 struct 就自动生效
2. **swag v2 支持注解里写泛型**：`// @Success 200 {object} kernel.Envelope[kernel.ListData[string]]`
   → 实测生成 `Envelope-...-ListData-string` 与 `ListData-string` 两个 schema，嵌套/数组/`$ref` 全对
3. **swag v2 无法表达 null**：`extensions:"x-nullable"` 能出 `"x-nullable": true` 但
   **`openapi-typescript` 忽略它**；`swaggertype` 无用；源码里 `Nullable` 没有从 `*T` 推导的路径
   → null 必须靠"后端去掉响应侧指针"或"前端 `Nullable<T,K>` 补偿"

### 指针字段实测分布（internal/*/adapter/http/）
- **请求侧 49 个**（`*Request`/`*URI`/`*Payload`）= PATCH 语义，**必须保留**
- **响应侧 22 个**（`*Response`/`*Item`/`*Data`）= 表示"没有值"，可改零值
→ 所以 null 问题只有 22 个字段，不是 68 个

### 建议顺序：P0 → P2 → P1 → P3 → P4 → P5
- P0 定义 `kernel.Envelope[T]` / `kernel.ListData[T]`（已验证）
- **P2 先做**（7 处列表泛型化）：小、能立刻验证泛型方案在真实场景的表现
- **P1 后做**（119 处注解引用真实类型）：大工程，每处要核对"手写形状 vs 真实 DTO"，
  不一致处就是既有 bug。按模块拆（article 30 / analytics 14 / auth 13 / notification 11 / site 10 ...）
- P3 修 22 处响应侧指针（记得同时去掉 `omitempty`，否则 `""` 被省略又变成 undefined）
- P4 api.ts 迁移（30 已证明 / 15 待 P2 / 6 纯 UI 保留 / 29 待确认）
- P5 删 `contract-guard.ts`（类型直接来自契约后多余），但 `contract.ts` 要保留并加泛型 schema 别名
  （`Envelope-myblogx_internal_kernel_ListData-string` 太长）

### 不做什么（写进文档防后人白干）
- 不给 `res.OkWithList(list any, ...)` 加泛型：**swag 只读注解，不读调用处泛型实参**
- 不追求 100% required：请求侧 49 个指针本来就是可选
- 不回到"生成后处理脚本"：M7 刚删掉，不想让契约正确依赖一个可能忘跑的中间层

### 成果
| 指标 | 之前 | 现在 |
|---|---|---|
| 手写 `object{...}` 响应注解 | **119** | **0** |

| api.ts 里从契约派生的类型 | 0 | **30** |

### 方案与原计划的差异（重要，别按老文档做）
1. **P3（改 22 个响应侧指针）取消**。不需要动后端：前端 `Nullable<T,K>` 显式声明哪几个字段
   可能是 null，既不改 API 行为、又不用改所有 `=== null` 判断，而且"谎言的边界"写在类型里可见。
2. **P4 不是裸用 `Schema<>`**。直接换会产生 33 个编译错误（契约全字段可选 + 嵌套也全可选
   + null 表达不了）。实际做法是在 `contract.ts` 加三层工具：
   - `RequiredSchema<K>` = `DeepRequired<Schema<K>>` —— 递归去掉 `?` 和 `| undefined`
   - `Nullable<T,K>` —— 指定字段放宽为 `| null`
   - `OptionalFields<T,K>` —— 指定字段放回可选（后端确实可能不返回）
   用起来：`type ArticleDetail = Nullable<RequiredSchema<"...">, "category_id" | ...>`
   **这比原方案好**：字段名+类型来自契约（改名/改类型都编译报错），必填与可空在前端显式补。
3. **required 不再是目标**。原计划说"注解引用 struct 后 68 处 `binding:required` 会自动生效"——
   **实测不成立**：那 68 处全在**请求** DTO 上；响应侧 289 个字段里只有 **2** 个有 binding。
   Go 的响应 struct 没有"一定返回值"的表达载体。改完 required 从 6.9% → 6.0%（分母变大）。

### 顺手抓到的真实 bug
`GET /articles/author_info` 注解写 `data=object{}`，实际返回 `{id,username,nickname,avatar}`；
而前端 `ArticleAuthorInfo` 期望 `{author_id, article_count, article_visited_count, fans_count}`。
**字段名和内容都不一致** → 文章页右侧「文章数/访问量/粉丝数」**恒显示 0**（模板有 `|| 0` 所以不报错）。
后端已按真实返回补 `ArticleAuthorInfoResponse`（id 从 uint64 改成 ctype.ID）。
**那三个统计要不要后端补，是产品决策，未擅自实施。**

### 两个必须记住的坑
1. **注解里引用跨包类型，那个包必须被文件真正 import**（注释不参与编译）。
   代码里不直接用时要写 `_ "path"` 空白 import，swag 从 import 列表推断包名。
2. **批量替换注解的 pattern 必须带行首 `//`**。我漏了，7 处变成 `// // @Success ...`（被注释掉），
   swag 静默丢弃、生成 `"responses": {}`。**更坑的是这让我得出"swag 泛型不支持自定义类型"的
   错误结论并写进了方案**——实际 swag v2 完全支持 `kernel.Envelope[kernel.ListData[XxxItem]]`。
   教训：**排查"工具不支持"之前，先看一眼源文件的真实字节**（`sed -n 'Np' f | cat -A`）。

### 遗留（有意保留，见文档 §7.8）
- 纯 UI 形状 6 个（不对应接口）
- 列表包装 15 个（契约里是超长泛型实例名 `Envelope-...-ListData-...-Item`，可读性差；
  后续可做 `ListResponse<Item>` 短别名收掉）

- `frontend_admin` 也有 `api.ts`，但从来没有 guard，未纳入本次范围

### 【重要】新坑：`omitempty` 指针是「缺席」，不是 `null`

| `*T` + `omitempty` | **可能不存在** | `T \| undefined`（OptionalFields） |

## 死信重投（ADR-008）落地：把"同步失败"补成闭环

用户选了方案①（接线）。动手前先核对了前提，发现**我原来的说法是错的**：
不存在"死信回放路径"，`deadletter` 包只有 `SaveBatch`/`Query`，没有重投执行器，
死信状态写进去后永远是 `pending`。所以这是"做一个功能"，不是"接一根线"。

### 支持范围按 payload 自洽性划定（这是本轮最重要的判断）
| stream | payload | 结论 |
| --- | --- | --- |
| `es_river` | 完整 ES bulk body | ✅ 原样重投（按文档 id 幂等） |
| `outbox_relay` | `{payload}` + `outbox:<id>` | ✅ 把发件箱行 dead→pending、attempts=0 |
| `es_projection` | 只有 schema/table/action/rowCount | ❌ 无主键，不知道是哪一行 |
| `image_ref_river` | binlog 原始行 `[]any` | ❌ JSON 往返后 float64，行快照还原不可靠 |

后两类返回 `unsupported` + 替代动作（重建投影 / 重新保存对象），不改库。

### 落地结构
`platform/cdc/deadletter/status.go`（状态机 + MarkResolved/BumpRetry/ByIDs/Count）
→ `platform/cdc/dlq/service.go`（编排，Replayer 接口 + 注入式 Emit）
→ `river.replay.go` / `outboxrelay/replay.go`（两个执行器）
→ analytics 端口 `DeadLetterReplayer` + `GET /logs/dead-letter` + `POST /logs/dead-letter/replay`
→ admin `/logs`（五类日志）+ `/logs/dead-letter`（勾选重投）

### 三个刻意取舍（写进 ADR-008）
1. **不要 `replaying` 中间态**：执行器幂等，人工低频，重复点最多重投两次。
   用幂等换掉互斥，省掉"僵尸状态恢复"。
2. **不自动重投**：死信多半是"改之前必然失败"，自动重投会把 ES 打出一片 400。
3. **outbox 重投 = 重置状态**，复用中继的重试/退避/租约；代价是最长等一个轮询周期。

### 又一次踩到"入口存在、目标不存在"
侧边栏「日志中心 → /logs」**从来没有对应页面文件**，点进去 404。本轮顺手建了。
这类问题没有任何门禁会报（已记在 baseline §46 待办：加"菜单 path ↔ 页面文件"校验）。

### 门禁踩坑
`errors.New` 里写中文会被 archcheck **R8** 拦（`ErrSkipped` 第一次就红了）。
哨兵错误用英文文案 + 中文注释。

## 第六轮：先验证再规划（对应上一轮 9 条，未改任何代码）

**自己纠正两处**：
1. 上一轮建议"把 role 加到 `/users/base`"是**不安全**的——`/users/base` 必传 `id`，是查任意用户公开主页的接口，
   加 role 等于公开管理员名单。改为 scope=admin 或 `GET /users/detail`（无 id 参数，只查自己）。
2. "update 折叠成 index 现在不炸"的**原因说错了**：article 规则在 config 里**根本没配 pipeline**；
   真正原因是通用规则分支对 6 张源表全部不可达（`handleOutboxEvent` / `handleArticleSearchProjectionEvent`
   先 return），所以 `makeUpdateReqData` 那条路今天就没人走。

**新发现（已验证）**：`es_river` 在当前两份配置下**没有生产者**。生产者只有 `sync.go` 的通用规则分支
（唯一 rule = `article_models`，且它被投影分支 intercept）。所以生产环境 ES 类死信只会是
`es_projection`——而它恰好是**不支持重投**的那一类。死信重投的"主路径"是一个没有输入的执行器。

**鉴权细节**：`AdminMiddleware` 用 `FailWithMsg("权限错误")` → envelope code **1001**（与参数校验失败同码）、
HTTP **200**。所以前端 `isAuthLikeError` 匹配不到，"没权限"与"参数错"无法区分 → 越权/降级只能看到"校验失败"。
后端每请求都 `FindAccount` 取 role（`auth/service.go:312-336`），**权限是实时的**，这块本来就安全。

**scope=admin 的边界**：`Refresh` 读 session 表、不读 claims，零 DDL 无法把 scope 持久化
→ scope 只能在"登录那一刻"生效；之后靠后端按 role 每请求校验兜底。不要在文档里写成持久边界。

**门禁可行性**：gin 的 `Routes()` 不暴露中间件链，只能行为探测（注入 stub `TokenVerifier`：
无 token→auth 错、有 token→RoleUser claims），拿零值 handler 时 admin 组的请求会被中间件挡住、
不会 panic。菜单↔页面门禁用 vitest + fs 扫 `app/pages`，所以 navItems 要抽到 `app/utils`（覆盖率只算 utils）。

**用户拍板**：A 接受（scope 只在登录那一刻生效）；B 不做（不让前端/用户区分"没权限"，避免暴露
"普通账号能登录"这件事）→ 因此降级管理员不会被前端统一踢出，只能看到"校验失败"，这是有意接受的行为。

**C 的成本比原估低**：`articlesync.SyncArticleSearchProjection(db, es, {Type, IDs})` 是现成的
"按主键补偿重建"入口，8 种语义（article_upsert/delete、author/category/tag_snapshot、
article_tags_changed、article_top_changed、top_user_changed）全都按 ID 从库里重读。

## 第九轮：批量写的部分失败 + 重试 + ES 死代码清理（b3df100）

**IndexBulk 变诚实**：ES bulk 是"HTTP 200 + 逐条结果"。原来 `IndexBulk` 只看 HTTP 状态、
**从不读 `errors`**，个别文档 mapping 冲突失败会被当成功放过（不进死信、无日志、静默少一篇）。

`bulkWriteError`：有遗留失败→报明细；有逐条结果但已处理→成功；无逐条结果→报原始 Msg。

### 编号迁移的坑（可复用）

用「倒序 replace」迁移章号是错的：`十` 是 `十一/十二/十三` 的**前缀**，
先把 十一→十二 再处理 十→十一 时，会把 `#十二代码约定` 污染成 `#十一二代码约定`。
正解：**一次正则替换 + 映射函数**，交替式按长选项优先：
`re.sub(r"## (十三|十二|十一|十|[一二三四五六七八九])、", f, s)`，目录锚点同理。
另外可见文字 `[9.2]` 与锚点 `(#102-` 是两处，要分别改。

## 修 CI 三个失败（`540bd46`）

`75c8575` push 后 CI 红，三处失败根因各不相同，**都不是那次提交引入的**。

抓 CI 日志的路子（本机没有 gh，值得记住）：用 `git credential fill` 取出
https 凭据里的 token，再打 GitHub API：
`GET /repos/{o}/{r}/actions/runs?per_page=1` → runs，
`.../runs/{id}/jobs` → 每个 job 的 id + conclusion，
`GET .../actions/jobs/{job_id}/logs` → 纯文本日志（会 302 到 blob）。
**坑**：blob 下载偶发 `ServerBusy: Egress is over the account limit`，
重试即可；别把它当成没权限。

三个根因：
1. **frontend_admin (test)**：`formatDateTime` 用 `toLocaleString` 且没传 `timeZone`，
   会把时刻换算成运行环境时区。原用例用 `+08:00` 的输入断言"输出含 3:04"，
   UTC runner 上变成前一天 19:04。**带偏移的输入反而更依赖运行环境时区**，
   原注释写反了。改成不带偏移的输入 + 四个前端 job 钉 `TZ: Asia/Shanghai`。
2. **backend (integration)**：`markFailed` 把 `available_at` 设为
   `now + BackoffMS*attempts`，领取要求 `available_at <= now`。测试用
   `BackoffMS=1`，第 2 次失败后窗口仅 2ms < 一次往返 → 第 3 次 Dispatch 落空
   （返回 nil 不改状态，是正常竞争）→ 状态停在 failed。加了 `waitClaimable` 轮询。
   用 sqlite 复现过（连续投三次 attempts 卡在 1），临时文件已删。
   **sqlite 复现的坑**：`deadletter.SaveBatch` 用了 MySQL 的 `GREATEST`，
   sqlite 报 `no such function: GREATEST`，所以这套路只能覆盖到"写入死信"之前。
3. **backend (contract)**：swag `--parseDependency` 内部调 `go list -deps` 与模块
   下载并发，抖动就报 `cannot find all dependencies, <nil>`。本地
   `make openapi` 成功且产物零差异 → 纯环境问题。CI 里 `make openapi` 前加
   `go mod download`。

**过程中的一次真实失误**：改 lint job 时 old_string 带上了整个 steps 块、
new_string 只写了头部，等于把 5 个步骤删了。靠"逐 job 对比 HEAD 的 steps 数量"
（PyYAML 解析新旧两份）才确认恢复完整，最终只有 contract +1 是预期的。
教训：**往 YAML 里插入内容时，old_string 只用要插入点前后的锚点，别把整段当锚点**；
改完必须做结构级比对（步骤数/键名），不能只看 diff 看着顺眼。
