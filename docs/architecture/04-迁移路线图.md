# 04 · 迁移路线图

> 原则：**每个阶段结束都能编译、能上线**；**每个验收项都必须能用一条命令判定通过/失败**。
> 这条原则针对本项目的历史教训——上一轮改造有规则但没有执行，所以这次拒绝"看起来做了"。

---

## 0. 总览

| 阶段 | 目标 | 规模 | 可上线 |
| --- | --- | --- | --- |
| **R0** 仓库重建 | 删旧 `.git` → 目录重排为 `backend`/`frontend`/`frontend_admin`/`deploy` → 重新 `git init` | 目录级 | 首提交即目标形态 |
| **S0** 清场 | 删死代码 + 修明显缺陷 | 删除 8,000 行 / 2.1MB | ✅ |
| **S1** 建闸 | CI + 可执行守卫 + lint 真跑 | 新增约 600 行工具 | ✅ |
| **S2** 打地基 | `platform/` 真实化 + AI 网关 + CDC 合并 + openapi 自动生成 | 中等 | ✅ |
| **S3** 试点 | article 模块走通三段结构 | 大 | ✅ |
| **S4** 铺开 | 其余 12 个模块 | 很大 | 每模块可独立 |
| **S5** 收尾 | 删 Deps / models / 单上游代理 / 生产部署 | 大 | ✅ |

## S1 · 建闸（本阶段是整份方案的分水岭）

| 1.12 | vitest 加覆盖率门槛 | 当前 `thresholds` 缺失 |

### 关键：首批规则必须"打得中"

如果新规则上线后全绿，**说明规则无效**。以下是必须命中的：

| 规则 | 现状应报违规 |
| --- | --- |
| 禁止导出结构体含 `*gorm.DB` | **32 处 Deps** |
| `adapter` 之外禁止 `*gorm.DB` | **61 个 api 文件** |
| 单文件 ≤ 800 行 | `article_sync.go`(1547)、`sync.go`(852)、`query_read.go`(655)、`enter.go`(517) |
| `enter.go` ≤ 50 行 | **65 个** |
| 禁止 `type Deps struct` | 32 处 |

**做法**：规则先以 `--warn` 模式上线（不阻断），列出全部存量违规作为"债务基线"；S3 起逐模块清零，清完的模块转为 `--error` 阻断。

### 验收

```bash
# 1. CI 真的跑（在 PR 上能看到 5 个 job）
gh run list --limit 1

# 2. lint 不再是永真
#    故意加一行明显错误（如未定义变量），期望 lint 失败
pnpm lint && echo "FAIL: lint 应该报错但没有"

# 3. typecheck 会阻断构建
#    故意在 .ts 里写类型错误，期望 build 失败
pnpm build && echo "FAIL: typecheck 未阻断构建"

# 4. archcheck 能报出存量违规
go run ./tools/archcheck --warn | grep -c "Deps"   # 期望 >= 30
go run ./tools/archcheck --warn | grep "article_sync.go"  # 期望命中

# 5. 规则自检通过
go test ./tools/archcheck/...

# 6. 版本可追溯
go build -ldflags "-X main.commit=$(git rev-parse --short HEAD)" ./cmd/server
./server --version | grep "$(git rev-parse --short HEAD)"
```

### 回滚

CI 与 archcheck 都是新增文件，删除即可回到现状（但建议不要回滚——这是唯一能防止再次腐化的机制）。

### 风险

| 风险 | 缓解 |
| --- | --- |
| 一次性开启 lint 报出上千条错误，团队抵触 | 分两步：先 `eslint --fix` 自动修格式，再对剩余规则设 `warn` |
| archcheck 误报导致无法合并 | 存量用 `--warn`，只对新增代码 `--error`（按 git diff 判定） |

## 2. 与上一轮改造的区别
