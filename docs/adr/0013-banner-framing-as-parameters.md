# ADR-0013：封面上传前定形（裁到目标比例并降采样）

- 状态：已交付
- 日期：2026-10-31
- 来源：2026-10-31 的取景 spec 与 2026-11-03 的封面定形决策（[#200](https://github.com/Jenlybein/NewblogX/issues/200) / [#203](https://github.com/Jenlybein/NewblogX/issues/203) / [#204](https://github.com/Jenlybein/NewblogX/issues/204)）

## 背景与问题

首屏轮播面板此前没有锁定比例，运营上传的图什么样就渲染成什么样：同一张图在不同屏宽下被 `cover` 裁得不一样，竖图与超宽图则被裁得莫名其妙。运营侧更直接——后台只能选文件、传上去、填跳转链接，**无法决定这张图露出哪一块**。

早期方案把构图表达成「焦点 + 缩放」参数存进取景表、由读者端 CSS 复现，并为它单开了一张通用取景表。该机制已全量退场。

长期运行后，旧方案暴露出三个无法靠修补解决的问题：

1. **维护负担与表例外**：为了"只描述怎么显示"，多了一张跨主体类型的表（零 DDL 的唯一登记例外）、一条读写端口、一类契约字段与错误码；每加一种封面主体，参数与校验就要跟着扩散。
2. **构图在部分链路静默丢失**：浏览历史、收藏等链路根本不消费取景参数，同一张封面在这些位置按居中渲染，与详情页不一致；而"预览即最终效果"的承诺要靠每一处消费点都正确复现几何才成立。
3. **产品决定改向**：管理员希望**上传时就把图直接定形**，不再单独维护取景参数。封面比例是设计常量（16:9），不再有"同一张图换一个框再裁一次"的需求。

于是本决策把旧结论整体推翻，改为**上传前定形**：封面在进入对象存储之前，就在后台按目标比例裁好、降采样，产出一张新文件；原图不上传。读者端不再有任何取景参数，固定居中渲染。

## 决策

1. **封面在上传前定形**：后台在浏览器里按目标比例裁切并降采样，产出一张新的图片文件再上传；原图不上传、不入库。轮播封面、文章封面、合集封面**共用同一套实现**，不各写一套。与目标比例相差 ≤1% 时自动居中裁；比例不合规时弹裁剪窗由作者自选区域（固定比例框 + 拖动 + 1–3× 缩放），确认后把结果烤进新文件，取消即中止本次上传。产物永远是新文件，不存任何裁剪参数。
2. **封面比例仍是设计常量**：16:9，写死在两端并由跨端静态断言锁住；不进运行时配置——比例一旦可调，历史定形文件的构图就会与版式对不上。
3. **读者端固定居中渲染**：`object-fit: cover` + 居中，不再读任何焦点/缩放参数；封面只有一个形状。没有定形过的历史封面按居中兜底，不出现空白或拉伸。
4. **取景参数体系全量退场**：焦点/缩放概念、`crop` 契约字段、`banner.crop_invalid` 错误码、通用取景表、它的 CDC 监听与索引投影字段、两端取景窗与取景几何纯函数一并删除。取景表 `picture_crop_models` 的物理下线属**一次性现场操作**：`schema.sql` 只登记 `CREATE TABLE IF NOT EXISTS`、不写 `DROP`，下线步骤写进部署序列（[README §11.4.3](../../README.md#1143-本批189的一次性部署序列新表取景表下线与索引重建)）。
5. **上传前必须能预览定形结果**：管理员看到的就是将要上传的那张图，不靠事后猜。
6. **取消定形＝中止本次上传**：不产生图片、不产生封面记录、不留半成品；定形失败等同上传失败。
7. **头像定形是同一条原则的独立实例**：头像在上传前居中裁成 1:1、降采样到 256 边长、输出 PNG；它改动图片文件本身，与封面定形并列，但不共用封面比例，也不写任何附加表（概念见 [GLOSSARY · 头像定形](../../GLOSSARY.md)）。

## 理由与已否决方案

核心判断换成了：**封面构图是一次性、不可逆的产品决定，不是读者端要反复计算的排版量**。比例固定为 16:9 之后，"原图 + 参数 + CSS 复现"的可逆性没有换来任何运营价值，只换来一张表、一条同步链路与多处必须正确复现的几何实现；反过来，上传前定形让"线上文件"就是构图真相——所有消费点（首页、列表、详情、历史、收藏、后台缩略）自动一致，不需要各自复现几何。

被否决 / 被推翻的方案：

- **旧方案：存焦点 + 缩放，CSS 复现**（原选中，现推翻）：可逆、可回退，但跨链路不消费时构图静默丢失；为它单开通用取景表破坏了零 DDL 口径的简洁性；每加一种主体就扩散一次参数与校验。
- **服务端裁切**（服务端裁，或用对象存储厂商的图片样式参数）：把渲染绑死到存储厂商，换存储、换域名、本地与测试环境都要复刻同一套变体规则；带参数的 URL 让缓存键爆炸。本决策明确不引入服务端或存储侧裁切。
- **只在 CSS 里"定形"、仍然上传原图**：读者端仍要按容器裁切，历史/收藏等不消费参数的位置依旧不一致——这正是旧方案的病根，没有解决任何问题。**否决**。
- **保留 `crop` 字段做兼容（双轨永久化）**：死字段会长期留在契约里，生成类型、前端手写类型、后台表单都要为它维护；双轨期只用于让旧封面可读，退场收尾必须删干净。**否决**（双轨只是过渡，本批收尾删除）。
- **为"上传前定形"再造一张派生图表**：定形结果就是封面自己（`banner_models.cover` / 文章封面 / 合集封面），不需要额外的记录表。**否决**。

## 代价 / 不做什么

- **定形不可逆**：线上只有裁好的那一张。改构图只能重新选择原图、重新定形、重新上传；原图不保留在服务器上。这是本决策明码标价的成本，换来的是"线上文件即真相"。
- **历史封面不迁移**：旧封面没有定形过，按居中兜底渲染。构图与当年取景参数下的效果可能不同——这是取景退场的预期后果，不提供回填。
- **前端裁切实现不引库**：由 `frontend/app/utils/imageShaping.ts` 的手写 canvas 完成（两端逐字节同源门禁），画布/图像构造可注入，测试环境没有 canvas 实现也能测；裁切逻辑是纯函数/可测的。不引 cropperjs：v2 没有纯数学裁切 API，静态 import 会破坏 SSR 与 vitest。
- **旧表下线是一次现场操作**：不可逆，必须先备份。仓库内不写 `DROP`，只把步骤写进部署序列。
- **不做什么**：不做服务端裁切与对象存储厂商的图片样式参数；不做历史封面的批量重裁或重传；不做按屏宽 / 设备下发不同构图；不做移动端专用比例（4:3、1:1 等）；不做人脸识别 / 主体检测 / AI 自动构图；不做旋转、镜像、滤镜；不恢复 `crop` 字段或任何取景参数。

## 当前生效约束

1. 三种封面（轮播、文章、合集）统一走同一套上传前定形实现；不得各写一份。
2. 封面比例是设计常量 **16:9**，所有断点同一比例；不进运行时配置，跨端由静态断言锁住一致。
3. 只上传**定形后的新文件**；原图不上传、不入库。上传前必须可预览定形结果。
4. 取消定形＝中止本次上传：不产生图片、不产生封面记录。
5. 读者端封面固定居中渲染，不读任何焦点 / 缩放 / `crop` 字段；字段、错误码与取景表均不存在。
6. 禁止在服务端或存储侧裁切封面（含对象存储厂商的图片样式参数）；定形只发生在后台上传前。
7. 历史封面不迁移、不回填、不保留旧取景读取路径；未定形过的旧封面按居中兜底。
8. 定形实现零依赖手写 canvas，不引裁剪库；比例不合规时允许弹裁剪窗由作者自选区域，但不得存任何裁剪参数。
9. 取景表 `picture_crop_models` 已物理下线：`schema.sql` 不得再出现该表的 `CREATE`，也不得写 `DROP`（下线只按 [README §11.4.3](../../README.md#1143-本批189的一次性部署序列新表取景表下线与索引重建) 现场执行一次）；后端代码、测试建模与契约里不得再引用该表或取景参数。
