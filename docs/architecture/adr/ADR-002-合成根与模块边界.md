# ADR-002：垂直模块切分与合成根

## Status

**Proposed**（2026-10-24）

## Context

现状是**水平切分**：`api/` 170 包、`service/` 170 包、`repository/` 8 包、`models/` 48 文件。

后果：

| 现象 | 数据 |
| --- | --- |
| 同一功能跨 3 个顶层目录 | 改一个文章接口要动 `api/article_api/` + `service/article_service/` + `repository/` |
| 切分极不均匀 | `article_api` 55 文件 6,012 行 vs `article_service` **1 文件 99 行** |
| service 层名存实亡 | `comment_service` **11 行**；4 个模块完全没有 service |
| 包数爆炸 | 65 个 `enter.go` / 1,327 行，全是包装 |
| 依赖方向混乱 | 三层都能查库：api 61 文件 / service 40 文件 / repository 全部 |

水平切分的隐含假设是"每一层都均匀有内容"。但实际业务逻辑全压在 handler（api 层），service 只剩空壳，repository 只覆盖 9% 的查询。

**这个假设已经被证伪。**

## 备选方案

### A. 保持水平切分，只做"补空"

保留 `api/ service/ repository/`，要求每个功能三层都写。

- 优点：迁移量最小，目录不变
- 缺点：
  - 强制制造空壳（`comment_service` 11 行就是榜样）
  - 跨目录改动的问题不变
  - 圈复杂度只是被分散，没有降低
- 判断：**把形式主义再推一层**

### B. 水平切分 + `internal/` 强制边界

保留三层，但放进 `internal/`，用编译器禁止跨层。

- 优点：边界能强制
- 缺点：
  - 仍然要跨 3 个目录改一个功能
  - "每层均匀"的假设依然不成立
  - 5 个模块没有 service，边界规则会变得形式化
- 判断：**改善了症状，没解决病因**

### C. 垂直模块切分（推荐）

每个业务模块自包含 `domain / app / adapter`。

- 优点：
  - 改动局部化（一个功能在 `internal/article/` 内）
  - 模块边界天然（跨模块必须定义接口）
  - 可按模块独立迁移、独立上线
  - 包数可控（12 模块 × 3 = 36，远少于现状的 300+）
- 缺点：
  - 目录结构与现状差异大，需要适应
  - 跨模块共享数据要定义接口（增加约 50 个端口）
  - `adapter` 包会比较大（单模块 2,000-4,000 行）

### D. 完整 DDD（限界上下文 + 防腐层 + 领域事件）

- 优点：理论最纯
- 缺点：83k 行项目上过度设计；团队规模撑不起
- 判断：**架构宇航员**

## Decision

**采用方案 C：垂直模块切分。**

### 模块内三段结构

```
internal/article/
├── domain/          # 实体、值对象、规则、仓储端口（零外部依赖）
├── app/             # 用例编排，持有事务边界
└── adapter/         # HTTP handler + DTO + MySQL + ES 投影
```

**为什么是 3 个而不是 5 个**：

纯 DDD 会把 http 和 store 分成两个 adapter 包。这里合并，因为：
- 两者的生命周期一致（都由合成根构造、都是"与外界打交道"）
- 分开只增加 import，不增加约束
- 代码量集中在 adapter，可用**文件粒度**控制（`http.go` <500 行、`mysql.go` <800 行，archcheck 强制）

代价：`adapter` 包较大。用 R6（单文件 ≤800 行）约束。

### 合成根

```go
// cmd/server/main.go —— 唯一允许 import 具体实现的地方
func main() {
    infra := platform.New(cfg)
    defer infra.Close()

    articleSvc := wireArticle(infra)
    commentSvc := wireComment(infra, articleSvc.Gate)   // 跨模块走接口
    ...
    httpiface.NewRouter(...).Run()
}
```

**约束**：
- `main.go` 之外不得 `new` 具体实现（archcheck 检查）
- 无包级可变状态
- 每个模块的 `adapter/wire.go` 提供一个 `wireXxx(infra)` 函数

### 跨模块协作三条规则

| 需求 | 做法 | 禁止 |
| --- | --- | --- |
| 读别的模块数据 | 消费方定义窄接口（`ArticleGate`） | import 别的模块 domain |
| 被通知 | 发领域事件（outbox） | 直接调别的模块 service |
| 共享值对象 | 放 `internal/kernel` | 把业务实体放 kernel |

## Consequences

### 变好的

- **改动局部化**：文章功能只在 `internal/article/`
- **可增量迁移**：迁完一个模块就是一次可上线的交付
- **依赖单向**：`adapter → app → domain`，编译器可校验
- **模块间零 import**：跨模块只能通过合成根连线，耦合降到最低
- **包数从 300+ 降到 36**

### 变差的

- **目录认知成本**：团队需要理解"模块内三段"
- **跨模块调用变啰嗦**：要定义接口、在合成根接线
- **共享数据要投影**：`article` 的数据被 `comment`/`search`/`ai` 用，需各自定义只读接口
- **迁移期双轨**：旧 `api/ service/` 与新 `internal/` 并存

### 需要跟进的

- `internal/kernel` 必须严格限制（只放 ID、分页、错误），否则会变成新的垃圾桶
- 需要 archcheck R5（模块间禁止互相 import）兜底，否则半年后又会互相纠缠
- 每个模块迁移前录 golden file，保证行为不变

## 验证

```bash
# 模块间零 import
go list -deps ./internal/article/... | grep "myblogx/internal/comment" && echo "FAIL: 模块互相依赖"

# 只有 cmd 能 import adapter
go list -deps ./internal/article/app/... | grep "myblogx/internal/article/adapter" && echo "FAIL: app 依赖 adapter"

# 合成根唯一
grep -rln "NewMySQLRepo\|NewRedisClient" --include="*.go" apps/api/ | grep -v "cmd/server" && echo "FAIL: 装配点分散"
```
