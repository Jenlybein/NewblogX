## 一、孤儿图回收（原 #53，已取消）

### 现状事实（已核实，勿重复排查）

- **引用账本已建成**：`image_ref_models`（`schema.sql:398-415`），由 CDC `image-ref` river 从 binlog 维护，覆盖四类引用源：文章正文/封面、轮播封面、收藏封面、用户头像。**但只写不读**，全仓无按 `image_id` 反查引用数的代码。
- **引用靠 URL 反解**：`extractObjectKey`（`imageref/refs_common.go:99-132`）要求 URL 以 `{prefix}/images/` 开头，否则丢弃。正文用 goldmark 解析 `![]()` 与 `<img src>`。
- **无引用计数字段**，账本是明细行式。`StatusOrphaned` 枚举已定义但**从未被写入**。
- **无任何图片 GC 定时任务**（`app/cron_wiring.go` 只有计数刷盘 + 日志清理）。
- **存储后端仅七牛一家**，无 S3/MinIO/本地磁盘。
- **真删实现现成**：`media/app/service.go:433-450` 先删对象再 `DeleteWithRefs`（事务内删引用后硬删行）。
- **CLI 的 dry-run/`-apply` 抽象已就绪**（`cmd/cli/enter.go`），可沿用。
- **已澄清的疑点**：站点配置、分类（`category_models` 无 icon 列）、通知图标都**不存图**，所以"账本没覆盖的引用源"这个风险**不存在**。`schema.sql:369` 那个 `icon` 列属于 `image_models` 自己。

### 定案（用户已选）

| 项 | 决定 |
|---|---|
| 判定 | **删前重扫真实引用**（不信任账本；账本有死信 + 靠 URL 反解，漏记不能承受不可逆删除） |
| 冷静期 | **14 天**，做成配置项（覆盖周更 + CDC 积压余量） |
| 删失败 | **先删对象、确认成功才删行**；任一步失败整条跳过留待下次，重试幂等 |
| 排除范围 | **排除头像**（被 CDN 缓存，删了长期裂图）与**审核中/封禁**（语义未定：审核中尚未定性；封禁可能需作证据保留） |
| 拆票 | **拆成两张**：① 账本可信化 + 只读清单；② 真删回收（确认清单准确后才做） |

### 术语（已入 GLOSSARY）

- **引用账本**：`image_ref_models` 的明细行集合；不是 `image_models` 的字段，无引用计数。
- **孤儿图**：判定结果（存在于图片表但无账本行），**不是** `image_models.status` 的值。与"零引用"不等价——账本可能漏记。

## 二、正文内联 SVG

### 根因（实测，两处独立拦截）

1. **后端保存时 SVG 已丢失**：`MdToSafe` 用 `bluemonday.UGCPolicy()`，不含 svg → `<svg>` 被**整块删除**（非转义），`class` 被剥，`<center>` 被剥空。实测证据见 [ADR-0021](../adr/0021-inline-svg-in-article-body.md)。
2. **前端不解析内联 HTML**：`useArticleMarkdown.ts` 的 markdown-it 配 `html: false`。

边界：`![x](https://…/a.svg)` 图片语法**本来就能显示**；**上传** SVG 被格式白名单拒绝（默认白名单无 svg，本次不做）。

### 定案（用户已选）

| 项 | 决定 |
|---|---|
| 修法 | **两层都改**：后端 bluemonday 放行 SVG + 前端开 `html:true` 并消毒 |
| 放行范围 | SVG 绘图元素 + **少量排版标签**（`div/center/figure/figcaption`，保留 `class`）以保住"图 + 图注"写法 |
| 消毒粒度 | **严格白名单**：禁 `script`、`foreignObject`、`animate*`、`on*` 事件属性 |
| 后台预览 | **一并修**（共用同一条渲染管线） |
| 存量 | **不迁移**；保有原始 markdown 的重新保存一次即可（库里那部分已丢失、无法恢复） |

### 顺序

**先修 SVG**（现成显示故障，影响写作），孤儿图等用户新开票。
