## 1. 本轮修掉的问题

### 1.1 IP 归属地库从未被加载（功能缺陷，已修）

`deadcode` 查出 `core.InitIPDB` **零调用**，而 `utils/requestmeta` 一直在调 `ipmeta.GetAddr`。

后果链：

```
InitIPDB 没人调 → ipv4Searcher/ipv6Searcher 恒为 nil
  → GetAddr 对任何真实 IP 都走 `if ipv4Searcher == nil { return "未知地址" }`
  → 登录日志、用户列表的 addr 字段全是「未知地址」
```

而仓库里躺着 `resources/ipbase/ip2region_v4.xdb`(11MB) + `ip2region_v6.xdb`(36MB)，  
**从来没被打开过**。

修法（`app/bootstrap.go`）：

```go
logger := core.InitLogrus(&cfg.Log, &cfg.System)
// IP 归属地库。之前这里漏了这一步……
if err := core.InitIPDB(); err != nil {
    logger.Warnf("IP 归属地库加载失败，addr 将显示为「未知地址」: %v", err)
}
```

三个设计决定：

| 决定                               | 理由                                                               |
| -------------------------------- | ---------------------------------------------------------------- |
| 返回 `error` 而不是内部 `logger.Fatalf` | `addr` 只是展示字段，缺库时 `GetAddr` 自己会降级；不该因为资源缺失让整个服务起不来               |
| 失败只告警                            | 同上。启动中断的代价远大于「地址显示未知」                                            |
| 路径向上探 3 层而不是写死相对路径               | 容器里 CWD 是 `/app`，`go test ./core/` 的 CWD 是 `backend/core`，两者基准不同 |

**回归测试的判据特意不是"返回非空"**：`GetAddr` 有兜底分支，库没加载时也会返回「未知地址」，  
所以旧测试 `TestGetIpAddrBranches`（只断言非空）永远通过——正是它让缺陷藏了这么久。  
新测试 `TestInitIPDBLoadsRealLibrary` 先 `InitIPDB()`，再断言公网 IP **不是**「未知地址」。

## 3. 工程缺口（按影响排序）

### 3.1 CI 完全不碰契约 ⚠️ 最高优先级

`.github/workflows/ci.yml` 里有 backend / backend-integration / archcheck / frontend-lint /  
frontend-typecheck / frontend-test / gates-canary 七个 job，**没有一个安装 swag 或生成契约**。

后果：有人改了 Go 注解但忘了跑 `make openapi`，`docs/swagger.json` 会静默过期，  
前端类型照着过期契约生成，**门禁全绿但契约是错的**。

补一行就够：

```yaml
- name: 契约未过期
  run: |
    make openapi
    git diff --exit-code docs/swagger.json
```

代价是 CI 要装 swag（`go install github.com/swaggo/swag/v2/cmd/swag@v2.0.0-rc6`），  
多约 30 秒。**这笔交易很划算**：契约是前后端唯一的耦合点，它过期了整条链都不可信。

### 3.2 admin 站零测试

`frontend_admin/vitest.config.ts` 里写着 `passWithNoTests: true` 并注释了"当前没有任何测试用例"。  
所以 `vitest run` 输出 `No test files found, exiting with code 0` ——**门禁里那一项是空转的**。

admin 有约 50 个页面（用户管理、文章审核、日志查询、媒体库），**0 个用例**。  
配置里"保留入口是为了降低加第一个测试的门槛"这个理由成立，但要承认：  
**现在 `frontend_admin: test` 这一项提供的保障是 0。**

### 3.3 `deadcode` 没有进闸

本轮的 IP 库缺陷就是它查出来的——一个"写了但没人调用"的函数，编译、vet、测试、archcheck  
**全都发现不了**。目前 Go 侧的死代码检查只靠人工。

现状：`deadcode -test ./...` 报 88 条，其中大部分是 `apptest` 包的测试辅助函数（正常）。  
真正值得处理的是生产代码里的几条：

| 位置                                                                     | 说明          |
| ---------------------------------------------------------------------- | ----------- |
| `internal/ai/search/ai_search_analyze.go` `AnalyzeArticleSearch`       | AI 搜索分析，未接入 |
| `internal/ai/search/ai_search_rewrite.go` `AnalyzeArticleSearchIntent` | AI 搜索改写，未接入 |
| `internal/kernel/request.go` `PagedRequest.Normalize`                  | 分页归一化，未使用   |

这三条是"实现了但没接线"，属于功能缺口而非垃圾代码，需要产品判断。  
建议：**把 `deadcode` 作为定期审查工具（不是硬门禁）**，因为它的输出需要人工区分  
"死代码"和"未接线的功能"。

### 3.4 契约精度（已知，收益递减）

| 指标                            | 现值                 | 说明                                               |
| ----------------------------- | ------------------ | ------------------------------------------------ |

### 6.3 「恢复已隐藏文章」——我原来的判断是错的

审查里写的是"该页用 `/search/articles`，而搜索只索引可见文章"。实际逐条核对代码后：

1. 前端 `searchAdminArticles` **确实传了 `type: 5`**
2. `buildDSL` 的 `case 5` 走 `adminQuery`，**它本来就没有 `visibleFilter()`**
3. ES 同步（`article_sync_load.go`）没有可见性过滤，`visibility_status` 也在增量更新的列里

所以隐藏文章本来就在索引里、也对管理员可见。**真正的缺陷只是契约**：
`myblogx_internal_search_domain.VisibilityStatus` 这个类型在搜索模块只声明了 `"visible"` 一个常量，
swag 于是把枚举印成单值，前端只好用 `Omit<..., "visibility_status">` 手工放宽回三值。

修法是把搜索模块的单值枚举**别名**到 `kernel/enum.ArticleVisibilityStatus`（三值），
不再重新声明一份词表。契约枚举随之变成 `"visible" | "user_hidden" | "admin_hidden"`，
前端那个 `Omit` 就可以删掉，`SearchArticleItem` 变成纯契约派生。

**教训**：这次是我拿着契约去推断运行时行为，而契约本身就是错的那一方。
判断"某条流程走不到"之前，必须读一遍实际调用链，不能只看类型。

### 6.4 admin 角色列：补字段时抓到一个提权方向的 bug

后端补 `role` / `status`（`domain.User` 本来就有，只是没带出边界）之后，列表终于显示出角色了，
然后立刻暴露出一件事：**管理端的角色数值和后端是反的**。

```
后端  RoleAdmin = 1 / RoleUser = 2 / RoleGuest = 3
前端  { label: '普通用户', value: 1 } / { label: '管理员', value: 2 }
```

后果：在编辑弹窗里选「普通用户」提交的是 `role: 1`，后端据此把该用户**设为管理员**；
选「管理员」提交 `role: 2`，反而降成普通用户。而且因为之前列表里根本不显示角色，
界面上完全察觉不到。

修法：

- 新建 `frontend_admin/app/utils/roles.ts`，把 `ROLE_ADMIN/ROLE_USER/ROLE_GUEST`、
  `roleLabel/statusLabel`、`roleOptions/statusOptions` 收成一处，并在文件头写明
  **数值必须与 `backend/internal/user/domain/user.go` 逐字一致**
- 默认角色从 `1` 改成 `ROLE_USER`（缺省按最小权限，绝不能默认成管理员）
- `test/unit/roles.test.ts` 断言**具体数字**，后端改枚举时这组用例会先红

为什么不能靠契约兜住：`role` / `status` 在契约里是 integer（`swaggertype`），
只保证"是个数字"，不暴露枚举值。这层映射必须手写，就得有测试钉住。

## 8. 第四轮：把死信重投做完（2026-10-26 深夜）

上一节（§7.6）留了一个决策：`replay_event_logs` 只有读端，要么接线、要么删。
用户选了**接线**。但真正动手前先做了一件事：**核对"回放"这个动作本身是否存在**。

### 8.1 先纠正一个前提错误

我原来的说法是"在 CDC 死信回放路径上接线"，隐含"那条路径已经有了"。读完代码发现：

- `deadletter` 包只有 `SaveBatch`（写）与 `Query`（查），**没有任何重投执行器**；
- 死信写进去时状态是 `pending`，**之后永远不会被改成别的值**——只进不出的黑匣子。

所以这不是"接一根线"，而是**做一个功能**。这也是为什么 §7.6 里我把"支持范围"
写成需要拍板的事：payload 里有没有足够的信息，决定了这条流能不能重投。

### 8.2 最终支持范围（按 payload 自洽性划定）

| stream | payload 里有什么 | 结论 |
| --- | --- | --- |
| `outbox_relay` | `{payload}` + `CdcJobID=outbox:<id>` | ✅ 把发件箱行 `dead → pending`、attempts 归零 |
| `es_projection` | `{schema,table,action,rowCount,ids}` | ✅ 按 `ids` 重算投影（见 §9） |
| `image_ref_river` · 删除 | `{owner_id, ref_type}` | ✅ 重新清理该对象的图片引用 |
| `image_ref_river` · 新增/更新 | binlog 原始行 `[]any` | ❌ JSON 往返后数值变 float64，行快照会静默算错 |

不支持的记录不是"以后再说"：接口会返回 `unsupported` + **一句人话告诉他该改用别的什么办法**
（重建投影 / 重新保存业务对象），且**不改库、不涨 `retry_count`**。运维最怕的是"点了没反应"，不是"点不了"。

### 8.3 落地的东西

| 层 | 内容 |
| --- | --- |
| 状态机 | `deadletter.Status*` + `MarkResolved` / `BumpRetry` / `ByIDs` / `Count`（**零 DDL**，只用已有列） |
| 编排 | `platform/cdc/dlq.Service`：取记录 → 按 stream 分派 → 更新状态 → 写回放日志。单条失败不影响同批 |
| 执行器 | `river.ESReplayer`（bulk body 重投）、`outboxrelay.Replayer`（退回发件箱） |
| 接口 | `GET /logs/dead-letter`（分页+过滤）、`POST /logs/dead-letter/replay`（逐条返回结果） |
| 页面 | 修好了从来没有过的 `/logs`（侧边栏一直挂着，点进去 404）→ 五类日志一个切换；新增 `/logs/dead-letter` 做勾选重投 |
| 回放日志 | `EmitReplayEvent` 第一次被真正调用：成功/失败/跳过/不支持**都记**，`cdc_job_id` 可串时间线 |

### 8.4 三个刻意的取舍

1. **不引入 `replaying` 中间态**。重投是人工、低频、单实例操作，两个执行器都幂等
   （ES 按文档 id；outbox 重置是纯状态写），重复执行无害。中间态反而要写"僵尸状态恢复"。
2. **不自动重投**。死信多半是"改之前必然失败"（字段不兼容、索引不存在），
   自动重投会在故障期间把 ES 打出一片 400，还掩盖真实原因。人工触发天然带"先看看为什么"。
3. **outbox 的重投是"重置状态"而不是"立刻投递"**。复用中继自己的重试/退避/租约，
   代价是最长等一个轮询周期。绕开它另开一条投递路径，会多出"两条路径同时投"的风险。

侧边栏的「日志中心 → /logs」**从来就没有对应的页面文件**（`app/pages/logs/` 不存在），
点进去是 404。这跟"读端活、写端没了"是同一类问题，只是发生在路由层：
入口存在、目标不存在，而且没有任何检查会报错。

修法就是本轮把 `/logs` 建起来。**这类问题值得单独一条门禁**（"菜单里的每个 path

### 8.7 更阴的一层：`.gitignore` 让页面根本进不了版本库

页面写完之后发现 `git status` 里看不到 `app/pages/logs/`。原因是
`frontend_admin/.gitignore` 里有一行裸的 `logs` —— 它匹配**任意层级**的同名目录，
于是 `app/pages/logs/` 被静默忽略：

- 本地能跑（文件在磁盘上）；
- `git status` 什么都不提示；
- **CI 和别人的机器上就是 404**，而且没人知道为什么。

已改成 `/logs`（只忽略根目录的运行时日志目录），两个前端都改了。

这是"入口存在、目标不存在"的第三种形态，也是最难发现的一种：
前两种（读端活写端死、菜单指向空页面）至少能在运行时或对账里看到，
这一种**连版本控制都不提示**。

而且还有第二层：**ESLint v9 默认拿 `.gitignore` 当忽略源**，所以这两个页面

（未使用的 import）——说明"之前 lint 通过"是假的通过。

**一条 .gitignore 写错 = 同时关掉两道门禁**，且两道都不吭声。

## 9. 第五轮：把"投影失败"从停摆变成可补救（2026-10-26 深夜）

> 触发：用户问"ES 和 MySQL 怎么配合、作者名冗余怎么办"。查下去发现两个比扇出严重得多的问题。

### 9.1 先纠正两个错误判断

| 我之前的说法 | 事实 |
| --- | --- |
| "把 `role` 加到 `/users/base` 就能让后台判断是不是管理员" | ❌ **不安全**。该接口必传 `id`，是"查任意用户公开主页"，加 role 等于公开管理员名单 |
| "update 折叠成 index 现在不炸，因为 article 规则带 pipeline" | ❌ **理由错**。那条规则在配置里根本没配 pipeline；真正原因是通用规则路径对 6 张源表**全部不可达**（投影分支先 return），所以 `makeUpdateReqData` 今天没人走 |

### 9.2 最严重的既有缺陷：投影失败会让整个同步永久停摆

`sync.go` 里投影报错时执行 `h.r.cancel()`，而 `River.Run` 只在装配时调用一次，
**没有任何重启监督**。后果：一篇文章投影失败 → canal 停止 → 之后所有 MySQL→ES
变更都不同步，而 API 照常服务、没有告警。

当初这么做是合理的：投影死信里没有主键，补不回来，停下来是唯一能"不丢数据"的办法。
所以修复不是简单地把 `cancel()` 删掉，而是**先让死信可重投，再改成跳过**：

1. 落死信时带上行主键 `ids`（6 张表的提取函数本来就有）；
2. 新增 `river.ProjectionReplayer`：按 `(表, 动作)` 映射到 `SyncArticleSearchProjection`
   的重建类型，只重算受影响的文档；
3. `OnRow` 改成"记死信 + 继续跑"，并留一条 error 日志（死信页是事后看的，日志是当时看的）。

**顺序不能反**：先跳过、后补能力 = 静默丢数据。

### 9.3 "不支持"与"失败"混成了一个结果

`image_ref_river` 的新增/更新类死信永远补不上（行数据 JSON 往返后类型不可靠），
但实现把它当**失败**处理：红色"失败" + `retry_count+1`。运维会以为再点几次就好。

修法是加 `deadletter.ErrUnsupported` 哨兵：编排层见到它记 `unsupported`、
**不写库、不涨 retry**、用执行器给的那句人话当提示。四种结果从此分开：
success / skipped / unsupported / failed。

### 9.4 两份手写的 payload → 一份

`imageref` 写入端拼 `map[string]any`、重投端另写一个结构体，靠"字段名恰好一致"对齐。
字段一改名，重投会一律报"只支持删除类死信"，而单测因为手写 JSON 仍然全绿。

收成 `imageref.replayPayload` 一个类型，写入端三处（delete/insert/update）都用它 ——
**改名会在编译期失败**。另外补了 `ParseRefType ↔ RefType.String()` 的 round-trip 用例：
两个手写 switch 各写一遍同一份词表，加第 5 种类型时编译器不会报错。

### 9.5 update 不再折叠成 index

`replayAction` 原来把 `update` 也映射成 `index`。update 的 data 是**只含变更列**的局部文档，
当 index 重发等于整篇覆盖，没变的字段会静默消失。当前没有规则走这条路（见 9.1），
但这是一条"加张非投影表就会咬人"的线，改成保留 `ActionUpdate`。

### 9.6 后台独立登录入口 + 两条门禁

| 项 | 做法 |
| --- | --- |
| 后台登录入口 | `POST /users/login` 支持 `scope=admin`：密码验证通过后、**创建会话之前**校验角色，非管理员返回 `auth.admin_required`，不签发令牌、不写 refresh cookie |
| 边界 | 只在"登录那一刻"生效。`Refresh` 读 session 表、不读 claims，零 DDL 无法持久化 scope；真正的授权始终由 `AdminMiddleware` 每请求查库取 role |
| 权限错误可辨识 | **有意不做**。`AdminMiddleware` 仍返回"权限错误"（与校验失败同码、HTTP 200）。代价：降级的管理员不会被前端统一踢出，只会看到"校验失败" |
| 门禁：后台路由鉴权 | `admin_gate_test.go` 用普通用户令牌逐个探测后台操作，必须停在 AdminMiddleware；另配契约交叉检查防止新接口逃过。附一条对照用例证明"探测真的能分辨拦住与放行" |
| 门禁：菜单 ↔ 页面 | `ADMIN_NAV` 抽到 `app/utils/menu.ts`，vitest 扫 `app/pages` 双向对账（缺页面会红，藏起来的死页面也会红） |

| ES 别名 + 双索引重建 | 重建空窗在这个量级可接受 | 索引大到"重建要十分钟"时 |

| 让"没权限"可辨识 | 不让用户从错误码看出"普通账号能登录" | — |

### 9.8 最后一步：把"没有生产者的旧路"删掉

前面 9.7 里 `es_river` 的处置是"待定"。用户在核对后决定删除，理由是三条都已证实：
6 张源表全部被投影分支拦截、唯一一条 rule 指的也是其中一张、且它拼不出搜索文档
（白名单只有 8 列）。完整依据与代价见 [ADR-009](./adr/ADR-009-删除通用规则同步路径.md)。

| 删掉 | 说明 |
| --- | --- |
| `river/rule/`、`sync_request.go`、`sync_bulk.go`、`replay.go`（`ESReplayer`） | 通用路径的全部实现 |
| `river.go` 的 `rules` / `prepareRule` / `parseSource` / `updateRule` | 约 200 行，含通配符表解析 |
| `sync.go` 的批量合并 + `doBulkWithRetry` | `syncCh` 从 `chan interface{}` 收窄成 `chan posSaver`，同步循环只剩"3 秒节流落位点" |
| `conf.River.Rules` / `flush_bulk_time` / `river.retry` / `BLOGX_RIVER_INDEX` | 两份 yaml + `.envrc.example` + 两个 compose + `env.example` |
| `es_service.Bulk` | 删完 ESReplayer 后没有调用方 |

**没有删的**：`master`（位点）和 canal 的 dump 配置。全量转储会把行按 INSERT 重放，
投影分支照常把它们变成文档 —— 首次部署的数据初始化仍然靠它。

**两处刻意的保留**：

- `deadLetters.ts` 里 `es_river` 的中文名保留 —— 历史死信记录里还会出现这个值，
  删了只会让页面显示原始字符串（页面显示"搜索同步（ES 直投）"比显示 `es_river` 好）。
- `-es -s article-sync`（全量重建）保留，它是"历史数据要补"时的唯一手段。

**代价（写在这，免得以后当成 bug）**：

- 加一张"不需要 join 的表"进 ES，现在要写 handler，不能只改配置。
- ES 写入没有重试 —— 但投影路径本来就没有（一次 `IndexBulk` 失败即落死信），
  这不是本次回归。要加重试应该加在 `articlesync` 的批量写里。

**补记（同一天收尾）：索引名的最后一个"两个地方必须一致"**

删掉 `rule.index` 之后，`BLOGX_RIVER_INDEX` 一并消失了，但暴露出一处更早的耦合：

```
搜索读取 / AI 检索 / CLI 建索引  →  配置 es.index
river 增量写入                  →  硬编码 DefaultArticleESIndex = "article_index"
```

两边默认值恰好相同，所以从没暴露；改了 `BLOGX_ES_INDEX` 就会"建在新索引、搜在新索引、
增量写进旧索引"，且**不报错**（ES 自动建一个没人读的索引，或每次写都失败刷死信）。

修法：`articlesync` 提供 `SetIndexName/IndexName`，装配层（`app.Bootstrap`）与
`-es -s article-sync` 各注入一次，两个写入点改读注入值。没有给 12 个入口加参数 ——
真正用到索引名的只有 2 个内部函数，一路穿参数是给签名加噪音。
配一条用例：给假 ES 发一次写，断言 `_bulk` 路径里是注入的索引名。
