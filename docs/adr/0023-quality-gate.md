# ADR-0023：发布前的质量闸门——评分即闸门、失败关闭、事务外评分

- 状态：已交付
- 日期：2026-11-08
- 来源：parent spec [#302](https://github.com/Jenlybein/NewblogX/issues/302)（发布治理一期）· 落地票 [#306](https://github.com/Jenlybein/NewblogX/issues/306)（质量闸门）· 来自 2026-11-07 的发布治理设计评审 §2.1 / §2.2 / §三

## 背景与问题

评分原本只用于发布之后的异步展示（"文章质量总分 82"），投稿路径没有把关：站点默认 `skip_examining: true`，提交即发布。要把它变成发布前的硬闸门，必须先回答五个问题：

1. **闸门与人工审核是什么关系？** 同一条流水线的两段，还是两道独立的门？
2. **AI 不可用时怎么办？** `ai.enable` 默认是 `false`，"AI 不可用"是默认状态，不是边界情况。
3. **评分调用能不能放在事务里？** 一次模型调用 5–30 秒。
4. **"分数不够"与"系统挂了"是不是同一件事？** 对作者来说，这两种失败的下一步动作完全不同。
5. **及格线与分数档名谁说了算？** 档界与及格线可以不一致。

还有一条判定形状的问题：只看加权总分时，"某一项崩了、其余五项不错"与"六项都不错"会被同一把尺子放行；两行祝福语在清晰与规范两项上轻松拿高分（没有东西可错），加权后就把总分抬过线。评分口径还必须能在不发版的前提下调整宽严，而可数的硬事实不能只靠模型自觉。

## 决策

1. **闸门与人工审核是两道独立的开关**，四种组合都合法；默认闸门关闭、人工审核维持现状。顺序固定为：配额预占 → 评分 → 分数判定 → 落库 →（可选）建审核任务 → 发事件。评分永远排在人工之前——它的价值就是把垃圾挡在人工队列之外。
2. **开启闸门这个动作本身要求 AI 可用**。总闸关闭或没有启用的模型配置时，后台保存直接失败（`article.quality_gate_requires_ai`）。把失败面从运行期挪到配置期：保存不了，这个状态就不存在。
3. **失败关闭，但失败分四类**：配额超限、系统不可用、分数不达标、合规违规，各一个错误码。前端据此给不同文案。
4. **"拿不到可用分数"才算系统失败**：网络错、超时、限流、5xx、返回非 JSON、缺总分。拿到分数（哪怕 23 分）一律算有效结论，走"不达标"；低分不是失败。
5. **评分必须在数据库事务之外，且温度固定为 0**。Create 与 Update 都先算出"这次会不会提交"，再据此在事务外评分；写事务重新读文章、以它读到的状态为准。温度只影响评分场景，不跟随站点级 `ai.temperature`——评分要拿去做放行判定，需要的是可复现而不是创造性。
6. **放行用木桶判定**：总分 ≥ `pass_score + gray_band_width` **且**六个维度**每一项**都 ≥ `pass_score`。灰带只加在总分上，把放行线整体抬出抖动量程（±2 分），避免"同一篇文章今天能发、明天不能发"；维度下限就是 `pass_score` 本身，不加灰带、不共用。总分再高，只要一项不够就不放行。
7. **两个驳回理由相互独立**：`weak_dimensions` 只列 `< pass_score` 的维度（分最低的排最前）；`gap` 只表示**总分**差额，按 `pass_score + gray_band_width` 算，总分过线但被维度卡住时归零，不给负数。两者可以同时成立，作者侧因此分两种文案（"有几项低于及格线" / "还差几分"），后端不拼含糊句子。
8. **评分宽严来自运行时策略文本**：`skills/scoring/SKILL.md` 经 `ai.scene_skills.scoring` 注入。代码只保留解析契约（JSON 形状、维度键名、分档数字）与不可让渡的底线，宽严判断交给运营可改的正文；口径冲突时以更严者为准，这句必须留在提示词里。
9. **代码侧形态硬封顶**，不依赖模型自觉：正文 < 100 字或 < 3 个自然段 → `completeness` ≤ 30、`structure` ≤ 45、总分 ≤ 40；整篇基本是寒暄 / 祝福 / 致谢 / 链接文本（短 + 段落少 + 多数句命中礼节词）→ 总分 ≤ 30、`completeness` ≤ 20；并统一限制"总分 ≤ 最低维度 + 15"，堵住长板补短板。端口带六维得分；拿不到维度分时退回"只看总分"，不把所有提交一起拒掉。缺失维度兜底分为 40，稳定低于任何合理的及格线。
10. **及格线与四个档界自由可配、不做交叉校验**。允许保存"及格线 50 而 31–59 叫不合格文章"这类自相矛盾的组合；作者侧照旧显示档名，因此可能看到"不合格文章 · 55 分 · 已通过"。这是有意接受的代价。
11. **被拒的文章落草稿**（而不是"已拒绝"）：作者能继续改、能立刻重投。拒绝时带结构化数据（分数、放行线、总分差额、档名、最低维度分与问题维度列表），错误码仍由 apperr 一处映射。
12. **评分结果必须落库**（复用既有的单行 Upsert 记录）：不落库的话，同一次提交会被异步补评分再评一次，等于一次提交烧两次模型调用。
13. **不重算存量**：已发布文章维持原分数与可见性，不重算、不下架，只影响新提交；要重算走作者「重新评分」入口。
14. **article 用例层引入同步端口 `QualityGatePort`**，打破「article app 不依赖 AI 模块」的既有格局。既有约定是 article 的副作用一律走事务型发件箱，app 层不认识别的模块；闸门不适用这条——提交还没落库，评分结果决定"这次提交落不落、落成什么状态"，没有后面可以补的时机。端口由使用方定义（一个方法），实现在 `backend/app/article_wiring.go`，跨模块的具体形状（`ScoreForGate`）只活在装配层。**闸门判定必须同步**，它是唯一允许 article app 直接调用别的模块的地方；其余副作用继续走 outbox。合规判定（[ADR-0024](./0024-risk-models.md)）仍然异步：模型结论会改变文章的最终可见性（`clean` 才转 `visible`，`suspect` / 判定失败改回审核中），但不决定本次请求成败，见 [ADR-0025](./0025-risk-gated-publish.md)。判据是"结论要不要影响本次请求的结果"。
15. **零 DDL**：评分记录复用既有表，不加列、不加表。

## 理由与已否决方案

- **否决"闸门与人工审核串成一条流水线"**：两者失效模式完全不同——闸门会因 AI 额度/网络/模型不发 JSON 而失效，人工审核会因管理员不在而积压。绑死等于"AI 一挂投稿全停"或"管理员休假垃圾稿照发"。
- **否决"AI 不可用时放行"（fail-open）**：默认配置下闸门从未生效，且灌水者只要探测到"AI 一挂就全放行"就会主动去打它。
- **否决"AI 未配置就当闸门不生效"**：与失败关闭的语义自相矛盾，且会让"配置缺失"变成一条静默的旁路。
- **否决"评分留在事务内"**：一次 5–30 秒的模型调用占着事务等于钉死连接池。
- **否决"灰带上下各留一半"**：它挡不住阈值正上方的抖动。
- **否决"给维度下限单独加灰带 / 另设 `dimension_min_score`"**：多一个数字就多一处要解释的相互作用，"每项都要及格"正是"及格线"这个词的直觉含义。
- **否决"木桶替代总分"**：六项都 51 与六项都 90 会被同一标准放行，分数失去区分度；总分仍是"整体值不值得读"的粗粒度信号。
- **否决"只把 pass_score 抬高或只改提示词"**：两行祝福语在清晰与规范两项上照样拿高分；提示词是请求不是保证，能被"这次没遵守"绕过的判定不算判定。
- **否决"阈值必须锚定档界（防矛盾配置）"**：两者各自自由，矛盾从"接受作者看得到档名"处消解。
- **否决"多次采样取中位数"**：成本是每人每天 45 次调用；抖动改由固定温度 + 灰带抑制。
- **否决"分数不落库、只实时算"**：与异步补评分路径重复计费，且作者看不到自己被拒时的分数。
- **否决"把评分提示词整体搬进 skill"**：JSON 形状与维度键名是解析契约，写进可热改的文本等于让运营一次手滑就让所有评分解析失败。分工是代码管形状、文本管宽严。
- **否决"按文体豁免完整度下限"**：本站是个人博客，"通知 / 邮件"这类标签很容易被拿来当绕过口子；所有文体同一套维度底线。
- **否决"把闸门判定挪回 outbox"**：看起来更"合规"，但闸门就不再是闸门，退化成事后展示。

## 代价 / 不做什么

- **提交会变慢 5–30 秒**：前端必须有"评分中"状态与幂等保护，否则双击会变成双份配额 + 双篇文章。
- **误判不可复盘**：不保留分数历史，评分误判是不可申诉的黑箱；唯一缓解是灰带与人工复核。
- **可保存自相矛盾的配置**：作者可能看到"不合格文章 · 已通过"。
- **闸门依赖 AI 可用性**：AI 额度耗尽、上游故障时，开启闸门的站点投稿会被拒（失败关闭的有意代价，需靠运维告警而不是静默放行）。
- **短而好的文章会被误伤**：三行的精炼笔记也会被封顶到 40 分；闸门开着时，本站更愿意让"不够一篇"的东西留在草稿里。作者也可能同时收到两条驳回理由（总分不够 + 某项不够），这是真实情况，不做合并。
- **礼节词判据是启发式**：判据是"短 + 段落少 + 多数句命中"，缺一条就不触发；漏判时退回"过短"那条封顶。
- **不记录"因闸门被拒几次"**：拒稿次数只有审核任务与配额计数侧面反映。
- **不做**：采样校准、按文体的差异化维度权重（维持现有 20 套权重表）、评分历史留档、AI 分与人工分的一致性评估、按读者反馈回流调阈值。
- **零 DDL**：评分记录复用既有表，不加列、不加表。

## 当前生效约束

1. **闸门默认关闭**；零值配置即关闭，关闭时提交路径不触发评分与判定。
2. **开启闸门的保存动作必须校验 AI 可用**（总闸 + 至少一条启用模型），不满足即拒绝保存并返回 `article.quality_gate_requires_ai`。不得改成"警告后继续"。
3. **评分调用不得进入数据库事务**。任何提交路径的评分都必须发生在 `WithinTx` 之前；事务内只做落库与判定结果的写入。
4. **失败分四类错误码，不得合并**：`article.submit_quota_exceeded`、`article.score_unavailable`、`article.quality_rejected`、以及合规相关码。低分不是"失败"。
5. **评分场景温度恒为 0**，不得改为跟随站点配置。
6. **灰带只作用于总分**：实际放行线（总分）= `pass_score + gray_band_width`，UI 与文案都按这个线算差额；维度下限是 `pass_score` 本身，不加灰带、不共用。只改其中一个数字都会改变放行口径，必须同时改文案与测试。
7. **放行 = 总分过线 AND 六项都 ≥ `pass_score`**。不得只判其中一侧，也不得给维度下限单独加灰带。
8. **`weak_dimensions` 只列 `< pass_score` 的维度**，分最低的排最前；`gap` 只表示总分差额，被维度卡住时必须是 `0`（不是负数）。两者相互独立，可同时成立。
9. **评分宽严由运行时策略文本 `skills/scoring/SKILL.md` 注入**（`ai.scene_skills.scoring` 绑定）；代码只保留解析契约（JSON 形状、维度键名、分档数字）与不可让渡的底线，**冲突以更严者为准**，这句必须留在提示词里，不得删。提示词的解析契约不得进入 skill 正文；运营可改的只有宽严判断。
10. **形态硬封顶只在代码里生效**：`completeness ≤ 30/20`、`structure ≤ 45`、总分 `≤ 40/30`，并统一限制"总分 ≤ 最低维度 + 15"。封顶数字只在 `backend/internal/ai/scoring/ai_scoring_shape.go` 声明一次；改动必须同步 `skills/scoring/SKILL.md` 里的表格与测试。策略文本可以放松口径，但放不过硬封顶。
11. **摘掉 `scoring` 绑定不等于关掉底线**：内置形态下限必须始终在提示词与代码里；绑定缺失不报错。
12. **拿不到维度分时退回只看总分**，不得因此拒绝所有提交，也不得假装它过了木桶；**缺失维度兜底分必须低于及格线**（当前 40），不得改回 50。
13. **维度中文名只在前端一处映射**（`frontend/app/utils/scoreDimensions.ts`），后端只传英文键。
14. **不重算存量文章**：历史文章维持原分数与可见性，只影响新提交。
15. **及格线与四个档界自由可配、不做交叉校验**；不得在保存路径加"档界必须递增"之类的校验。
16. **评分结果必须落库（单行 Upsert）**，否则异步补评分会重复计费。
17. **闸门判定必须同步**，不得挪回发件箱。它是唯一允许 article app 直接调用别的模块的地方（`QualityGatePort`）；新增"影响本次请求结果的跨模块判定"时才可复用这条通道，其余副作用继续走 outbox。
18. 零 DDL 口径不变。
