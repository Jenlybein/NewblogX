# ADR-009: 删除"通用规则"同步路径，ES 同步只留文章搜索投影

## Status

Accepted（2026-10-26）

## Context

`internal/platform/cdc/river` 里长期并存两条"MySQL → ES"路径：

| | 通用规则路径 | 文章搜索投影 |
| --- | --- | --- |
| 配置 | `river.rule`：表 → 索引 + 字段白名单 + 类型转换 | 代码里固定 6 张表 |
| 数据来源 | 只用 binlog 那一行 | 回库按主键重读并 join 用户/分类/标签/置顶 |
| 文档形状 | 这张表自己的列 | 搜索卡片需要的一整篇 |
| 失败证据 | 完整 bulk body（可原样重发） | 曾是"表名+动作+行数"（不可重发） |
| 重试 | `doBulkWithRetry`（2 次 + 200ms） | 无 |

2026-10-26 的核查确认了三件事：

1. **通用路径对本项目的每一张表都不可达。** `OnRow` 先把 outbox、再把 6 张源表交给
   `handleArticleSearchProjectionEvent` 并提前 `return`；配置里 `source` 的 6 张表全在投影清单里，
   唯一的 `rule` 指的也是 `article_models`。
2. **它拼不出搜索文档。** 白名单只有 8 个列，缺作者名、分类名、标签、各项计数 ——
   即使可达，产出的文档也不是搜索结果要的那份。
3. **它独有的两项能力都不再被需要。** "删除类死信重投"的能力已由投影侧的
   `ProjectionReplayer`（带行主键、按主键重算）覆盖；`doBulkWithRetry` 从未作用于投影路径，
   所以删掉它不会让现在的同步失去重试。

与此同时，死信侧的语义已经收敛（ADR-008）：投影失败不再停掉整个 canal，
而是"记死信 + 继续跑"，且死信带 `ids` 可重投。**旧路径存在的最后一个理由（"只有它能把
bulk body 原样重发"）随之消失。**

## Decision

删除整条通用规则路径：

- 代码：`river/rule/`（整包）、`sync_request.go`、`sync_bulk.go`（只留 `saveProjectionErrorToDLQ`
  与 `buildCDCJobID`，已并入 `sync.go`）、`replay.go`（`ESReplayer`）、以及 `river.go` 里的
  `rules` / `prepareRule` / `parseSource` / `updateRule` / `ruleKey`。
- `sync.go` 的批量合并与重试循环一并删除；`syncCh` 从 `chan interface{}` 收窄成 `chan posSaver`，
  同步循环只剩"按 3 秒节流落位点"。
- 配置：`conf.River.Rules`、`flush_bulk_time`、`river.retry`、两份 `settings.yaml` 的 `rule:` 段、
  以及只为它存在的 `BLOGX_RIVER_INDEX`（搜索索引一直取 `es.index`，与它无关）。
- 装配：`analytics_wiring` 不再注册 `es_river` 执行器。
- 顺带删除因此变成死代码的 `es_service.Bulk`。

保留 `master`（位点）与 canal 的 dump 配置：**全量转储会把行按 INSERT 重放一遍，
投影分支照常把它们变成文档** —— 首次部署的数据初始化仍然可用。

## Consequences

**变好的：**

- 少约 1000 行、10 个文件。表清单从两份（`source` + `rule`）收敛成一份。
- 消灭一类"配置看起来在生效"的陷阱：`rule` 段在解析时是**非严格**的，
  删了字段却留着 yaml 只会静默失效。现在没有第二份配置可写错。
- 死信只剩 3 条流（`es_projection` / `outbox_relay` / `image_ref_river`），
  死信页上不会再出现一条永远不会有数据的 `es_river`。

**变差的 / 必须接受的：**

- **加一张"不需要 join 的表"进 ES，现在要写代码**，不能只改配置。步骤是：
  在 `article_search_projection.go` 的分派里加一个 case → 在 `projection_replay.go` 的
  `projectionReplayEvents` 里登记 `(表, 动作) → 事件类型` → 补一条映射用例。
  大约半小时，比"配置 + 猜字段"更可控。
- **ES 写入没有重试了。** 投影路径本来就是一次 `IndexBulk` 失败即落死信（以前也一样），
  所以这不是本次回归；但"想加重试"的人应该加在 `articlesync` 的批量写里，
  而不是恢复一条独立的同步路径。
- **历史 `es_river` 死信不再可重投。** 页面上仍显示流名（保留词表是为了历史记录可读），
  但点重投会得到 `unsupported`。需要补历史数据时用 `./server -es -s article-sync` 全量重建。
- 删掉的那批 `es_service` 单文档 API（`CreateDocument` / `Search` / `GetMapping` 等）
  在本次之前就已经没有生产调用方，属于既有历史包袱，不在本 ADR 范围内。

## Alternatives

- **保留但标注"当前不产生数据"**：成本是一个永不出数据的执行器 + 一份会误导人的 `rule` 配置。
  这是上一轮的选择，本轮的结论是"标注"挡不住下一个人照着它改配置。
- **把通用路径改成"配置 + 投影函数"**（配置里指定用哪个重建函数）：本质是给一个只有一个实现的
  场景加一层间接，且仍然需要为每张表写代码 —— 没有解决任何问题。
