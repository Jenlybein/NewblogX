# 03 · 契约：单一来源、生成流水线与类型真相（v1 归档）

> 归档自：`11-契约可用性方案.md`、`ADR-003-前后端契约单一来源.md`、`ADR-007-ID类型统一为string底层.md`
> 拍板时间：2026-10-24（ADR-003）/ 2026-10-26（ADR-007 + 契约可用性改造）
> 状态：**已交付并落地**
> 归档时实测：`backend/docs/swagger.json` = OpenAPI **3.1.0 / 92 path / 119 operation / 203 schema**

**一句话结论**：契约只有一个来源——**后端 Go 代码**。中间产物全部可再生成，任何"生成后手工修一遍"的环节都已删除。前端类型从 `openapi.d.ts` 派生，剩下的手写部分必须能回答"为什么契约里没有它"。

## 2. swag v2 的坑（踩过，逐条保留）

### 2.1 坑一：必须带 `--v3.1`，否则静默退回 Swagger 2.0

swag **只有 v1 输出 Swagger 2.0**（顶层是 `definitions` / `securityDefinitions` / `basePath`），而 `openapi-typescript` 明确只吃 OpenAPI 3.x。v2 靠 `--v3.1` 开关直出 3.1。

装成 v1 时的症状是**链式的**：`make openapi` 正常退出并产出 2.0 文件，直到前端 `pnpm openapi:types` 才报错——排查方向会被引到前端去。

### 2.2 坑二：带枚举的 domain 类型 + tag 里 `enums` 收窄 → 输出 `$ref` + `enum` 并存

v2 遇到「字段类型是带枚举的 domain 类型，tag 里又写了 `enums` 收窄」时，会**同时**输出 `$ref`（指向完整枚举）和 `enum`（收窄值）。`openapi-typescript` 只认 `$ref`，于是 `status: 1 | 2` 被放松成 `ArticleStatus`（=`1|2|3|4`）。

修法：给该字段加 `swaggertype`，强制 v2 输出内联枚举而不是 `$ref`。

```go
Status ArticleStatus `json:"status" binding:"required,oneof=1 2" swaggertype:"integer" enums:"1,2"`
// 契约：{"enum":[1,2],"type":"integer"}   ← 精确，无 $ref
// 前端：status: 1 | 2
```

| 注意 | 说明 |
| --- | --- |
| 只用于 5 个字段 | 不是全局方案 |
| 副作用 | `swaggertype` 会丢掉"这是 `ArticleStatus` 类型"的语义 |
| 使用判据 | 只在**该字段确实需要收窄**时才用 |

### 2.3 坑三：注解里不能写 `map[string]any` → 静默跳过整份契约写入

swag 报 `cannot find type definition: map[string]any` 之后，**跳过整份契约的写入**：

- exit code 仍是 **0**
- `swagger.json` **时间戳不变**（内容还是上一版）

必须用具名类型。本项目为此加了 `kernel.SiteConfigData`（定义在 `backend/internal/kernel/envelope.go`）。

> **这是三个坑里最危险的一个**：CI 里只看 exit code 会完全看不到失败，而且旧文件仍在，前端照旧生成，一切看起来正常。

### 2.4 另外两个（同类，一并记下）

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 注解引用跨包类型，那个包必须被文件 import | 注解是注释，不会让 import 生效 | 代码里不直接用该包时写 `_ "path"` 空白 import，swag 从 import 列表推断包名 |
| 批量替换注解时 pattern 漏了行首 `//` | 7 处注解变成 `// // @Success ...` 被注释掉，swag 静默丢弃、生成 `"responses": {}` | pattern 必须带 `//`；排查前先看一眼实际字节 |

## 3. 后端泛型响应类型

位置：`backend/internal/kernel/envelope.go`。这些类型**只服务契约**，业务代码不要拿它们构造响应（会让 `data` 变强类型，丢掉"任意 data"的灵活性）。

### 3.1 五个类型

| 类型 | JSON 形状 | 对应 helper | 用途 |
| --- | --- | --- | --- |
| `Envelope[T]` | `{"code":0,"msg":"成功","data":{...}}` | `res.OkWithData` | 统一响应外壳 |
| `ListData[T]` | `{"list":[...],"count":42}` | `res.OkWithList` | 分页列表（有总数） |
| `HasMoreListData[T]` | `{"list":[...],"has_more":true}` | `res.OkWithHasMoreList` | 游标 / 无限滚动 |
| `EmptyData` | `{}` | `res.OkWithMsg` | 只有提示语、没有数据体 |
| `SiteConfigData` | 自由键值块 | `/site/{name}` | 结构随 name 变，无法用固定字段表达 |

```go
type Envelope[T any] struct {
	Code int    `json:"code"`
	Msg  string `json:"msg"`
	Data T      `json:"data"`
}

type ListData[T any] struct {
	List  []T `json:"list"`
	Count int `json:"count"`
}

type HasMoreListData[T any] struct {
	List    []T  `json:"list"`
	HasMore bool `json:"has_more"`
}

type EmptyData struct{}

type SiteConfigData map[string]any
```

### 3.2 注解里的写法

```go
// @Success 200 {object} kernel.Envelope[kernel.ListData[http.ArticleListItem]]
// @Success 200 {object} kernel.Envelope[kernel.HasMoreListData[http.HistoryItem]]
// @Success 200 {object} kernel.Envelope[kernel.EmptyData]
// @Success 200 {object} kernel.Envelope[kernel.SiteConfigData]
```

swag v2 支持注解里写泛型，嵌套泛型、数组元素类型、`$ref` 全部正确。产物里的 schema 名形如：

```
myblogx_internal_kernel.Envelope-internal_article_adapter_http_ArticleAuthorInfoResponse
```

> **关键约束**：`ListData` vs `HasMoreListData` 必须按 handler **实际调用的 helper** 选。
> 第一轮批量迁移时用正则替换、没核对 handler 调用的是 `OkWithList` 还是 `OkWithHasMoreList`，
> 导致契约说 `{list,count}` 而实际返回 `{list,has_more}`——前端读 `has_more` 恒为 `undefined`（当 false 用），
> **编译器一个字都不会提示**，共 9 处。

## 4. 前端 `contract.ts` 的工具

两个前端各有一份同构的 `app/types/contract.ts`。

```ts
import type { components, paths } from "./openapi";

/** 契约原样（全字段可选），用于请求体 */
export type Schema<K extends keyof components["schemas"]> = components["schemas"][K];

/** 取某个操作的类型，如 Operation<"/banners","post">["responses"] */
export type Operation<P extends keyof paths, M extends keyof paths[P]> = paths[P][M];

/** ① 响应体：递归去掉 ? 和 | undefined */
export type RequiredSchema<K extends keyof components["schemas"]> = DeepRequired<components["schemas"][K]>;

export type DeepRequired<T> = T extends (infer U)[]
  ? DeepRequired<U>[]
  : T extends object
    ? { [K in keyof T]-?: DeepRequired<Exclude<T[K], undefined>> }
    : Exclude<T, undefined>;

/** ② 后端会返回 null 的字段 */
export type Nullable<T, K extends keyof T> = Omit<T, K> & { [P in K]: T[P] | null };

/** ③ 后端确实可能不返回的字段 */
export type OptionalFields<T, K extends keyof T> = Omit<T, K> & { [P in K]?: T[P] };
```

| 工具 | 用途 | 典型用法 |
| --- | --- | --- |
| `Schema<K>` | **请求体**。契约原样，全字段可选 | `Schema<"internal_auth_adapter_http.LoginRequest">` |
| `RequiredSchema<K>` | **响应体**。递归去可选 | `RequiredSchema<"internal_site_adapter_http.SEOResponse">` |
| `Nullable<T,K>` | 后端 `*T` 会序列化成 `null`，swag 不表达 null，只能前端显式声明 | `Nullable<RequiredSchema<"...ArticleDetailResponse">, "category_id" \| "cover_image_id">` |
| `OptionalFields<T,K>` | 后端确实可能不返回（`*T` + `omitempty`） | `OptionalFields<RequiredSchema<"...BaseInfoResponse">, "avatar_image_id">` |

**为什么 `RequiredSchema` 必须递归**：内置 `Required` 只作用于顶层属性，嵌套对象字段仍是可选（`author?: { avatar?: string }` 里 `avatar` 还是 `string | undefined`），业务侧照样到处判空。数组要单独分支，否则 `keyof T[]` 会展开成数组的所有方法名。

> 直接裸换成 `Schema<>` 实测会得到 **33 个编译错误**，根因是契约全字段可选 + 嵌套对象也全可选 + null 表达不了。

## 5. 可空性三态（必须记住）

| Go 写法 | JSON 里的实际表现 | TS 应该 | 用哪个工具 |
| --- | --- | --- | --- |
| `T` | 一定有值 | `T` | `RequiredSchema<K>` 即可 |
| `*T` | `null` 或值 | `T \| null` | `Nullable<T, K>` |
| `*T` + `omitempty` | **可能整个字段不出现** | `T \| undefined` | `OptionalFields<T, K>` |

**第三态最容易被忽略**：`RequiredSchema`（`DeepRequired`）会强制字段存在，而 `*T + omitempty` 在空值时整个字段不进 JSON。后果是任何构造该类型对象字面量的地方（比如加载失败时的兜底对象）**都编译不过**，因为它被迫编造一个值。正确做法是把它用 `OptionalFields` 放回可选。

**swag v2 无法输出 `type: ["string","null"]`**，三条路都实测过：

| 尝试 | 结果 |
| --- | --- |
| `extensions:"x-nullable"` | 契约出 `"x-nullable": true`，但 `openapi-typescript` 忽略它，仍生成 `string` |
| `swaggertype:"string"` | 本来就是 string，无变化 |
| swag 从 `*T` 自动推导 `nullable` | 不支持（源码里 `Nullable` 字段没有从指针赋值的路径） |

结论：**null 只能在前端侧解决，或后端侧去掉指针。** 本项目选了前端侧 `Nullable`。

### 6.4 顺带抓出的真实缺陷

"逐处核对注解形状 vs 真实 DTO"这一条抓出了多起**"契约写错 → 前端照着错的类型写 → 运行时静默失效"**：

### 6.5 仍然手写的 19 个（12 + 7），每个都有理由

| 类别 | 数量 | 为什么留着 |
| --- | --- | --- |
| 纯 UI 形状 | 7 | `ApiEnvelope` / `OptionItem` / `ChatSocketEnvelope` / `ThemeMode` / `HasMoreList<T>` / `LogListData<T>` —— 不对应任何接口 |
| SSE 帧载荷 | 3 | `/ai/diagnose` 是 `{string} string "SSE 流"`，契约里没有 JSON schema |
| 前端枚举字面量 | 2 | `AiDiagnoseIssueType` / `AiDiagnoseSeverity`，后端是 `string`，窄枚举是前端自己的需求 |

## 7. ADR-007：ID 类型底层统一为 string（类型即真相）

### 7.1 决策

**把 `ctype.ID` 底层从 `uint64` 改成 `string`。** 改之前的问题是一道算术题，不是偏好问题：

| | 值 | 位数 |
| --- | --- | --- |
| 现有雪花 ID | 372,842,048,379,686,912 | **18 位** |
| JS 安全整数上限 2^53-1 | 9,007,199,254,740,991 | 16 位 |
| uint32 上限 | 4,294,967,295 | 10 位 |

现有 ID 是 uint32 容量的 **8680 万倍**；且存量 ID 已全是 18 位，改生成器救不了老数据。

```go
type ID string                                  // 类型即真相

func (id ID) Uint64() uint64              { ... }   // 需要数值时显式取
func (id ID) IsZero() bool                { ... }
func (id ID) Uint64OrZero() uint64        { ... }
func (id ID) Value() (driver.Value, error){ ... }   // 入库仍转 int64
func (id *ID) Scan(src any) error         { ... }   // 出库仍从 int64 转回
```

**零 DDL**：数据库不动，`Value`/`Scan` 里照常转 int64，约束不受影响。

### 7.2 为什么不选最省事的方案 A（`.swaggo` 全局类型覆盖）

方案 A 是 1 行配置、5.6 秒生成，是 swag 官方支持的声明式机制。否决理由只有一条：

> **A 买的是"这次对了"，不是"以后都对"。**

- 只覆盖 `ctype.ID` 那 61 处；剩下 75 处（45 处裸 `uint64` 字段 + 约 30 处 `@Param` 注解）要另改
- 根因「类型是数字、传输是字符串」这层隐式转换**还在**
- 以后谁新写一个 `uint64` ID 字段，契约会再错一次，而且这次没人会注意到

E 消灭的是根因：隐式转换消失后，类型和 JSON 永远是同一个东西，**swag 不可能印错**，且 `.swaggo` 与后处理脚本都可删。代价是工作量翻倍，但换来的是**编译器强制审计**——`id == 0` 这类判断全部编译报错，等于把全后端 ID 使用点强制过一遍。

（其余备选：B 逐字段 `swaggertype` 会让契约撒谎——那些裸 `uint64` 发出的 JSON 真的就是数字；C 维持后处理脚本正是本次要消灭的对象；D 换 huma/go-fuego 需 123 个接口全部重来。）

### 7.3 统一策略与 R12 规则

| 层 | 做法 |
| --- | --- |
| `ctype.ID` | 底层改 `string`，提供 `Uint64()` / `IsZero()` / `Uint64OrZero()` / `ParseID()` |
| 其余 9 个 domain ID 类型 | 全部收敛为 `ctype.ID` 的别名或同构 string 类型 |
| 裸 `uint64` 的 ID 字段（实际 175 处） | 收编进 `ctype.ID` —— 同时修掉前端丢精度的潜在 bug |
| 非 ID 的整型字段（237 处 `Page`/`Limit`/`DiggCount`/`Size`/`Score`） | **一个都不动**，值小、前端用 number 没问题、swag 印 integer 也是对的 |

配套守卫：`backend/tools/archcheck/rules_id.go` 的 **R12 `id-must-be-ctype`**——字段名以 `ID` / `IDs` / `Id` / `Ids` 结尾且类型是原生整型（含 `*` / `[]`）则违规。7 条人造用例（4 正例 + 3 豁免反例），由 `TestAllRulesHaveSelfCheck` 元测试强制要求存在，**基线 0**。

> 关键实测：只改 `ctype.ID` 时残留 **192 处**转换错误；把 10 个 ID 类型统一后塌缩到 **22 处**。这验证了"10 套 ID 类型并存本身就是债"。（后续实测又把这一项修正为 175 处，最终收编 149、豁免 26。）

### 7.4 四类豁免（共 26 项）

| 范围 | 数量 | 理由（一句话） |
| --- | --- | --- |
| `internal/platform/log/**` | 6 | 对应 ClickHouse `UInt64` 列，外部真相在 `01-logs.sql`，改 string 会与列类型不一致 |
| `internal/testkit/schema/**` | 17 | 同上 |
| `ServerID`（conf ×3 + canalbase ×1） | 4 | MySQL 复制协议 / 雪花机器号，uint32 节点编号，非业务 ID |
| `initializedID`（platform/idgen） | 1 | 雪花 worker 编号 |

**原则**：「类型即真相」要求对齐的是**各自的外部真相**。HTTP 契约的真相是"JSON 里 ID 是字符串"，所以 DTO 用 `ctype.ID`；日志表的真相是"CH 列是 UInt64"，所以落盘结构保持 `uint64`。两边都对齐了，就不存在"两套说法"。

### 7.5 唯一不能靠编译器发现的风险

**6 处 ID 大小比较会静默变语义**：字符串比较下 `"10" < "9"` 成立，数值比较下 `10 > 9`。

| 文件 | 行 | 后果 |
| --- | --- | --- |
| `platform/es/articlesync/article_sync_load.go` | 615 / 618 | tag 排序 tie-breaker，不丢数据但排序结果变 |
| `article/apptest/repo_social.go` | 47 / 152 / 112 / 271 | fake 的 nextID 推进与 `sort.Slice`，同上 |

必须改成显式数值比较（`a.ID.Uint64() < b.ID.Uint64()`），或确认为无害后保留并加注释。项目有 golden 测试（20 篇 × 12 接口逐字节比对），排序一变 golden 就红——不会静默漏过去。

同类隐性 bug（已修）：`internal/chat/domain/chat.go` 的 `BuildSessionID` 在字符串比较下双方算出不同 `session_id` → **私信串号**。
