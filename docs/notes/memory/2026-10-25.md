## 收尾：① MdToSafe 并发缺陷 + ③ outbox 落地（已 commit 3d1db81）

### ① MdToSafe 并发缺陷（已修复）
- **根因不是"goldmark 没做并发隔离"**：`mdrenderer.Renderer`（blackstork goldmark-markdown v0.1.3）
  把 `previousLineBlank`/`wasAtNL`/`source`/`bufs` 等渲染状态存在**渲染器实例**上；
  构造时 `previousLineBlank=true`（"文档开头视为空行"），`Render` 结束不复位、开头也不重置。
  → 复用实例必然继承上一次的脏状态。
- **sync.Pool 修不了**（实测：panic 消失但仍有 ~12% 输出不一致）——归还再取出只是换个
  goroutine 继承脏状态；字段在 internal 包私有，外部无法重置。
- 修法：`MdToSafe` 每次调用 `newSafeEngine()`；`rawHTMLMarkdownEngine` 经并发+`-race` 验证
  可安全共享，保持单例。**去掉了 safeEngine 包级变量，杜绝再被共享**。
- 新增 `utils/markdown/md_concurrency_test.go`（32 goroutine × 100 次 × 8 输入）：
  修复前**直接 panic**（flush 里 index out of range [-1]），不只多换行 → 生产并发下会打挂请求。
- golden 恢复 `t.Parallel()`，连跑 3 次绿；开销实测：newSafeEngine ~12µs、MdToSafe ~22–28µs，
  只在文章创建/更新两处写路径调用，可接受。

### outbox TTL 清理（对应"TTL 收尾"，MySQL 侧；与 L.8 的 ClickHouse TTL 是两件事）
- **只清理已终结行**：`done` 默认保留 7 天、`dead` 默认 30 天；
  `pending/failed/processing` **永不清理**（清掉等于丢事件）。
  `dead` 能删是因为转 dead 时已同步写 `cdc_dead_letter_models`，证据还在。
- **必须物理删除**：`OutboxEventModel` 内嵌 `Model`（含 `gorm.DeletedAt`），
  普通 `Delete` 是软删、回收不了磁盘 → 用 `Unscoped()`。
- **分批删**：先按 `status + updated_at < cutoff` 捞 ID，再按 ID 删；
  不依赖 MySQL `DELETE ... LIMIT` 方言（sqlite 不支持），单批默认 1000、
  单轮最多 20 批（`maxCleanupBatches`），避免大事务长时间持锁。
- **接线**：`Relay` 新增 `cleanupLoop`（`safego.Go`，随 `Run()` 启动、`Close()` 收尾），
  `Options` 加 4 个旋钮 + `withDefaults`（done 168h / dead 720h / interval 1h / limit 1000）。
  `Cleanup()` 内部再调一次 `withDefaults` 防御"绕过 New 直接构造 Relay"导致 retention=0 全删。
- **配置**：`conf/conf_outbox.go`（新）+ `Config.Outbox` + `settings.yaml` 的 `outbox:` 段；
  `app/outbox_wiring.go` 的 `relayOptions(infra)` 映射（0 值交给 withDefaults）。
- **测试**：`relay_integration_test.go` 加 `TestRelayCleanup`（过期 done/dead 物理删除、
  未过期保留、三种非终结态即使很老也保留）。造陈旧 `updated_at` 必须用原生 SQL
  `UPDATE ... SET updated_at=?`——GORM 的 autoUpdateTime 回调会把它改写回 now。
- **验证**：`go build ./...` / `go vet -tags integration` / gofmt 干净；
  `TestRelayCleanup` PASS（真 MySQL）；archcheck 236（未涨）；`bash scripts/check.sh backend` exit 0 全绿。

### S4.5b chat 内部机制（本轮已读透，下次直接写）
**表**：`chat_session_models`（user_id+receiver_id 唯一，含 last_msg_*、clear_before_msg_id、
unread_count、is_top/is_mute、软删）；`chat_msg_models`（session_id+send_time 索引，read_at、
msg_status、msg_type）；`chat_msg_user_states`（msg_id+user_id 唯一，软删时间 = 该用户删除时间）。

**关键语义**
- 会话 ID：`chat:<小ID>:<大ID>`（`buildSessionID`）。
- 发消息：事务内 `EnsureSessions`（双向各一条，OnConflict 恢复软删并把 unread 归零）
  → 插消息 → `UpdateLastMsgSession`（双方更新 last_msg；接收方 unread+1；**期望 RowsAffected=2**，
  自聊时=1 且不加 unread，数量不对就报错）。
- 消息类型：1 文本 / 2 图片（Content 存 JSON）/ 3 语音 / 4 视频 / 5 文件 / 6 表情 /
  7 Markdown / 8 已读通知。会话摘要：文本原文，图片"[图片]"，Markdown 走 `markdown.MdToText`，截 20 字。
- 已读：只更新 `receiver_id=me AND msg_status<read` 的消息；事务里同时按会话
  `unread_count = max(0, unread-delta)`（CASE SQL）；然后按 (sender, session) 聚合推 WS 已读回执。
- 单条删除：写 `chat_msg_user_states` 软删（OnConflict 覆盖 deleted_at），**不动原消息**；
  普通用户列表用 `NOT IN (subquery)` 排除，管理员查（type=2）不过滤。
- 会话删除：`clear_before_msg_id = max(msg.id)`、`unread_count=0`、会话软删；
  列表按水位 `id > clear_before_msg_id` 过滤。type=2 管理员查用 `Unscoped()` 连软删一起看。
- 发送限流：`CheckAndReserveChatSend` → 分钟级（单会话 30、跨会话 60）+ 自然周配额
  （陌生人 1 条、单向关注/粉丝 3 条、好友无限）；落库成功 `Commit`（单向关系会清对向周配额），
  失败 `Rollback` 释放预占。陌生人还需对方 `StrangerChatEnabled`。
- WS：`/chat/ws-ticket` 生成 24 字节随机 ticket 存 Redis 1 分钟（payload=userID+sessionID）；
  `/chat/ws` 先试 Authorization，再试 ticket + `AuthenticateSession`；upgrader 用
  `middleware.IsAllowedOriginRequest`；读限制 4K、pong 60s、ping 54s；在线池支持多连接，
  推送前先 `Snapshot` 复制连接再逐条写（不要持锁写 socket）。
- 在线/离线：接收人不在线时消息已落库，但给发送方回"接收人不在线"。

**缺口**：`internal/platform/http/ws` 不存在，必须先建（Upgrader/Conn/OnlineStore/PingLoop），
再把 chat 的 domain/app/adapter + WS handler 接上；最后删 `api/chat_api`、`service/chat_service`、
`repository/chat_repo`、`repository/follow_repo`、`service/follow_service`。

### 门禁慢的真正原因（2026-10-25 深挖，commit d0f70d8）
**不是 MySQL 慢，也不是测试本身慢 —— 72% 的时间在链接测试二进制。**

实测数据：
| 场景 | 耗时 |
|---|---|
| `go test -tags integration -run '^$' ./...`（只编译不执行） | 67–75s |
| 同样命令但完整执行 | 93s |
| 代码未变、再编译一遍 | 67s（完全没变快） |

- 160 个包 / 80 个有测试 / **单个测试二进制 76MB**（gorm+gin+ES+AWS SDK 全打进去）
- 80 个包各产出一个独立二进制，Windows 链接器慢 + 杀毒实时扫描
- **`-count=1` 是"禁用 Go 测试结果缓存"的开关**，check.sh 一直带着它
  → 每次都重新链接 80 个 76MB exe

去掉后实测（代码未改）：
- 无 race：74s → **7.5s**
- 带 race：173s → **26s**

**最终三档（稳态）**：默认含 race **48s** / `BLOGX_FAST=1` **36s** / 改动前 5分20秒。
首次全量：3分15秒（race）/ 1分36秒（fast）。

**关键设计**：check.sh 默认允许缓存，但**必须打印"其中 N 个包命中缓存（未重新执行）"**，
否则"门禁绿了"可能只是缓存给的。`BLOGX_NO_CACHE=1` 强制真跑；CI 用 `-count=1`。

**还能从根上省的（未做）**：
- 合并测试包（80 → 少数几个）：能砍掉大部分链接时间，但要重组 80 个包，属独立改造。
- 换 Linux/WSL：链接快 3–5 倍。
- Windows 上把项目目录 + GOCACHE 排除出 Defender 实时扫描（需管理员，用户自己决定）。

**注意**：切换 `-race` 开关会换一套缓存 key，导致一次全量重跑（1分36秒）。
选定一档后别来回切，或者接受这一次代价。

### S5.5 已做完（commit ea430cc）—— 上一轮只建任务没做，被用户指出
**教训**：发现问题后只"建任务"等于把尾巴换个地方放。用户要的是"发现即清"。

**做法**：`/_origin/*` 与 `/_backend/*` 全是"代理到后端根目录"的别名，而后端只有
`r.Static("/uploads", "./uploads")` + `/api` 两组挂载，没有根路径静态 → 三路径做同一件事。
- nginx 删 4 段 location（`/_origin/`、`/_backend/api/chat/ws`、`/_backend/api/`、`/_backend/`）
  → 现只留 `= /admin`、`^~ /admin/`、`= /api/chat/ws`、`^~ /api/`、`^~ /uploads/`、`/`
- 删 `frontend/server/routes/{_backend,_origin}`，保留 `api/[...path].ts`、`uploads/[...path].ts`
- `assetProxyBase` 默认 `/_origin` → **`/uploads`**（nuxt.config / env/common.env / compose 三处）
- `avatar.ts` 删 `/_backend/x → {基址}/x` 兼容改写
- 同步 3 个测试文件（avatar/auth/ai），README 去旧路径
- **没做 301 过渡**：环境只有本地可重建，无外部调用方

**踩坑**
- `avatar.ts` 判定顺序必须是"先判已带基址、再判以 / 开头"，否则 `/uploads/a.png`
  → `/uploads/uploads/a.png`（不报错，只是图全 404）
- `nginx -t` 首次失败是**容器里解析不到 compose 服务名**（DNS，不是语法）；
  upstream 换回环地址后才 `syntax is ok`
- Git Bash 的 `/tmp` 与 Windows python 的 `/tmp` 不是同一路径，
  临时文件要用 `C:/Users/Jen/AppData/Local/Temp/...`
- `cmd | tail` 会吞掉 cmd 的退出码，验证 typecheck 要单独 `> log; echo EXIT=$?`
