## 1. 本轮修掉的问题

### 1.1 IP 归属地库从未被加载（功能缺陷，已修）

`deadcode` 查出 `core.InitIPDB` **零调用**，而 `utils/requestmeta` 一直在调 `ipmeta.GetAddr`。

后果链：

```
InitIPDB 没人调 → ipv4Searcher/ipv6Searcher 恒为 nil
  → GetAddr 对任何真实 IP 都走 `if ipv4Searcher == nil { return "未知地址" }`
  → 登录日志、用户列表的 addr 字段全是「未知地址」
```

而仓库里躺着 `resources/ipbase/ip2region_v4.xdb`(11MB) + `ip2region_v6.xdb`(36MB)，  
**从来没被打开过**。

修法（`app/bootstrap.go`）：

```go
logger := core.InitLogrus(&cfg.Log, &cfg.System)
// IP 归属地库。之前这里漏了这一步……
if err := core.InitIPDB(); err != nil {
    logger.Warnf("IP 归属地库加载失败，addr 将显示为「未知地址」: %v", err)
}
```

三个设计决定：

| 决定                               | 理由                                                               |
| -------------------------------- | ---------------------------------------------------------------- |
| 返回 `error` 而不是内部 `logger.Fatalf` | `addr` 只是展示字段，缺库时 `GetAddr` 自己会降级；不该因为资源缺失让整个服务起不来               |
| 失败只告警                            | 同上。启动中断的代价远大于「地址显示未知」                                            |
| 路径向上探 3 层而不是写死相对路径               | 容器里 CWD 是 `/app`，`go test ./core/` 的 CWD 是 `backend/core`，两者基准不同 |

**回归测试的判据特意不是"返回非空"**：`GetAddr` 有兜底分支，库没加载时也会返回「未知地址」，  
所以旧测试 `TestGetIpAddrBranches`（只断言非空）永远通过——正是它让缺陷藏了这么久。  
新测试 `TestInitIPDBLoadsRealLibrary` 先 `InitIPDB()`，再断言公网 IP **不是**「未知地址」。

### 1.2 go.mod 依赖标记不准（已修）

`go.mod` 149 行，其中 3 个直接依赖在代码里零 `import`。逐个验证后发现性质不同：

| 依赖                        | 真相                                  | 处理              |
| ------------------------- | ----------------------------------- | --------------- |
| `segmentio/kafka-go`      | 确实是死依赖，全仓 0 引用                      | **删除**          |
| `gabriel-vasile/mimetype` | 被 `go-playground/validator` 间接使用    | 标 `// indirect` |
| `golang.org/x/image`      | 被 `freetype` / `base64Captcha` 间接使用 | 标 `// indirect` |

**为什么不跑 `go mod tidy`**：它会顺手把 `go` 指令从 1.25.1 抬到工具链版本、重排 indirect 标记，  
产生 60 行无关改动（M7 时踩过一次）。这里只手改 3 行，`go build` + `go vet` 验证。

## 2. 待产品决策的缺陷（4 个）

原则：**这些不是"技术债"，是产品行为和类型描述不一致。** 我没有擅自改行为，  
只在类型里写明「后端当前不返回、恒为 undefined」，让缺口可见而不是被 `RequiredSchema` 藏起来。

| # | 位置              | 症状                                         | 根因                                                                                                       | 可选修法                             |
| - | --------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 1 | 首页「精选文章」区块      | **整块坏掉**：链接指向 `/article/undefined`，标题/封面全空 | `GET /articles/top` 返回的是**文章 ID 字符串数组**（`ListTops` → `[]domain.ArticleID`），前端却按 `ArticleTopItem[]`（对象）渲染 | ① 后端把 id 解析成展示对象返回；② 前端拿 id 再查一次 |
| 2 | 主页「点赞/收藏/评论」    | 三个数字**恒为 0**                               | `BaseInfoResponse` 没有 `digg_count` / `favor_count` / `comment_count`                                     | ① 后端补聚合；② 撤掉这三个指标                |
| 3 | admin 用户列表「角色」列 | **恒为空**（编辑弹窗里能改，列表看不到）                     | `AdminUserItemResponse` 没有 `role` / `status`                                                             | ① 后端补字段；② 撤掉该列                   |
| 4 | admin「恢复已隐藏文章」  | **流程走不到**                                  | 该页用 `/search/articles`，而搜索只索引可见文章（`VisibilityStatus` 枚举只有 `"visible"`）                                   | ① 管理端单独的文章列表接口；② 搜索对管理员返回全部      |

第 1 项最严重：它不是"少个统计数字"，是**首页一个区块整体不可用**。

## 3. 工程缺口（按影响排序）

### 3.1 CI 完全不碰契约 ⚠️ 最高优先级

`.github/workflows/ci.yml` 里有 backend / backend-integration / archcheck / frontend-lint /  
frontend-typecheck / frontend-test / gates-canary 七个 job，**没有一个安装 swag 或生成契约**。

后果：有人改了 Go 注解但忘了跑 `make openapi`，`docs/swagger.json` 会静默过期，  
前端类型照着过期契约生成，**门禁全绿但契约是错的**。

补一行就够：

```yaml
- name: 契约未过期
  run: |
    make openapi
    git diff --exit-code docs/swagger.json
```

代价是 CI 要装 swag（`go install github.com/swaggo/swag/v2/cmd/swag@v2.0.0-rc6`），  
多约 30 秒。**这笔交易很划算**：契约是前后端唯一的耦合点，它过期了整条链都不可信。

### 3.2 admin 站零测试

`frontend_admin/vitest.config.ts` 里写着 `passWithNoTests: true` 并注释了"当前没有任何测试用例"。  
所以 `vitest run` 输出 `No test files found, exiting with code 0` ——**门禁里那一项是空转的**。

admin 有约 50 个页面（用户管理、文章审核、日志查询、媒体库），**0 个用例**。  
配置里"保留入口是为了降低加第一个测试的门槛"这个理由成立，但要承认：  
**现在 `frontend_admin: test` 这一项提供的保障是 0。**

### 3.3 `deadcode` 没有进闸

本轮的 IP 库缺陷就是它查出来的——一个"写了但没人调用"的函数，编译、vet、测试、archcheck  
**全都发现不了**。目前 Go 侧的死代码检查只靠人工。

现状：`deadcode -test ./...` 报 88 条，其中大部分是 `apptest` 包的测试辅助函数（正常）。  
真正值得处理的是生产代码里的几条：

| 位置                                                                     | 说明          |
| ---------------------------------------------------------------------- | ----------- |
| `internal/ai/search/ai_search_analyze.go` `AnalyzeArticleSearch`       | AI 搜索分析，未接入 |
| `internal/ai/search/ai_search_rewrite.go` `AnalyzeArticleSearchIntent` | AI 搜索改写，未接入 |
| `internal/kernel/request.go` `PagedRequest.Normalize`                  | 分页归一化，未使用   |

这三条是"实现了但没接线"，属于功能缺口而非垃圾代码，需要产品判断。  
建议：**把 `deadcode` 作为定期审查工具（不是硬门禁）**，因为它的输出需要人工区分  
"死代码"和"未接线的功能"。

### 3.4 契约精度（已知，收益递减）

| 指标                            | 现值                 | 说明                                               |
| ----------------------------- | ------------------ | ------------------------------------------------ |
| 字段总数 / 必填                     | 949 / **44（4.6%）** | 响应 struct 没有 required 的语义载体，见 11 §7.5，**不再作为目标** |
| 表达 null 的字段                   | **0 处**            | swag 无此能力，靠前端 `Nullable` / `OptionalFields` 声明   |
| 内联 properties 块（无独立 schema 名） | **192 处**          | 前端引用不到，只能手写；要给它们起名是后端注解的活                        |
| 无类型的 list                     | **0 处**            | 已解决                                              |
| 接口响应解析失败                      | **0 / 123**        | 已解决                                              |

要再往上走只有一条路：**给嵌套结构定义具名类型**（后端加 DTO），把 192 处内联块收编。  
这是纯体力活，收益是前端能少写十几个手写类型。

### 3.5 前端残留的三处匿名响应类型

```
frontend/app/services/article.ts:4    request<{ list: ArticleTopItem[]; count: number }>   ← 就是第 2 节第 1 项那个 bug
frontend/app/services/site.ts:22      request<{ list: BannerItem[]; has_more: boolean }>   ← 与契约一致，可换
frontend_admin/app/services/admin.ts:123  request<{ list?: ImageListItem[]; count?: number; has_more?: boolean }>  ← /images 契约里没有
```

这三处是上一轮"从服务层挖出重复类型"的同款模式（那次挖出了 `getPublicFavoriteFolders`  
手写了 4 字段的假类型）。数量已经很少，但 `article.ts:4` 那一处正是活的 bug。

## 5. 建议的处理顺序

| 顺序 | 做什么                       | 成本                   | 为什么排这个位置                   |
| -- | ------------------------- | -------------------- | -------------------------- |
| 1  | **CI 加契约校验**（§3.1）        | 极低（几行 YAML + 装 swag） | 唯一能防止"整条链静默失真"的改动，且不依赖任何决策 |
| 2  | **修首页精选区块**（§2 第 1 项）     | 中（需定后端返回形态）          | 唯一一个"用户直接看到坏了"的缺陷          |
| 3  | 另外 3 个产品缺陷定方案（§2 第 2–4 项） | 低-中                  | 都是"补后端字段"或"撤 UI"，需产品判断     |
| 4  | admin 补第一批测试（§3.2）        | 中                    | 先给 auth/审核这类"错了代价大"的页面加    |
| 5  | 契约内联对象具名化（§3.4）           | 高（体力活）               | 收益只是前端少写十几个类型，可最后做         |

**不建议现在做的事**：为了把 required 从 4.6% 提上去而给响应 struct 加 `binding:"required"`。  
那是 949 个字段的人工判断，而 `RequiredSchema` 已经在消费侧解决了问题——重复且容易写错  
（注解写错的契约比没有契约更糟）。
