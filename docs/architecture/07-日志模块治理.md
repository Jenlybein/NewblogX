# 07 · 日志模块治理

> 本文只解决一件事：**把日志从"请求路径里同步写结构体"改成"有界、类型化、不阻塞、可计损的异步管道"**。
> 所有结论附真实文件与行号。目标不是"少记日志"，而是**记该记的、记不爆、丢得明白**。

---

## 0. 本版拍板：审计字段策略（选项 1 · 纯热库）

> 2026-10-24 决策记录。本节是**硬约束**，覆盖下文"现状 / 目标"中与它冲突的描述。

**一句话**：审计日志默认**不记全量原始 body/header**；热库（ClickHouse）只存元数据 + 业务语义 + **失败请求**的脱敏限量体；不做冷存储分层。

| 项 | 决定 |
| --- | --- |
| `request_body_raw` / `response_body_raw` / `request_header_raw` / `response_header_raw` | **删除**（应用字段 + ClickHouse 列），不再采集全量报文 |
| `request_body` / `response_body` | 保留，但**仅在请求失败（`success=0`）时填充**；成功请求留空；列加 `CODEC(ZSTD(9))` |
| header | 只保留白名单（`content-type` / `user-agent` / `referer` / `x-request-id` / `x-trace-id`），不导全量 |
| 采集 | HTTP 边界 `io.LimitReader` 限量读（硬上限 1MB），再脱敏 + 截断到 ≤16KB；**禁止 `any`、禁止传结构体** |
| 冷存储分层 | **不做**（选项 1）；`payload_ref` 列预留但默认不写，将来升级再加 |
| 闸门 | archcheck 新增 `log-no-any`：审计输入禁 `any`、禁结构体 |

**为什么**：全量 raw 同时踩了三个雷——① 它是最长的行，采集/传输最先出问题；② 它逼着"反射整棵树再截断"，是 §1.2 爆炸路径的根源；③ 请求体里几乎必然含 PII，落库即有合规风险。而审计真正要回答的"谁、何时、对什么、做了什么、结果如何"，由 `action_name` / `target_type` / `target_id` / `user_id` / `result` 这些**业务语义字段**承载，不依赖原始报文。

## 1. 现状：为什么会被打爆

### 1.1 五个真实病灶（按危害排序）

| # | 病灶 | 证据 | 后果 |
| --- | --- | --- | --- |
| L1 | **任意结构体反射序列化** | `utils/logsafe/sanitize.go:52-127`，`SanitizeValue(any)` 用 `reflect` 递归 + `json.Marshal`，**遍历时无深度/大小上限** | 一个大对象/深嵌套对象先被完整反射一遍才截断 → 瞬时大内存 + CPU 尖刺 |
| L2 | **审计把 request/response 整体塞进来** | `write_action_audit.go:49-55` `RequestBody any` / `ResponseBody any`；`write_audit_body.go:218-231` 仍走 `SanitizeValue` | 大 JSON、列表页响应、上传体被整体反射；16KB 截断发生在**反射之后** |
| L3 | **同步写文件、全局互斥** | `write_sink.go:25-45`：`json.Marshal` 后 `s.mu.Lock()` 直接 `file.Write`；`init_logrus.go` 的 `FileDateHook.Fire` 同样同步 `file.Write` | 磁盘慢 → 请求 goroutine 排队 → 并发一高，内存与延迟同时涨 |
| L4 | **每条日志调雪花 ID（可能触 DB）** | `log_base.go:53-57`、`init_logrus.go:41-48` | 日志路径依赖 ID 服务；高并发下争用，故障时整条链路退化 |
| L5 | **全量 `SetReportCaller(true)`** | `init_logrus.go` `logger.SetReportCaller(true)` | **每条日志**都抓一次调用栈（`runtime.Caller`），CPU 成本随日志量线性上升 |
| L6 | **采集侧会丢且会重** | `fluent-bit.conf:12-65`：5 个 tail 输入，`Mem_Buf_Limit` 10–20MB，`Skip_Long_Lines On`（超长行直接丢），`Read_from_Head On`（重启可能重读）；`input_format_allow_errors_num=1000`（静默丢坏行） | ClickHouse 慢时缓冲打满 → 丢日志；重启 → 重复日志；**丢失不可见** |

### 1.2 一个具体的爆炸路径（推演）

```
一次列表接口返回 2MB JSON
  → 审计中间件把整个响应读进内存（PrepareCapturedBody(raw []byte)）
  → MarshalAuditValue → SanitizeValue 反射整棵树
  → marshalStructuredWithinLimit 反复尝试 8 档 leaf 截断，每次都 json.Marshal 一遍
  → 最终仍可能 > 16KB → truncatePlainText
  → 结果同步写文件（全局锁）
  → 同时 logrus 每条 entry 抓调用栈 + 调雪花 ID
```

单个请求可能触发**数次 2MB 级反射 + 多次 Marshal + 一次磁盘同步写**。并发 100 就是"内存打爆 + RT 抖动"。

### 1.3 现有设计里有价值的部分（不要推翻）

- `write_audit_body.go` 已有 **16KB 上限 + 敏感 key 黑名单 + 多级 leaf 截断 + 嵌套折叠**（`MaxBodyBytes`、`sensitiveKeys`、`collapseNested`）——方向是对的，问题在**执行位置**（在反射之后）和**输入类型**（`any`）。
- 已有 **trace_id / span_id / parent_span_id** 贯穿（`log_middleware.go`），这是可观测性的地基，保留。
- 已有 **五类日志分表**（runtime / login / audit / cdc / replay）与 ClickHouse TTL，分类模型正确，保留。
- `logsafe.SlogAttrToField` 用于 river 的 slog 适配，思路正确，但同样缺限额。

## 2. 目标：六条硬约束

任何设计必须同时满足这六条，缺一不可：

1. **内存有界**：进程内日志缓冲有硬上限（条目数 + 字节数双限），超限**丢最旧或丢新并计数**，绝不无限增长。
2. **请求路径不阻塞**：`Emit` 只做"投递"，不做序列化、不做磁盘、不做网络。投递失败可丢（审计除外，见 3.4）。
3. **类型化事件**：日志字段是**封闭类型集合**（`string/int64/uint64/float64/bool/duration/time/[]string`），**禁止 `any`、禁止传结构体**。违反由 `archcheck` 阻断。
4. **边界采集**：request/response body 在 HTTP 边界用 `io.LimitReader` **限量读取**，先截断再脱敏再序列化；绝不"先反射整个对象再截断"。
5. **不丢要可计损，要丢要可解释**：每类日志有明确的"可丢/不可丢"策略；所有丢弃都有计数器与采样告警。
6. **日志自身可观测**：队列深度、丢弃数、刷盘延迟、WAL 积压、写入错误率，全部有指标；`/healthz` 能反映日志管道健康。

## 3. 目标架构

```
业务代码
  │  log.Emit(ctx, event)        ← 只传类型化事件，O(1) 投递
  ▼
┌─────────────────────────────────────────────┐
│ Emitter（有界环形缓冲，双限额）                 │
│  - entries 上限 N（默认 8192）                 │
│  - bytes   上限 M（默认 8MB）                  │
│  - 满：runtime 丢弃+计数；audit 落 WAL+计数     │
└───────────────┬─────────────────────────────┘
                │ 单写协程（批量）
                ▼
      ┌───────────────────┐
      │ Batch（≤500 条/1s） │
      └─────┬─────────┬───┘
            │         │
      成功  ▼         ▼ 失败/超时
   ClickHouse    本地 WAL（append-only）
   (HTTP 批量)      │
                    ▼ Replayer（退避重放）
                 ClickHouse
```

### 3.1 类型化事件模型

```go
// internal/platform/log/event.go
type Kind uint8
const (
    KindRuntime Kind = iota
    KindAccess
    KindAudit
    KindLogin
    KindCDC
    KindReplay
)

// Field 是封闭的字段联合，禁止 any。
type Field struct {
    Key string
    Val fieldValue // 内部私有 union：str/i64/u64/f64/bool/dur/time/strs
}

func Str(k, v string) Field
func Int(k string, v int64) Field
func Uint(k string, v uint64) Field
func Bool(k string, v bool) Field
func Dur(k string, v time.Duration) Field
func Time(k string, v time.Time) Field
func Strs(k string, v []string) Field   // 有长度上限
```

事件是**具体结构体**，字段全部是标量：

```go
type AuditEvent struct {
    Base
    Method, Path   string
    StatusCode     int
    ActionName     string
    TargetType     string
    TargetID       string
    Success        bool
    RequestBody    []byte // 已脱敏+已截断的 JSON，≤16KB；仅失败时填充（见 §0）
    ResponseBody   []byte // 同上，仅失败时填充
    RequestHeaders map[string]string // 仅白名单
    ResponseHeaders map[string]string
}

type Base struct {
    EventID    uint64    // 本地单调计数，见 3.5
    TS         time.Time
    Level      Level
    Kind       Kind
    Service    string
    Env        string
    InstanceID string
    RequestID  string
    TraceID    string
    SpanID     string
    ParentSpanID string
    EventName  string
    ErrorCode  string
    ErrorMsg   string
    UserID     uint64
    IP         string
    Extra      map[string]string // key 白名单 + value ≤256B + 总 ≤2KB
}
```

**关键差别**：没有 `any`，没有 `reflect`，序列化是直接写已知字段。`Extra` 也只能是 `map[string]string`，从类型上消除"把结构体塞进来"。

### 3.2 Emit 必须 O(1)

```go
func (e *Emitter) Emit(ctx context.Context, ev Event) {
    if !e.levelEnabled(ev) { return }
    if !e.sample.Allow(ev) { e.metrics.Sampled(ev.Kind()); return }

    rec := encode(ev) // 只做字段拼装 + 估算大小，不 Marshal
    if e.bytes+rec.size > e.maxBytes || len(e.ring) == cap(e.ring) {
        e.overflow(ev)  // runtime: drop+count；audit: WAL
        return
    }
    select {
    case e.ring <- rec:
        e.bytes += rec.size
    default:
        e.overflow(ev)  // 永不阻塞
    }
}
```

- **不做 `json.Marshal`**：`encode` 只计算大小并保留字段；真正序列化在写协程批量做。
- **不做磁盘/网络**：全部在写协程。
- **`ctx` 只用于取 trace 字段与取消**，不用于阻塞等待。

### 3.3 写协程：批量 + 退避 + WAL

```go
func (w *Writer) run() {
    ticker := time.NewTicker(w.flushInterval) // 默认 1s
    batch := make([]Record, 0, w.batchSize)   // 默认 500
    for {
        select {
        case rec := <-w.ring:
            batch = append(batch, rec)
            if len(batch) >= w.batchSize { w.flush(batch); batch = batch[:0] }
        case <-ticker.C:
            if len(batch) > 0 { w.flush(batch); batch = batch[:0] }
            w.replayer.Tick() // 重放 WAL
        case <-w.stop:
            w.drain(batch); w.flush(batch); return
        }
    }
}
```

`flush` 策略：
- 主路：ClickHouse HTTP 批量 `INSERT ... FORMAT JSONEachRow`，超时 3s，失败退避重试（100ms→1s→5s，最多 3 次）。
- 仍失败：把整批写 **WAL 文件**（按 kind + 日期分文件，单文件 ≤64MB，写完 fsync 可配置）。
- `Replayer` 后台按序重放 WAL，成功后截断；WAL 积压超阈值 → 告警并降级（只保 audit）。

### 3.4 可丢 / 不可丢

| 日志类 | 队列满 | ClickHouse 挂 | 说明 |
| --- | --- | --- | --- |
| runtime / access | **可丢**，计数 + 采样告警 | 可丢（或极短 WAL） | 运行日志允许损失，换取业务稳定 |
| audit / login | **不可丢**：落 WAL | 落 WAL，无限重试（有积压上限告警） | 合规要求 |
| cdc / replay | **不可丢**：落 WAL | 落 WAL | 用于对账 |
| security | 不可丢 | 落 WAL | 登录/越权事件 |

### 3.5 去掉雪花 ID 依赖

现状 `log_base.go:54` 与 `init_logrus.go:42` 每条日志都调 `db_service.NextSnowflakeID()`。改为：

- 进程启动生成 `instance_id`（配置或随机）。
- 进程内 `atomic.Uint64` 单调递增作为 `event_id`。
- 唯一性 = `(instance_id, event_id)`；ClickHouse 排序键已含 `service, ts, event_id`，足够。
- 若跨实例需要全局唯一，用启动时生成的 `ULID` 前缀 + 本地序号，**仍然零 DB 调用**。

### 3.6 去掉全量调用栈

- 生产默认 `SetReportCaller(false)`。
- 仅 **error 级** 按配置采样抓栈（`runtime.Caller` 或 `debug.Stack`，8KB 上限）。
- dev 环境可开全量，但用 build tag / 配置隔离，不带到生产。

### 3.7 边界采集（替代反射）

HTTP 审计中间件：

```go
const maxCapture = 16 << 10 // 16KB

func captureBody(r io.Reader) ([]byte, bool) {
    buf := make([]byte, 0, maxCapture)
    n, _ := io.ReadFull(io.LimitReader(r, maxCapture+1), buf[:cap(buf)])
    // 若 n > maxCapture → truncated=true
    return redactAndCompact(buf[:min(n, maxCapture)], truncated)
}
```

- **先限量读，再脱敏，再压缩**；绝不把整个 body 读进内存。
- header 用**白名单**（`content-type`、`user-agent`、`referer`、`x-request-id`、`x-trace-id`），不再导全量 header。
- 非 JSON 直接截断字节；JSON 用 `json.Decoder` 限深（≤8 层）+ 限节点数（≤2000）。
- 业务代码**不允许**自行传 `RequestBody any`。

### 3.8 采样与限流

- 按 `event_name` 做令牌桶（默认 100/s），超限合并为 1 条 `log_suppressed` 摘要（每 10s 一次）。
- access 日志：成功请求 1:1（低流量）或 1:10（高流量，可配）；4xx/5xx 全量。
- DEBUG 生产关闭；INFO 高频路径可降为每秒首条。

### 3.9 配置（替代现有 `conf.Logrus` 的散字段）

```yaml
log:
  level: info
  format: json
  async:
    enabled: true
    buffer_entries: 8192
    max_bytes: 8MB
    flush_interval: 1s
    batch_size: 500
  sink:
    type: clickhouse        # clickhouse | file | both
    clickhouse:
      addr: http://clickhouse:8123
      database: blogx_logs
      timeout: 3s
    wal_dir: /app/var/log-wal
  sampling:
    default_rate: 1.0
    rules: { "http_request": 0.1 }
  capture:
    body_limit: 16KB
    header_allowlist: [content-type, user-agent, referer, x-request-id, x-trace-id]
    redact_keys: [password, token, authorization, cookie, secret]
  retention:
    runtime_days: 30
    audit_days: 180
    login_days: 180
```

启动时校验：DSN 不通 → **fail fast**（不要带病启动）；`wal_dir` 不可写 → fail fast。热更新只允许 `level` 与 `sampling`（`atomic.Pointer`）。

## 4. ClickHouse 侧

现状 `deploy/docker/clickhouse/init/01-logs.sql` 的问题：

| 问题 | 现状 | 目标 |
| --- | --- | --- |
| 所有表 TTL 都是 **120 天** | 运行日志也存 120 天，成本高 | runtime 30 天；audit/login 180 天；cdc 30 天；replay 30 天 |
| 大文本列无压缩 | `message/request_body/...` 裸 `String` | `CODEC(ZSTD(3))`；body 列加 `CODEC(ZSTD(9))` |
| 审计 4 个 `*_raw` 列 | 全量原始请求/响应报文进热库 | **删除**；`request_body`/`response_body` 仅失败时写，`CODEC(ZSTD(9))` |
| 无采样/聚合 | 全量明细 | runtime 可加 1 分钟聚合物化视图，明细 7 天后降采样 |
| 无冷热分层 | 全在本地盘 | 90 天以上 audit 导出 OSS/S3（可选） |
| `event_id UInt64` | 依赖雪花 | 本地单调 + `instance_id`，唯一性由组合键保证 |

补充约束：`request_body` / `response_body` 列在应用侧已 ≤16KB；DB 侧再加 `CHECK` 或写入前校验，防止旁路写入超限。

## 5. 可观测性：日志管道自身

必须暴露的指标（先日志/内部 metrics，后接 Prometheus）：

| 指标 | 含义 | 告警阈值 |
| --- | --- | --- |
| `log_queue_depth{kind}` | 环形缓冲当前深度 | > 80% 持续 1min |
| `log_dropped_total{kind,reason}` | 丢弃数（满/采样/超限） | 1min 内 > 0（runtime 允许但不为零告警） |
| `log_flush_duration_seconds` | 批量刷盘耗时 | p99 > 1s |
| `log_write_errors_total` | ClickHouse 写入失败 | > 0 持续 1min |
| `log_wal_backlog_bytes` | WAL 积压 | > 256MB |
| `log_suppressed_total{event_name}` | 被限流合并数 | 突增 |

`/healthz` 增加：`log_pipeline: ok|degraded|failing`（队列、WAL、最近刷盘时间三者综合）。

## 6. 迁移路径（与 04 的 L 阶段对齐）

| 阶段 | 动作 | 验收 |
| --- | --- | --- |
| **L1 收口** | 新建 `internal/platform/log`（Event/Emitter/Writer）；`Emitter` 先只接 **file sink**，输出格式与现有一致；替换 `log_middleware` 与 `EmitActionAudit` 的写入路径 | 队列有上限；压测下进程 RSS 平稳；请求路径无 `json.Marshal` |
| **L2 换血** | 接 ClickHouse 批量写入 + WAL + Replayer；关闭 fluent-bit 的 5 个 app tail；保留其容器日志采集 | 断网 ClickHouse 10min，audit 不丢；恢复后自动补齐；无重复（幂等键 `instance_id+event_id`） |
| **L3 拆除** | 删除 `service/log_service` 旧写路径、`utils/logsafe` 反射、`init_logrus.go` 的两个 Hook；`log_service` 只留查询侧 | `rg "SanitizeValue|SetReportCaller|NextSnowflakeID" internal/platform/log` 为 0 |
| **L4 上闸** | archcheck 新增规则：日志字段禁 `any`、禁传结构体、单条 ≤32KB、`Extra` 必须 `map[string]string` | 存量违规先 `--warn` 列出，再逐模块清零 |

### 关键验收脚本

```bash
# 1. 请求路径不得出现序列化/磁盘写
( cd backend && ! grep -rn "json.Marshal\|file.Write\|os.OpenFile" internal/platform/log/emit.go )

# 2. 日志字段类型封闭
( cd backend && go run ./tools/archcheck --rule=log-no-any --error ./internal/... )

# 3. 有界性：压测 1 万 QPS 1 分钟，RSS 不随日志量线性增长
#    观察 log_dropped_total 有值、log_queue_depth 不持续 100%

# 4. audit 不丢：断开 ClickHouse，写 1000 条 audit，恢复后 count == 1000 且无重复
```

## 7. 与测试体系的关系

日志模块的可测性由**端口化**保证：

- `log.Emitter` 是接口，测试用 `testkit/log.Recorder` 捕获内存事件，断言**类型化字段**而不是字符串。
- 丢弃策略、采样、WAL 重放、脱敏、截断，全部有独立单测（不连 ClickHouse）。
- `internal/platform/log` 的纯逻辑（encode/redact/truncate/sample）**零外部依赖**，可 `t.Parallel`。
- 集成测试用 `//go:build integration` + testcontainers 起 ClickHouse，验证批量写入与 TTL。

详见 [06-测试体系重构](./06-质量保障与治理.md)。

## 8. 一句话总结

> 现状不是"日志写得太多"，而是**写日志这件事被放在了错误的层、用了错误的类型、走了错误的同步路径**。
> 目标是把日志变成一个**有界、类型化、异步、可计损**的基础设施：业务只管 `Emit` 一个值对象，剩下的交给后台管道。
