# ADR-008：死信重投（DLQ Replay）——让"同步失败"有闭环

## Status

**Accepted**（2026-10-26）

## Context

现状（证据见 [12 §7](../../architecture/12-重构收尾审查.md)）：

- 三个 CDC 子链路（`es_river` / `es_projection` / `outbox_relay` / `image_ref_river`）
  在重试耗尽后都会调 `deadletter.SaveBatch` 写 `cdc_dead_letter`，状态一律 `pending`；
- 但**没有任何代码把状态改成别的值**、也**没有任何代码去读它重做一次** ——
  死信表是个只进不出的黑匣子，出问题只能人工进 MySQL 翻，然后手动补数据；
- 展示端半成品更误导人：`replay_event_logs` 的**读端**（analytics `/logs/replay`）
  和写入函数 `writer.EmitReplayEvent` 都写好了，但**没有任何地方调用它**，
  表永远是空的，而且前端一个页面都没调过这两个接口。

一句话：**"失败留证据"做了，"照证据补救"没做。**

## Decision

建一套最小但完整的死信重投闭环，分四层：

```
管理端页面（列表 + 勾选重投 + 回放日志）
      ↓
POST /logs/dead-letter/replay        GET /logs/dead-letter
      ↓ 端口 domain.DeadLetterReplayer
platform/cdc/dlq.Service  ── 编排：取记录 → 分派执行器 → 更新状态 → 写回放日志
      ├── es_river      → 用死信里的 bulk body 重投 ES（幂等）
      └── outbox_relay  → 把 outbox 行从 dead 重置为 pending（交给中继自己重投）
```

### 一、状态机只用已有列，零 DDL

```
pending ──重投成功──> resolved（终态，不再参与重投）
pending ──重投失败──> pending（retry_count+1、error_code/error_msg 覆盖为本次失败）
```

**不引入 `replaying` 中间态**。理由：重投是人工、低频、单实例的管理操作；
中间态会带来"进程崩溃留下僵尸 replaying"的恢复逻辑，而它防的问题
（两人同时点同一个按钮）最坏结果是**重投两次**——而两个执行器都是幂等的
（ES 按文档 id index/delete；outbox 重置是纯状态写），重复执行无害。
**用"幂等执行器"换掉"分布式互斥"，代价低得多。**

### 二、支持范围按 payload 自洽性划定，不支持的要讲清原因

| stream | 死信 payload 里有什么 | 重投怎么做 | 支持 |
| --- | --- | --- | --- |
| `es_river` | `{index,type,id,parent,pipeline,data}` —— **完整的 ES bulk body** | 原样再投一次（delete 按 `Record.Action` 还原） | ✅ |
| `outbox_relay` | `{payload}` + `CdcJobID=outbox:<id>` | 把该 outbox 行 `dead → pending`、`attempts=0`，由中继按自己的退避重投 | ✅ |
| `es_projection` | `{schema,table,action,rowCount}` —— **没有主键** | 不可能是"重投"：不知道是哪一行 | ❌ 返回明确原因：需重建该表投影 |
| `image_ref_river` | `{table,row}` / `{table,before,after}` / `{owner_id,ref_type}` | 技术上可行，但 `row` 是 `[]any` 经 JSON 往返后数字变 float64，重建行快照的类型还原风险高 | ❌ 返回明确原因：重新保存该业务对象即可触发重建 |

不支持的流不是"以后再说"，而是**当场告诉操作员该改用什么办法**。
`POST /replay` 对这类记录返回 `unsupported` + 一句人话，不改数据库。

### 三、回放日志：把闲置的写端接上

每次重投尝试（成功或失败）都 `writer.EmitReplayEvent` 写一条到 ClickHouse
`replay_event_logs`，字段直接取自死信记录：`cdc_job_id/stream/source_table/action/
target_key/retry_count/result`。这样：
- 管理端「回放日志」页第一次真正有数据；
- 同一条死信的"失败→重投→再失败→再重投→成功"有完整时间线（`cdc_job_id` 可串）。

### 四、幂等与安全边界

- **已 `resolved` 的记录不再重投**，返回 `skipped`（避免重复打 ES）。
- 更新状态用条件更新（`WHERE id=? AND status<>'resolved'`），不引入锁。
- **不自动重投**。死信可能是"代码 bug 导致必然失败"，自动重投只会把 ES 打热。
- 重投不修改死信里的 payload —— 失败证据保持原样，便于事后比对。

## Consequences

**变好的：**

- 同步失败的处置从"进 MySQL 手改"变成"页面上勾选重投，结果立刻可见"。
- 死信状态有了终态，运维能区分"还没处理"和"已经补上了"。
- `replay_event_logs` 从死代码变成有数据的时间线。

**变差的 / 需要接受的：**

- 多了 3 个契约接口和 1 个管理端页面，需要维护。
- `outbox_relay` 的重投是"重置状态"而非"立即执行"，最长要等一个中继轮询周期
  （当前默认 2s 退避起步）。这是有意的：复用中继自己的重试与背压，不另开一条投递路径。
- `es_projection` / `image_ref_river` 仍然只能人工处置。要真正支持它们，
  得先改**落死信时**的 payload（带上主键/行快照），那是另一个改动。

## Alternatives

### A. 只给页面，重投仍靠人工 SQL

- 成本最低，但"看得见补不上"，等于把问题挪个地方。**否**。

### B. 自动重投（定时扫描 pending 死信重试）

- 听着省事，但死信多半是"改之前必然失败"的（字段不兼容、索引不存在）。
  自动重投会在故障期间把 ES 打出一片 400，且掩盖真实原因。**否**。
  人工触发天然带"我先看看为什么失败"这一步。

### C. 重投走消息队列（每条死信投给 MQ，由消费者慢慢重放）

- 引入新基础设施，收益是把重投变成异步可削峰；但当前死信量级（人工处理）
  完全用不上。**否，等真有量再说**。

## 执行口径

- 零 DDL：只用 `cdc_dead_letter` 已有列（`status` / `retry_count` / `error_*` / `updated_at`）。
- 新增契约接口的响应必须用 `kernel.Envelope[ListData[T]]`（后端注解引用真实 DTO）。
- 门禁：`TestContractMatchesRoutes` 会自动要求这 3 个新接口在路由表里存在。
